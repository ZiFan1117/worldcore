## 零、使用说明（填完全文后请删除本章）

### 0.1 这份文件解决什么问题

模块号是本仓库全套文档与代码的**主键**：需求追溯矩阵（`../02-需求类/03-需求追溯矩阵.csv`）、
概要设计、模块接口契约、详细设计、单元测试用例编号、代码目录、CI 门禁——**全都靠模块号串起来**。

因此模块号一旦引入混乱（重号、跳号、复用、随手改），追溯链会立刻断裂。
本文件的作用就是：**把模块号当成受控配置项来管理。**

### 0.2 与 `skeleton` 骨架的一致性（强制）

本登记表是**人读的视图**，`skeleton/` 骨架中的**模块注册表**是**机器读的视图**。两者必须一致。

| 视图 | 位置 | 形态 | 使用者 |
|---|---|---|---|
| 人读视图 | 本文件 §二 登记表 | Markdown 表格 | 评审、审计、新人上手 |
| 机器读视图 | `skeleton/modules.py` 的 `module_definitions()` → `ModuleDef` → `ModuleRegistry` | Python 代码中的模块契约声明 | 框架装配、依赖解析、CI 门禁 |

**字段映射（必须一一对应）**

`ModuleDef` 的字段定义见 `skeleton/module_system.py`；本表与它按下表对应：

| `skeleton/modules.py` · `ModuleDef` 字段 | 本文件 §二 登记表列 | 说明 |
|---|---|---|
| `module_id` | **模块号** | 必须匹配 `M\d{2}` |
| `name` | **模块名称** | |
| `version` | （契约版本，见 `03-模块接口契约.md`） | 登记表不重复登记 |
| `responsibility` | **职责** | |
| `not_responsible` | （非职责，见 `03-模块接口契约.md` §3） | 代码中已强制声明 |
| `depends_on` | **依赖模块** | 集合语义，登记表用分号分隔 |
| `provides` | **提供接口** | 代码中为类/方法名，登记表中填 `IF-*` 编号，两者须指向同一能力 |
| `owner` | **负责人** | |
| `implemented` | **状态**（`已实现` / 非 `已实现`） | 布尔值与状态枚举的映射 |
| —— | **所属分层** | 由模块号段位推导（§1.2），代码中不重复存 |
| —— | **首次登记日期 / 废弃日期** | 生命周期台账，代码中不存 |

**一致性要求**

| 编号 | 要求 | 校验方式 |
|---|---|---|
| C-1 | 登记表中的每个模块号，在 `skeleton/modules.py` 中有且仅有一个 `ModuleDef` 条目 | `python skeleton/run_skeleton.py` 的模块注册校验 |
| C-2 | 登记表的「依赖模块」列与 `ModuleDef.depends_on` **完全一致** | 依赖拓扑检查（无环、无跨层违规） |
| C-3 | 登记表的「提供接口」列与 `03-模块接口契约.md` 中的契约一一对应，且与 `ModuleDef.provides` 指向同一能力 | 契约清单比对（`CV-01`） |
| C-4 | 模块号必须符合 §一 的生成规则（分层分带内） | 模块号生成器 / CI 校验脚本 |
| C-5 | 任何一侧不一致时，**以代码注册表为事实、以本表为待更新项**，并在同一次提交内对齐 | 代码评审（R4） |

> **为什么必须两边都有**：只有代码注册表 → 评审与审计没有可读入口；只有 Markdown 表 → 框架无法自动装配。
> 两边都要，且必须一致——这是本仓库"文档与代码不漂移"硬要求在模块维度上的具体化。
>
> **门禁工具也会读本表**：`tools/trace_matrix.py` 的 `load_known_modules()` 会同时从**本文件**与 `skeleton/modules.py`
> 提取全部 `M\d{2}` 作为"已登记模块号"白名单。RTM 里出现未登记的模块号 → 门禁报 ERROR。
> **因此本表漏登记一个模块，会直接让 CI 失败。**

## 一、模块号生成规则

### 1.1 基本格式

```
┌─────────────────────────────────────────────┐
│   M 01                                      │
│   │  └── 2 位十进制序号（01–99，左补零）      │
│   └───── 固定前缀，表示"模块"（Module）      │
└─────────────────────────────────────────────┘
```

| 项 | 规则 |
|---|---|
| 格式 | `M` + **2 位序号**，序号范围 `01`–`99` |
| 书写 | **必须左补零**：写 `M01`，不写 `M1`；写 `M20`，不写 `M20.1` |
| 字符集 | 大写字母 `M` + 阿拉伯数字，**不得出现小写、下划线、连字符、后缀**（如 `M20a`、`M_20`、`M20-core` 一律非法） |
| 总容量 | 最多 99 个模块号 |
| 二级细分 | 模块内部的类/函数/文件**不另占模块号**，用模块内的命名约定表达 |
| 一对一 | **一个模块号 = 一个可独立评审、可独立测试的模块**，与代码目录一一对应 |

> **为什么要 2 位固定宽度**：字符串排序即自然排序，`M01 < M02 < … < M20` 不会出现 `M10 < M2` 的字典序陷阱；
> 也让 CI 工具的正则校验（`^M\d{2}$`）简单可靠。

### 1.2 分层前缀细分（模块号段位分配）

模块号**按分层分带分配**，使模块号本身就能表达该模块在架构中的位置与允许的依赖方向。

| 分层 | 号段 | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|---|
| **表现层** | **`M01`–`M19`** | 界面、输入校验、视图组装、请求/响应转换 | 业务层（`M20`–`M39`）、公共/工具层（`M80`–`M99`） | 禁止直连数据访问层与基础设施层 |
| **业务层** | **`M20`–`M39`** | 业务规则、用例编排、事务边界、领域状态流转 | 数据访问层（`M40`–`M59`）、基础设施层（`M60`–`M79`）、公共/工具层 | 禁止反向依赖表现层 |
| **数据访问层** | **`M40`–`M59`** | 持久化、查询、外部数据源适配、缓存读写 | 基础设施层、公共/工具层 | 禁止包含业务规则 |
| **基础设施层** | **`M60`–`M79`** | 日志、配置、认证、MQ、缓存、调度等技术能力 | 公共/工具层 | 禁止依赖业务层与表现层 |
| **公共/工具层** | **`M80`–`M99`** | 无业务语义的通用能力（日期、字符串、校验、错误码基类） | **不依赖任何其他层** | 禁止依赖任何业务/技术模块 |

**依赖方向铁律**：**依赖只能从上往下**（表现 → 业务 → 数据访问 → 基础设施 → 公共工具），
**禁止反向依赖，禁止跨层跳跃（表现层不得直连数据访问层）**。依赖图必须是有向无环图（DAG）。

```
  M01 ─── M19   表现层    ┐
  M20 ─── M39   业务层    │  依赖方向
  M40 ─── M59   数据访问  │  ↓ ↓ ↓
  M60 ─── M79   基础设施  │
  M80 ─── M99   公共/工具 ┘  （最底层，不依赖任何层）
```

### 1.3 分配规则（分配前必读）

| 编号 | 规则 | 说明 |
|---|---|---|
| **MR-1** | **在所属分层号段内，按顺序取下一个未使用的号** | 表现层从 `M01` 起、业务层从 `M20` 起、数据访问层从 `M40` 起、基础设施层从 `M60` 起、公共工具层从 `M80` 起 |
| **MR-2** | **编号一经分配，永不复用** | ⚠️ **模块废弃后编号作废，不回收、不递补**。`M20` 废弃后，下一个业务层模块取 `M27`（或当前最大号 +1），**不是** `M20` |
| **MR-3** | 号段用尽即停止在该层新增模块 | 号段用尽说明该层职责过载，应重新审视架构（提 R5），而**不是**挤占其他层号段 |
| **MR-4** | 模块拆分：保留原号给主模块，新增模块取新号 | **禁止**把 `M20` 拆成 `M20-M20.1` 这类子编号；拆出的部分独立取号 |
| **MR-5** | 模块合并：保留承载主要职责的号，另一个号登记为「已废弃」 | 废弃号不得再被引用；RTM 中引用该号的条目必须同步改指向 |
| **MR-6** | 模块**改名不改号** | 名称可变，号不变（历史追溯依赖号的稳定性） |
| **MR-7** | 换层 = 换号 | 模块从业务层移到基础设施层，必须取新号并把旧号登记为「已废弃」 |
| **MR-8** | 分配必须先登记后编码 | 未在本表登记的模块号，**代码不得引用**（CI 会校验） |

> ⚠️ **MR-2 是本节最重要的一条。** 复用废弃编号会制造"幽灵追溯"：
> 历史文档、旧测试用例、旧缺陷单都指向 `M20`，而新 `M20` 是另一个模块，追溯链直接指错方向。
> 编号是**一次性消耗品**，99 个够用是常态。

### 1.4 模块号生成流程

```
① 确定模块职责 → 判定所属分层 → 定位号段
        ↓
② 查本表：该号段内当前最大号 + 1（跳过所有已用号，含已废弃号）
        ↓
③ 在本表新增一行：模块号 / 名称 / 分层 / 职责 / 负责人 / 首次登记日期 / 状态 = 设计中
        ↓
④ 在 skeleton 模块注册表中同步注册（号、名称、依赖、对外接口）
        ↓
⑤ 定义该模块的接口契约（03-模块接口契约.md）→ R2 框架评审
        ↓
⑥ 骨架跑通校验（R3）：注册表可解析、依赖无环、装配成功
```

> **可用工具**：`python skeleton/run_skeleton.py` 提供模块注册、依赖拓扑与**模块号生成**的参照实现，
> 生成逻辑与本节规则一致（号段归属 + 跳过已用号 + 永不复用）。

### 1.5 号段容量预警

| 分层 | 号段 | 容量 | 预警阈值 | 达阈值时的动作 |
|---|---|---|---|---|
| 表现层 | `M01`–`M19` | 19 | 已用 ≥ 15 | 审视是否应合并界面/拆分子域为独立部署单元 |
| 业务层 | `M20`–`M39` | 20 | 已用 ≥ 16 | 审视是否应按子域再分层（提 R5） |
| 数据访问层 | `M40`–`M59` | 20 | 已用 ≥ 16 | 审视仓储是否过度拆分 |
| 基础设施层 | `M60`–`M79` | 20 | 已用 ≥ 16 | 审视是否引入过多第三方封装 |
| 公共/工具层 | `M80`–`M99` | 20 | 已用 ≥ 16 | 审视是否在造轮子（优先用标准库） |

### 2.1 「状态」列取值枚举

| 取值 | 含义 | 允许的后续状态 |
|---|---|---|
| `设计中` | 已分配模块号，设计文档在写 | → `骨架中` / `已废弃` |
| `骨架中` | 已以桩/Mock 形式接入骨架（S3） | → `实现中` / `已废弃` |
| `实现中` | 正在编码与单元测试（S4） | → `已实现` / `已废弃` |
| `已实现` | 模块评审（R4）通过 | → `已变更` / `已废弃` |
| `已变更` | 框架变更（R5）后需回归改造 | → `已实现` / `已废弃` |
| `已废弃` | 模块作废，**模块号随之作废且永不复用** | 终态（不再流转） |

> **注**：状态不是"进度汇报"，而是**门禁可用性**的机器可读信号。
> 例如 CI 可以拒绝引用状态为 `已废弃` 的模块号，或在 RTM 中出现 `设计中` 模块时给出警告。

### 2.2 「所属分层」与「依赖模块」的校验规则

| 编号 | 规则 | 违反后果 |
|---|---|---|
| V-1 | 模块号必须落在其「所属分层」对应号段内 | CI 失败：模块号与分层不符 |
| V-2 | 「依赖模块」中每个号必须已在**本表**登记 | CI 失败：引用了未登记模块 |
| V-3 | 依赖方向必须自上而下；不得反向、不得跨层跳跃 | CI 失败：依赖方向违规 |
| V-4 | 依赖图必须无环 | CI 失败：存在循环依赖（**R2 一票否决**） |
| V-5 | 「提供接口」中每个 `IF-*` 必须在 `03-模块接口契约.md` 中有对应契约 | 契约清单比对失败 |
| V-6 | 状态为 `已废弃` 的模块号，不得出现在任何「依赖模块」列中 | CI 失败：引用了废弃模块 |

## 四、模块生命周期登记

### 4.1 新增登记

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 模块号 | ✅ | 按 §1.4 流程生成 |
| 模块名称 | ✅ | 动宾/名词短语，≤ 12 字 |
| 所属分层 | ✅ | 五层之一 |
| 职责 | ✅ | 一句话 + 可选要点，**须写清"不负责什么"**（详见 `03-模块接口契约.md`） |
| 依赖模块 | ✅ | 无依赖填「无」 |
| 提供接口 | ✅ | 无对外接口填「无」 |
| 负责人 | ✅ | `<姓名>` |
| 状态 | ✅ | 新登记固定为 `设计中` |
| 首次登记日期 | ✅ | `<YYYY-MM-DD>` |

### 4.2 变更登记

| 变更类型 | 是否保留原号 | 必须执行的动作 |
|---|---|---|
| 改名 | ✅ 保留 | 更新「模块名称」，在 §五 变更记录留痕 |
| 职责调整 | ✅ 保留 | 更新「职责」+ 同步更新 `03-模块接口契约.md` + 若影响接口则提 R5 |
| 拆分 | ✅ 原号给主模块 | 新模块按 §1.4 取新号；更新双方依赖与接口 |
| 合并 | ✅ 保留主号 | 被合并号置为 `已废弃` 并填废弃日期；同步 RTM 中所有引用 |
| 换层 | ❌ 取新号 | 旧号置 `已废弃`；新号按新分层号段分配 |

## 六、填写指引

1. **最常见错误：复用废弃的模块号。** 例如 `M20` 废弃后又把新模块叫 `M20`。这会造成历史文档、旧测试用例、旧缺陷单全部指错方向。**编号一经分配永不复用，废弃即作废。**
2. **最常见错误：模块号不按分层号段分配。** 业务层模块写成 `M05`，会立刻破坏"号段即分层"的可读性与 CI 的依赖方向校验。分配前先定分层，再在号段内取号。
3. **最常见错误：一个模块号对应多个代码目录，或多个模块挤在一个目录里。** 模块号必须与代码目录**一一对应**，否则"模块可独立评审、可独立测试"无从谈起（FC-5 测试不可达）。
4. **最常见错误：Markdown 登记表与 `skeleton` 模块注册表不一致。** 两边说法不同时，框架装配用的是代码注册表，评审看的是本表，结果必然在集成时爆炸。**改一边就改另一边，同一次提交完成。**
5. **最常见错误：「职责」写成功能列表，不写"不负责什么"。** 只写做什么，边界必然在实现阶段被不断侵蚀（职责漂移）。职责必须成对：负责什么 + **明确不负责什么**（见 `03-模块接口契约.md`）。
6. **最常见错误：为了凑追溯，把需求映射给"已废弃"或"设计中"的模块。** 映射必须指向真实承载该需求的模块；若模块尚未实现，应在 RTM 中标 `<TBD-01>` 并写明责任人，而不是虚指。
