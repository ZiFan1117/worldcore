# 需求追溯矩阵（RTM）· 使用说明

> **文档编号规则**：`<项目代号>-RTM-<顺序号>-v<主版本>.<次版本>`，示例 `<项目代号>-RTM-001-v1.0`
> **适用阶段**：**S1 需求工程**建立，**S2 / S4 / S5 / S6 / S7 全程维护**（每次需求、设计、代码、测试变更都必须回写）
> **依据标准**：**GB/T 8567-2006**《计算机软件文档编制规范》（需求可追溯性要求）；GB/T 9385-2008（需求唯一标识要求）；过程依据 GB/T 8566-2022
> **文档状态**：**模板说明（Template）** · 配套文件为同目录的 `03-需求追溯矩阵.csv`

## 一、这份文件是什么

`03-需求追溯矩阵.csv` 是**需求 → 设计 → 代码 → 测试**的单点真相（Single Source of Truth）。

它不是"汇报用的表格"，而是**CI 门禁的输入**：`tools/trace_matrix.py` 会读取这个 CSV，
校验追溯链是否完整，不完整就直接让流水线失败。

> **红线（不可裁剪）**：需求基线与需求追溯矩阵是本仓库明确规定**不允许裁剪**的三项之一
> （见 `docs/00-标准依据/标准依据.md` §四）。任何项目都必须有 RTM。

## 二、列定义（共 14 列，列名不可改名、不可调序、不可增删）

| # | 列名 | 必填 | 取值 / 格式 | 说明 |
|---|---|---|---|---|
| 1 | **需求编号** | ✅ | `REQ-F-001` / `REQ-N-001` | 与 SRS 中的编号**逐字符一致**。`F` = 功能，`N` = 非功能。**唯一、永不复用**（需求删除后该行删除，编号作废不回收） |
| 2 | **需求名称** | ✅ | ≤ 20 字 | 与 SRS 卡片「名称」字段一致，便于人工检索 |
| 3 | **优先级** | ✅ | `P0` / `P1` / `P2` | 与 SRS 一致。门禁会对 P0 施加更严格判定 |
| 4 | **需求基线版本** | ✅ | `req-baseline/v1.0` | 该需求被基线化的标签。变更后基线版本递增，**历史行不覆盖**，另起新版本行或更新此列并留变更记录 |
| 5 | **设计模块号** | ✅ | `M20` 或 `M20;M40` | 实现该需求的模块号（分号分隔，无空格）。必须存在于 `02-模块清单与模块号登记表.md`；**尚未分配时填 `<TBD-01>` 并在备注写明责任人** |
| 6 | **设计文档章节** | ✅ | `HLD §3.3;LLD §3.2` | 需求在概要/详细设计中的落点（分号分隔）。章节号必须真实存在 |
| 7 | **接口编号** | ✅ | `IF-001` / `IF-001;IF-002` / `-` | 该需求涉及的接口编号（见 `02-接口需求规格说明.md`）。**确无接口交互的填 `-`**（不允许留空） |
| 8 | **实现代码位置** | ✅ | `src/m20_auth/service.py:45` | 文件路径 + 起始行号。多处置用分号分隔。**未实现时填 `<TBD-01>`** |
| 9 | **单元测试用例** | ⚠️ | `TC-001` | 覆盖该需求的单元测试用例编号。纯非功能需求（如整体性能）可填 `-`，但必须在备注说明由哪一级测试覆盖 |
| 10 | **集成测试用例** | ⚠️ | `TC-101` | 集成测试用例编号。可不适用时填 `-` |
| 11 | **系统测试用例** | ✅ | `TC-201` | 系统级用例编号。**每条需求至少要有单元/集成/系统三级中的一级非 `-`**，否则视为未覆盖 |
| 12 | **验收测试用例** | ✅ | `TC-301` | 验收用例编号（对应 GB/T 25000.51-2016 质量特性）。**P0 需求必须有验收用例** |
| 13 | **状态** | ✅ | 见 §2.1 枚举 | 该需求的实现/验证进展 |
| 14 | **备注** | ❌ | 自由文本 | 说明 TBD、例外、依赖、已知偏差等。**例外必须在此留痕**，不接受口头例外 |

> ⚠️ **多值列（第 5/6/7/8 列）用分号 `;` 分隔，不要用裸逗号。** 裸逗号会被 CSV 解析器当作列分隔符，
> 导致该行**整体右移一列**且默认模式下可能不报错。详见 §六 第 2 条。

#### 2.0.1 ⚠️ 测试用例编号格式（硬约束）

四列测试用例编号**必须**匹配 `TC-` + 3 位数字，即正则 `TC-\d{3}`。这是 `tools/trace_matrix.py` 的校验规则，
格式不符会被判为 **ERROR（门禁不通过）**。

本仓库约定用**百位数字编码测试级别**，使编号本身即可读：

| 编号区间 | 测试级别 | 示例 | 依据 |
|---|---|---|---|
| `TC-0xx` | 单元测试 | `TC-001` | GB/T 38634.2-2020 测试级别：组件测试 |
| `TC-1xx` | 集成测试 | `TC-101` | 集成测试 |
| `TC-2xx` | 系统测试 | `TC-201` | 系统测试（含性能、安全等非功能） |
| `TC-3xx` | 验收测试 | `TC-301` | 验收测试（映射 GB/T 25000.51-2016 质量特性） |

**同一条需求的四级用例建议使用同一序号**，形成垂直追溯（如 `REQ-F-001` → `TC-001` / `TC-101` / `TC-201` / `TC-301`），
这样从任一用例编号就能直接反推出它验证的需求。

> 用例编号是**全局唯一**的（不按模块分号段）；用例与模块的关联通过本表的「设计模块号」列表达。
> 编号一经分配**永不复用**。

### 2.1 「状态」列取值枚举

| 取值 | 含义 | 允许出现在哪个阶段 | `--strict` 严格模式 |
|---|---|---|---|
| `待设计` | 需求已基线，尚未落到设计模块 | S1 → S2 | ❌ 不通过 |
| `设计中` | 已分配模块号，设计文档在写 | S2 → S3 | ❌ 不通过 |
| `已实现` | 代码已提交，单元测试通过 | S4 起 | ✅ 通过 |
| `已测试` | 集成/系统测试已执行并留存记录 | S5 起 | ✅ 通过 |
| `已验收` | 验收测试通过 | S6 起 | ✅ 通过 |
| `已废弃` | 需求作废（编号不回收） | 任意 | ❌ 不通过 |

> **严格模式（`--strict`）** 用于 S6 验收 / S7 发布门禁：此时状态必须是 `已实现` / `已测试` / `已验收` 三者之一，
> 否则门禁不通过。日常开发阶段不加 `--strict`。

### 2.2 填写约定（保证 CSV 可被机器解析）

| 约定 | 规则 | 原因 |
|---|---|---|
| 编码 | **UTF-8（无 BOM）** | 保持列名逐字节可比对；`tools/trace_matrix.py` 以 `utf-8-sig` 读取，**有无 BOM 均可**。Excel 打开方式见 §五 |
| 分隔符 | 英文半角逗号 `,` | Excel 直接识别 |
| 多值分隔 | 分号 `;`（**本项目约定**，不要用逗号） | 避免字段被引号包裹，保持文件可 diff、可人工编辑。工具按 `[,，;；、]+` 容错拆分，但**约定用分号** |
| 引号 | 尽量避免；确需包含逗号时用双引号包裹整个字段 | 同上 |
| 表头 | **必须位于第 1 行**，不得有空行、注释行、标题行 | 工具按首行解析列名 |
| 行序 | 按需求编号升序 | 便于 diff |
| 换行 | 每个需求一行，**不得一行多需求** | 同上 |
| 用例编号 | **必须匹配 `TC-\d{3}`** | 格式不符直接判 ERROR（见 §2.0.1） |

## 三、双向追溯要求

### 3.1 正向追溯：需求 → 设计 → 代码 → 测试

**每一列都必须能在下游找到实体。** 任何一环断链，都意味着"这条需求没被实现或没被验证"。

```
REQ-F-001 ──┬─→ 设计模块号 M20 ──────→ 设计文档章节 HLD §3.3 / LLD §3.2
            ├─→ 接口编号 IF-001 ─────→ 接口需求规格说明 §3.2.1
            ├─→ 实现代码位置 src/m20_auth/service.py:45
            └─→ 测试用例 TC-001 / TC-101 / TC-201 / TC-301
```

**正向门禁规则（`tools/trace_matrix.py` 校验）**

| 编号 | 规则 | 不满足的后果 |
|---|---|---|
| F-1 | 第 1–8 列**均非空**（「设计文档章节」为空仅告警） | 失败：需求未落到设计或代码 |
| F-2 | 每条第 9–12 列（四个测试用例列）中**至少一列有有效用例** | 失败：需求无任何测试覆盖（报错文案即"写不出测试用例的需求 = 不合格需求"） |
| F-3 | 每条用例编号必须匹配 `TC-\d{3}` | 失败：用例编号格式非法 |
| F-4 | 「设计模块号」中的每个 `Mxx` 必须匹配 `M\d{2}`，且存在于**模块登记表**或 `skeleton/modules.py` | 失败：引用了未登记的模块 |
| F-5 | SRS 中出现的每条需求编号，必须在 CSV 中**有且仅有一行** | 失败：漏登记或重复登记 |
| F-6 | 「系统测试用例」与「验收测试用例」两列**同时为空** | **告警**（非失败）：需求缺少系统级/验收级覆盖 |
| F-7 | 需求编号必须匹配 `REQ-[FN]-\d{3}`；优先级必须为 `P0`/`P1`/`P2` | 失败：编号或优先级非法 |

### 3.2 反向追溯：测试 → 需求

**从任何一个测试用例出发，必须能回答"它在验证哪条需求"。**

```
TC-301 ──→ REQ-F-001 ──→ 用户登录 ──→ M20 ──→ src/m20_auth/service.py:45
```

**反向门禁规则**

| 编号 | 规则 | 不满足的后果 |
|---|---|---|
| R-1 | 测试报告中出现的每个用例编号，必须能在 CSV 的对应列中找到 | 失败：存在"无需求来源"的用例（可能是镀金测试或遗漏登记） |
| R-2 | 测试未通过的用例，其需求行的「状态」不得为 `已验收` | 失败：状态与事实不符 |
| R-3 | 需求变更为 `已废弃` 时，引用了它的测试用例必须同步处置（删除或改指向），并在备注留痕 | 失败：悬空引用 |

> **反向追溯的真正价值**：它逼你回答"这个测试到底在防什么风险"。
> 答不上来的用例应当删除 —— **无来源的测试是维护成本，不是质量保障。**

### 3.3 双向一致性检查（每次基线前必做）

| 检查 | 方法 | 通过判据 |
|---|---|---|
| 无孤儿需求 | SRS 需求编号集合 − CSV 需求编号集合 | 空集 |
| 无孤儿用例 | 测试用例编号集合 − CSV 中出现的用例编号集合 | 空集 |
| 无孤儿模块 | CSV 模块号集合 − 模块登记表模块号集合 | 空集 |
| 无 TBD 残留 | 检索 `<TBD-01>` | 基线时 0；日常允许但须有责任人与关闭日期 |

## 四、门禁工具如何使用本文件

**工具路径**：`tools/trace_matrix.py`（CI 中通过 `.github/workflows/gate.yml` 的 `traceability` 作业自动执行）

```powershell
# 1) 默认用法：校验仓库自带的示例数据（docs/阶段外-待启用/_非本项目样例/）
python tools/trace_matrix.py

# 2) 校验本模板（不校验 SRS 一致性）
python tools/trace_matrix.py --matrix "templates/02-需求类/03-需求追溯矩阵.csv" --srs no-such-srs.md

# 3) 项目落地后的标准用法（同时校验 RTM 与 SRS 一致）
python tools/trace_matrix.py --matrix docs/rtm/需求追溯矩阵.csv --srs docs/rtm/软件需求规格说明.md

# 4) 严格模式：S6 验收 / S7 发布门禁（状态必须是 已实现/已测试/已验收）
python tools/trace_matrix.py --matrix docs/rtm/需求追溯矩阵.csv --srs docs/rtm/软件需求规格说明.md --strict
```

> 退出码：`0` = 门禁通过；`1` = 未通过。

**读取约定（本仓库门禁工具的实际行为）**

| 项 | 约定 |
|---|---|
| 文件路径 | 默认 `docs/阶段外-待启用/_非本项目样例/需求追溯矩阵.csv`；项目落地后由 `--matrix` 指定（建议 `docs/rtm/需求追溯矩阵.csv`） |
| 编码 | `utf-8-sig`——**有 BOM / 无 BOM 都能正确读取** |
| 表头 | 第 1 行为表头，**列名与本说明 §二 的 14 个列名逐字符一致**；缺列直接报 ERROR 并**立即返回**（退出码 1），不静默跳过 |
| 多值列 | 按 `[,，;；、]+` 拆分并去空格（本项目约定写分号 `;`） |
| 空值占位 | `-` 表示"不适用"；空字符串表示"未填"。工具只把**空单元格**计入"无覆盖"，`-` 也被视为空 |
| 用例编号 | 必须匹配 `TC-\d{3}`，否则 ERROR |
| 模块号 | 必须匹配 `M\d{2}`，且能在**模块登记表**（`templates/03-设计类/02-模块清单与模块号登记表.md`）或 `skeleton/modules.py` 中找到 |
| 用例列过滤 | 用例单元格中形如路径的内容（含 `/`、`\` 或 `::`）会被忽略，不计入用例编号 |
| 失败输出 | 逐行输出「需求编号 + 第 N 行 + 具体原因」，便于直接定位 |
| 严格模式 | `--strict` 时「状态」必须为 `已实现` / `已测试` / `已验收` |

> ⚠️ **改列名 = 改契约。** 14 个列名是与门禁工具之间的接口，任何改名都必须同步修改
> `tools/trace_matrix.py` 的 `REQUIRED_COLUMNS` 与 CI 配置，否则门禁会全线失败。
>
> ✅ **验证记录**：本模板的示例数据已通过实际门禁校验——
> `python tools/trace_matrix.py --matrix "templates/02-需求类/03-需求追溯矩阵.csv" --srs no-such-srs.md --strict`
> 返回**退出码 0（门禁结论：通过）**，0 错误 0 告警。

## 五、如何用 Excel 打开与维护

本 CSV 为 **UTF-8 无 BOM** 编码（门禁工具以 `utf-8-sig` 读取，故无 BOM 亦完全兼容）。

| 方式 | 步骤 | 适用 |
|---|---|---|
| **推荐：数据导入** | Excel → 数据 → 获取数据 → 从文本/CSV → 选文件 → **文件原始格式选 `65001: Unicode (UTF-8)`** → 加载 | 中文显示正常，不产生乱码 |
| **双击打开** | 直接双击文件 | 部分 Excel 版本会把中文显示为乱码。此时**不要保存**，改用上面的导入方式 |
| **另存为带 BOM** | 导入后另存为「CSV UTF-8（逗号分隔）」 | ✅ 安全：门禁工具用 `utf-8-sig` 读取，**加 BOM 不会破坏列名比对**，可放心用此方式保存 |
| **纯文本编辑** | VS Code / Notepad++ 直接编辑 | 推荐用于日常维护与代码评审（可 diff） |

**维护纪律**

1. **RTM 与 SRS 同一次提交里更新**（文档与代码不得漂移，是本仓库硬性要求）。
2. **每次需求基线化、每次框架变更（R5）、每次测试准出（R6）前**，必须执行一次完整的双向一致性检查。
3. **不得为了"让门禁过"而填假数据。** 若某条需求确实暂无测试，正确做法是填 `-` 并在备注写明责任人与计划，而不是编一个用例编号。
4. 需求废弃时**删除该行或置状态为 `已废弃`**，但**编号永不复用**。

## 六、填写指引

1. **最常见错误：`需求基线版本` 留空或写成"最新"。** 必须是可解析的基线标签（如 `req-baseline/v1.0`），否则无法判断这行对应哪一次基线，追溯链在变更后就断了。
2. **最常见错误：多值用裸逗号分隔（`M20,M40`）且不加引号。** 这是**最隐蔽、后果最严重**的填写错误：裸逗号会被 CSV 解析器当作列分隔符，导致**该行整体右移一列**——
   `设计模块号` 只剩第一个、`状态` 读到用例编号、真实状态被挤进备注。
   更危险的是：默认模式下门禁可能**误报"通过"**（列非空即不报错），直到 S6 用 `--strict` 才暴露为"状态未达到可交付状态"，此时排查成本极高。
   **正确做法**：多值一律用分号 `M20;M40`（无需引号，手工编辑也不会错位）；确要用逗号则必须给整个字段加双引号 `"M20,M40"`。
3. **最常见错误：测试用例编号自创格式（`UT-M20-003`、`IT-004`、`PERF-003` …）。** 门禁只认 `TC-\d{3}`，自创格式一律判 ERROR。请按 §2.0.1 的百位级别编码：`TC-0xx` 单元 / `TC-1xx` 集成 / `TC-2xx` 系统 / `TC-3xx` 验收。
4. **最常见错误：把不适用留空。** 不适用要填 `-`（表示"确认过，确实不需要"），留空表示"忘了填"。
5. **最常见错误：只做正向、不做反向。** 测试写完不回填 RTM，导致"代码有、矩阵无"，门禁一跑就红。**测试用例编号一确定就回填，不要攒到最后。**
6. **最常见错误：改了列名去"优化"表格。** 14 个列名是与 `tools/trace_matrix.py` 的接口契约，改名必须同步改工具与 CI；且**改了列名 `tools/trace_matrix.py` 会直接报"追溯矩阵缺少必需列"并退出**。

> **补充**：`<TBD-01>` 临时占位长期挂着也是常见问题——基线化时若仍存在，R1 需求评审不得通过。
> **提交前自检**：`python tools/trace_matrix.py --matrix <你的 CSV> --srs <你的 SRS> --strict`，退出码必须为 0。

- **可执行性验证**：本模板示例数据已由仓库门禁工具实测通过（`python tools/trace_matrix.py --matrix "templates/02-需求类/03-需求追溯矩阵.csv" ... --strict` → 退出码 0）。
