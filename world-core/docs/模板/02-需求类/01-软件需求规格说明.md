## 3 需求可验证化改写【本仓库定制章节】

> 本章是 GB/T 9385-2008 骨架之外的**工程强化项**，但它是本仓库的**硬要求**：
> S1 阶段必须把第 2 章里的"愿望式表述"逐条改写为可度量、可判定的表述，改写结果进入 §4。

### 3.1 反例 → 正例 对照表（必须逐条检查）

| ❌ 不可验证（禁止进入 SRS） | ✅ 可验证（改写后） | 判定方式 |
|---|---|---|
| 界面要美观 | 主流程操作步数 ≤ 5 步；关键操作响应 ≤ 200ms（P95） | 操作步数人工计数；响应时间由性能用例 `TC-210` 度量 |
| 系统要稳定 | 连续运行 72h 无未处理异常；MTBF ≥ 200h；P0 缺陷为 0 | 长稳用例 `TC-204`；缺陷清单统计 |
| 支持大数据量 | 单表 1000 万行下，列表查询响应 ≤ 2s（P95）；批量导入 10 万行 ≤ 5min | 性能用例 `TC-203`，指定数据集与统计口径 |
| 要安全 | 通过 OWASP Top 10 检查；口令存储 bcrypt(cost ≥ 10)；越权访问用例 100% 拦截 | 安全用例 `TC-230` + 扫描报告 |

### 3.2 改写硬规则

1. **可判定**：需求必须能给出"通过 / 不通过"的客观判定，不得依赖主观评价（"美观""友好""流畅"）。
2. **有指标**：凡涉及性能、容量、可靠性、安全的需求，必须给出**数值 + 统计口径 + 度量条件**（数据集规模、并发数、环境配置）。
3. **有边界**：必须说明异常路径与边界条件（空值、超限、超时、并发冲突、权限不足）。
4. **可追溯**：每条需求必须能指向至少一条测试用例编号（`TC-\d{3}` 格式），并回填到需求追溯矩阵（见 §4 卡片的「关联测试用例」字段）。
5. **⭐ 总规则**：**任何写进 SRS 的需求，都必须能推导出至少一条测试用例。写不出测试用例的需求 = 不合格需求，不得基线化。**

> **R1 需求评审的判定口径**：评审时逐条问"这条需求，测试怎么判它过了？"
> 答不上来的需求，一律退回改写，不接受"先基线化、后面再细化"。

### 3.4 需求质量判据【国标：GB/T 45802-2025】

> **本章是 R1 需求评审的判定依据**，且是**国标明文要求**，不是本仓库自创。
> 出处：**GB/T 45802-2025**（≡ ISO/IEC/IEEE 29148:2018）。
> 条款号来自 OCR 提取件，**作为合同/验收依据前请回原 PDF 核对**。

### 3.4.1 单项需求的特性（§5.2.5，9 条）

逐条检查**每一条**需求。任一条不满足 → 该需求退回改写。

| # | 特性 | 判定问题 | 不合格的样子 |
|---|---|---|---|
| 1 | **必要的** Necessary | 删掉它，系统能力会缺失吗？ | 冗余需求、"顺手加上"的功能 |
| 2 | **合适的** Appropriate | 它属于本系统的职责范围吗？ | 把上游系统的职责写进本 SRS |
| 3 | **明确的** Unambiguous | 两个人读会得出同一种理解吗？ | "尽量快""合理提示" |
| 4 | **完整的** Complete | 它自身的信息够实现与测试吗？ | 只写功能不写异常与边界 |
| 5 | **单一的** Singular | 它只表达一件事吗？ | 一句话里塞了"且""或者""同时" |
| 6 | **可行的** Feasible | 在当前约束（技术/成本/进度）下做得到吗？ | 无依据的性能指标 |
| 7 | **可验证的** Verifiable | 能给出"通过/不通过"的客观判定吗？ | "界面美观" |
| 8 | **正确的** Correct | 它准确反映真实需要吗？ | 与业务规则不符 |
| 9 | **符合性的** Conforming | 符合约定模板、编号与属性要求吗？ | 编号跳号、缺验收准则 |

> **第 5 条最容易被忽略**：一条需求里用"并且""同时"连接两个可独立验收的行为，就是两条需求，应拆开。
> 拆开的价值：**测试失败时能定位到具体哪一件事没做到。**

### 3.4.2 需求集的特性（§5.2.6，5 条 + TBx 禁令）

检查**整份 SRS**（而非单条）：

| # | 特性 | 判定问题 |
|---|---|---|
| 1 | **完整的** Complete | 所有必要需求都在？没有"后面再补"的空白？ |
| 2 | **一致的** Consistent | 任意两条需求之间无冲突、无重复？ |
| 3 | **可行的** Feasible | 整集在给定约束下可实现？ |
| 4 | **可理解的** Comprehensible | 目标读者能读懂？（客户、开发、测试三类读者） |
| 5 | **可确认的** Able to be validated | 能通过确认活动判定它满足利益相关方需要？ |

#### ⚠️ TBx 禁令（§5.2.6 明文要求）

**需求集不应包含"待决定"（TBD / TBR / TBS / TBW）类条款。**

| 缩写 | 含义 |
|---|---|
| **TBD** | To Be Determined 待决定 |
| **TBR** | To Be Reviewed 待评审 |
| **TBS** | To Be Specified 待规定 |
| **TBW** | To Be Written 待编写 |

**本仓库口径**：TBx **允许短期存在**（否则前期无法推进），但必须满足三条，否则**不得基线化**：

1. 登记在**附录 A**（不得散落在 §4 需求卡片里）
2. 每条有**责任人**与**计划关闭日期**
3. **基线化前清零**——基线里不允许留 TBx

> 这与 §3.2 第 5 条是同一条红线的两面：
> **写不出测试用例的需求 = 不合格需求；留 TBD 的需求 = 尚未成为需求。**

### 3.4.3 评审怎么用这张表

**R1 需求评审时逐条过**：

```
对每条需求：
  ① 跑 §3.4.1 的 9 条 → 全 ✅ 才进入 ②
  ② 问"测试怎么判它过了？" → 答不上来 → 退回
  ③ 都过了 → 标 P0/P1/P2 优先级，登记到 RTM

对整份 SRS：
  ④ 跑 §3.4.2 的 5 条 → 全 ✅
  ⑤ 检查 TBx → 非空则不得基线化
```

**不接受**"先基线化、后面再细化"——那等于把不合格需求冻结进基线。

**`<REQ-F-001>` 用户登录**

| 字段 | 内容 |
|---|---|
| **需求编号** | `<REQ-F-001>` |
| **名称** | 用户登录（账号口令认证） |
| **优先级** | P0 |
| **来源** | 合同附件一 §3.1；用户访谈记录 `<YYYY-MM-DD>`-02 |
| **描述** | 系统应支持已注册用户以"账号 + 口令"方式登录；认证成功后建立会话并跳转至其默认首页。同一账号连续 5 次认证失败，锁定 15 分钟。 |
| **关联设计模块** | `<M20>`（业务层-认证服务）；依赖 `<M60>`（基础设施-统一认证适配） |
| **关联接口** | `<IF-001>`（统一认证登录，同步 / HTTPS / JSON） |
| **关联测试用例** | `TC-001`（认证成功/失败）、`TC-002`（锁定策略）、`TC-101`、`TC-201`、`TC-301` |

**输入 / 处理 / 输出**

| 项 | 内容 |
|---|---|
| **输入** | `account`：字符串，6–32 位，字母数字下划线；`password`：字符串，8–64 位；来源：登录页表单（POST `/api/v1/auth/login`） |
| **处理** | ① 校验入参格式，不合法直接返回 400；② 查询 `<M40>` 获取用户记录，取 `password_hash`；③ 以 bcrypt(cost≥10) 校验口令；④ 失败则 `fail_count += 1`，达 5 次写锁定标记（TTL 15min）；⑤ 成功则清零 `fail_count`，生成会话令牌（有效期 2h，滑动续期） |
| **输出** | 成功：`200` + `{token, expires_in, user:{id, name, roles[]}}`；失败：`401` + 错误码；锁定：`423` |

**异常与边界**

| 场景 | 期望行为 |
|---|---|
| 账号不存在 | 返回 `401` 且错误码与"口令错误"**一致**（不泄露账号存在性） |
| 口令为空 / 超长（> 64） | 返回 `400`，不写入失败计数 |
| 连续失败第 5 次 | 第 5 次即锁定，返回 `423`，并记录审计日志 |
| 锁定期间再次尝试 | 返回 `423`，附带 `retry_after` 秒数 |
| 认证服务（`<IF-001>`）超时（> 3s） | 重试 1 次（幂等：仅查询不写状态）；仍失败返回 `503`，不锁定账号 |
| 并发登录同一账号 | 允许，会话互不影响；锁定计数以原子操作累加 |
| 数据库不可用 | 返回 `503`，记录 ERROR 日志，不返回 500 堆栈 |

**验收准则（可测）**

| 编号 | 准则（Given / When / Then） | 对应用例 |
|---|---|---|
| AC-01 | Given 已注册用户，When 提交正确账号口令，Then 200 且返回有效 token | `TC-001` |
| AC-02 | Given 已注册用户，When 提交错误口令，Then 401 且响应体不含账号是否存在的信息 | `TC-001` |
| AC-03 | Given 已连续失败 4 次，When 第 5 次失败，Then 423 且在 15 分钟内正确口令也被拒绝 | `TC-002` |
| AC-04 | Given 认证服务不可用，When 登录，Then 503 且账号失败计数不变 | `TC-101` |
| AC-05 | Given 任意一次登录请求，When 记录日志，Then 日志中口令字段为掩码且不可还原 | `TC-201` |

## 7 填写指引

1. **别把 SRS 写成需求收集箱。** SRS 是**基线**，不是"想到什么先记下来"。未确认的信息放进附录 A 的 TBD，不要混进 §4 的需求卡片里充当正式需求。
2. **最常见错误：需求写成愿望。** "美观""稳定""友好""高效""尽量""等"这类词全文检索必须为 0。每一句都要能回答"测试怎么判它过了？"（见 §3）。
3. **最常见错误：只写成功路径。** 每条需求卡片的「异常与边界」至少要覆盖空值、超限、超时、并发、权限不足、外部依赖失败六类中的相关项。只写 happy path 的需求，到 S5 会集中爆炸。
4. **最常见错误：非功能需求不量化。** "响应要快"不合格；"P95 ≤ 2s，在 1000 万行 / 50 并发下度量"才合格。**没有度量条件的性能指标等于没有指标。**
5. **最常见错误：编号跳号或复用。** 需求编号一经分配**永不复用**（删除后序号作废），否则历史追溯与 RTM 会指向错误的条目。
6. **最常见错误：改了 SRS 不改 RTM。** 需求基线的任何变更，必须同步更新 `03-需求追溯矩阵.csv`，否则 CI 门禁 `tools/trace_matrix.py` 会失败，且追溯链断裂。
