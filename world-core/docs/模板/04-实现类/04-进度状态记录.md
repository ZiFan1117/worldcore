# 进度状态记录（PSR）

> **文档编号**：`<项目代号>-PSR-<三位序号>-V<主版本>.<次版本>`，示例 `<项目代号>-PSR-001-V1.0`
> **类别码**：`PSR`（Progress Status Record）
> **适用阶段**：**S0 立项后持续记录，S1–S7 全程**。频率见 §1.2。
> **依据**：**ISO/IEC 29110-5-1-2** 的 **PM.2 项目计划执行** 与 **PM.3 项目评估与控制**——
> 这两项要求"对照计划检查实际进展、识别偏差、采取纠正措施并留下记录"。
> `GB/T 8567-2006` 有「**开发进度月报**」这一文档种类，本文档是其落地形态。
> 过程依据 `GB/T 8566-2022` 的项目管理相关过程。
> **文档状态**：模板（Template）· 未基线化 · 禁止未填写直接作为交付物提交
>
> ⚠️ **本仓库补充说明**：ISO/IEC 29110 **中国未采标**，不能作为"符合国家标准"的依据。
> 此处引用它是因为它是**唯一为小组织明确定义"项目监控"活动**的标准，
> 而这一环恰是本仓库原有流程最明显的空缺（S0 定了计划，S1–S7 无任何对照检查动作）。
> 对外文件引用时，请引 `GB/T 8567-2006`（开发进度月报）+ `GB/T 8566-2022`（项目管理过程）。

## 1. 记录说明

### 1.1 这份记录解决什么问题

**计划定完就没人看了**——这是流程里最常见的空洞。

| 没有 PSR 时 | 有 PSR 时 |
|---|---|
| 计划是 S0 的一次性产物 | 计划每期被对照一次 |
| 进度靠记忆，偏差靠感觉 | 偏差可量化、可追溯 |
| 问题暴露在交付前夜 | 问题暴露在当期 |
| 纠正措施无人跟踪 | 纠正措施有责任人、有截止日、有闭环状态 |

> **一句话**：PSR 是**计划的对照面**。没有它，S0 的项目开发计划就只是一份存档。

### 1.2 记录频率（在项目开发计划里声明）

| 项目周期 | 建议频率 |
|---|---|
| < 1 个月 | 每周 1 次 |
| 1–6 个月 | 每两周 1 次 |
| > 6 个月 | 每月 1 次，里程碑处加记 1 次 |

**A 档**：可用 `git log` + 一段简短自述替代正式表单，但**必须留痕**（见 §4）。
**B 档**：按期填写本表，作为阶段评审的输入。

**偏差判定口径**（避免"感觉还行"）：

| 判定 | 标准 |
|---|---|
| **按期** | 完成时间在计划日 ±2 个工作日内 |
| **轻微延期** | 延期 3–5 个工作日 |
| **严重延期** | 延期 > 5 个工作日，**必须触发纠正措施**（见 §5） |
| **提前** | 完成时间早于计划日 2 个工作日以上 |

**填写规则**：

| 规则 | 说明 |
|---|---|
| **问题必须具体** | ❌ "进度紧张" → ✅ "模块 M23 详细设计延期 3 天，因接口契约未定" |
| **措施必须可验证** | ❌ "加强沟通" → ✅ "本周五前与 X 确认 M23 接口，输出契约 v0.2" |

| **上期未关闭项必须带入本期** | 不允许"上期问题本期消失" |

## 11. 本模板的边界

| 项 | 说明 |
|---|---|
| **性质** | **【本仓库·强化项】**——`GB/T 8567-2006` 有「开发进度月报」种类，但**未规定此详细程度** |
| **可裁剪** | 可简化（A 档只填 3 项指标 + 偏差），但**不可取消**——取消即等于放弃项目监控 |
| **裁剪留痕** | 在 `01-策划类/02-项目开发计划.md` 的「裁剪说明」里写明简化范围 |
| **不得作为** | 不得替代**阶段评审记录**（两者是不同文档：一个记进展，一个记决策） |

> **实施时请以标准正文为准。** 本模板是结构骨架，不复制标准正文。
