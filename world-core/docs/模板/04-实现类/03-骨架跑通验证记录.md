## 1 目的与定位

### 1.1 为什么要单独做「骨架跑通」

> **骨架跑通评审（R3）的目的，是用最低成本暴露框架的结构性错误。**
>
> 此时代码量最小、依赖最少、推翻框架的代价最低。装配方式错了、模块边界切错了、
> 依赖成环了、构建脚本缺了——这些问题在 S3 被发现，改的是**框架**；
> 拖到 S5 集成时才被发现，改的是**框架 + 所有已建立在该框架假设之上的模块 + 全部相关测试**。
> 两者的修复成本不在一个量级。

| 对照项 | S3 骨架跑通时发现 | S5 集成测试时发现 |
|---|---|---|
| 已实现模块数 | 0（全部为桩/Mock） | 全部 |
| 需重写的代码 | 框架装配代码 | 框架 + 各模块适配代码 |
| 需重跑的设计文档 | HLD、模块清单、契约 | 同上 + 各模块详细设计 |
| 对进度的影响 | 天级 | 周级 |
| 对团队信心的影响 | 低（本来就是骨架） | 高（"都快做完了才发现"） |

### 1.2 本记录要证明什么

|---|---|---|

## 4 模块装配清单核对（**核心证据**）

### 4.1 装配方式说明

| 装配方式 | 含义 | 本阶段是否允许 |
|---|---|---|
| **桩（Stub）** | 返回固定值的占位实现，用于打通装配 | ✅ **S3 的标准方式** |
| **Mock** | 可编程的假实现，可断言调用行为 | ✅ 允许 |
| **真实实现** | 已完成业务逻辑的模块 | ⚠️ S3 阶段应尽量少；若已有（如公共工具模块），须标注 |
| **未装配** | 未接入框架 | ❌ **不允许**——缺失装配即为 R3 不通过 |

### 4.2 模块装配核对表

> **逐一核对，不得抽样。** 每个模块号都必须出现，与模块清单登记表一一对应。

| 模块号 | 模块名称 | 对应需求 | 装配方式 | 注册结果 | 契约加载 | 依赖声明 | 判定 | 备注 |
|---|---|---|---|---|---|---|---|---|
| `<M01>` | `<模块名称>` | `<REQ-F-001>` | 桩 / Mock / 真实 | ☐ 成功 ☐ 失败 | ☐ 成功 | `<依赖模块号或"无">` | ☐ | |
| `<M02>` | `<模块名称>` | `<REQ-F-005>` | 桩 | ☐ 成功 ☐ 失败 | ☐ 成功 | `<M01>` | ☐ | |
| `<M03>` | `<模块名称>` | `<REQ-N-004>` | 桩 | ☐ 成功 ☐ 失败 | ☐ 成功 | `<M01>, <M02>` | ☐ | |
| `<Mnn>` | `<模块名称>` | `<需求>` | `<方式>` | ☐ | ☐ | `<依赖>` | ☐ | |

### 4.3 装配一致性核对

| 核对项 | 要求 | 实际 | 判定 |
|---|---|---|---|
| 模块清单中登记模块数 | `<n>` | — | — |
| 实际注册成功模块数 | `<n>`（必须等于登记数） | `<n>` | ☐ |
| 未装配模块数 | **0** | `<n>` | ☐ |
| 模块号命名合规 | 符合 `M` + 2 位规则 | ☐ | ☐ |
| 模块号无重复 | 登记表与实际一致 | ☐ | ☐ |
| 模块职责与契约一致 | 每模块有明确对外契约 | ☐ | ☐ |
| 桩实现未混入业务逻辑 | 桩只做占位，不承载真实规则 | ☐ | ☐ |

> **常见陷阱**：桩实现里"顺手"写了点业务逻辑（"反正是个默认值"）。
> 这会让骨架跑通产生**虚假信心**——真实的模块接入后行为不一致，S4 才发现。
> 桩只返回固定值或约定的假数据，**不实现任何业务规则**。

### 5.1 依赖拓扑记录

> **模块间循环依赖是框架级结构缺陷**，必须在 S3 消灭。
> 它在单模块开发时毫无症状，在集成时表现为初始化顺序无法确定、测试无法独立运行。

### 5.2 环检测核对

| 检查项 | 方法 | 结果 | 判定 |
|---|---|---|---|
| 全图环检测 | `<拓扑排序 / DFS 检测 / 工具>` | ☐ 无环 ☐ 存在环 | ☐ |
| 跨层依赖合规 | 上层可依赖下层，下层不得反向依赖上层 | ☐ 合规 | ☐ |

## 11 填写指引（常见错误）

1. **只填"跑通了"，不贴原始输出**——第 3.2 节必须粘贴**完整原始输出**。摘录关键几行无法证明"没有隐藏的异常与错误日志"，评审时不予采信。
2. **用多条命令或手工前置步骤凑出"跑通"**——先装依赖、再改配置、再建目录、最后跑主命令，这不叫一条命令跑通。所有前置步骤必须收敛进脚本，否则 CI 无法可靠复现。
3. **模块装配表抽样填写**——必须**逐一核对全部模块号**，并与模块清单登记表对齐。漏填的模块按"未装配"处理，直接导致 R3 不通过。
4. **桩实现里写了业务逻辑**——桩只返回固定值或约定假数据。桩里塞业务规则会让骨架跑通产生虚假信心，真实模块接入后行为不一致，问题被推迟到 S4/S5 才暴露。
5. **本地跑通即认定通过，不验 CI**——本地环境常有未提交改动与手工安装的依赖。"CI 跑不过"必须查明并修复或解释，不得以"CI 环境问题"跳过。
6. **发现循环依赖后带着问题通过**——未消除的环是**框架级结构缺陷**，必须提 R5 框架变更（FC-1/FC-2）回到 S2 调整划分后重新验证，不得在 R3 结论中标注"后续处理"而放行。
