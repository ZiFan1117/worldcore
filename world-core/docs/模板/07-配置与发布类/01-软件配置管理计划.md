# 软件配置管理计划

> **文档编号规则**：`<项目名称>-<文档类型码>-<三位流水号>-v<主版本>.<次版本>`，本文件类型码为 `SCMP`，
> 示例 `<项目代号>-SCMP-001-v1.0`；编号一经分配永不复用，版本号随文档修订递增。
> 文档类型码：`FSR` 可行性研究报告 / `SDP` 项目开发计划 / `SQAP` 软件质量保证计划 / `SCMP` 软件配置管理计划。
> **适用阶段**：**S0 立项与策划**；准出门禁为 **R0 立项评审**；本计划的活动贯穿 S0–S7，并在每一次
> 基线建立、版本发布与阶段门禁处被核查。
> **依据标准**：**GB/T 8567-2006**《计算机软件文档编制规范》（软件配置管理计划）；概念要素参照
> **GB/T 12505-90**《计算机软件配置管理计划规范》（1990 年老标准，**仅采其五要素框架**）；向上对齐
> **GB/T 8566-2022**《系统与软件工程 软件生存周期过程》的配置管理过程。
> **状态**：**模板（未填写）**。本计划经批准后即生效，是"配置管理与版本化"这一不可裁剪红线的落地载体。
>
> **关于 GB/T 12505-90 的立场**：该标准发布于 1990 年，其**五要素框架**
> （配置项标识、变更控制、状态记录、配置审计、基线管理）今天依然成立；
> 但其实现方式描述已过时——没有持续集成、没有制品仓库、没有分布式版本控制的概念。
> 本仓库**只采其五要素框架**，实现方式按现代工程实践落地：**Git 版本控制 + CI 流水线 + 制品版本化**，
> 并向上对齐 GB/T 8566-2022 的配置管理过程。
> **一句话原则：没有纳入版本控制的东西，等于不存在；没有基线的迭代，等于失控。**

## 二、配置管理五要素总览

> 五要素来自 GB/T 12505-90 的框架；"本仓库实现方式"一列是本仓库的落地要求，
> 二者是**框架与实现**的关系，不是替代关系。

| 要素 | 目标 | 本仓库实现方式（现代实践） | 对应章节 | 核查门禁 |
|---|---|---|---|---|
| **① 配置项标识** | 每个受控实体唯一可识别、可定位、可追责 | 统一编号规则 + 仓库路径唯一权威 + Git 版本控制 | 第四章 | R0、每阶段审计 |
| **② 变更控制** | 任何变更都在授权后发生，且可追溯 | 七步流程 + 变更分级审批 + PR 评审 + CI 门禁 | 第七章 | R4、R5、R8 |
| **③ 状态记录** | 随时能回答"当前是什么版本、有哪些未闭环变更" | 版本控制历史 + 缺陷/变更系统 + 状态报告 | 第八章 | R6、R8 |
| **④ 配置审计** | 验证"交付物 = 基线"与"基线 = 需求" | FCA/PCA 检查单 + CI 自动校验 + 人工审计 | 第九章 | R6、R7、S7 |
| **⑤ 基线管理** | 在正确的时点冻结正确的集合，形成可回退的锚点 | 语义化标签：`req-baseline/*`、`framework/*`、`product/*` | 第五章 | R1、R2、R6、R7 |

> **注意**：GB/T 12505-90 把"基线"分散在标识与控制两节中描述；本仓库将其提升为独立要素（第五章），
> 因为"什么时候该冻结、冻结了哪些东西"是迭代项目最容易失控的点。

## 三、配置管理组织和职责

### 3.1 组织

| 项 | 内容 |
|---|---|
| 配置管理归口 | 配置管理员 `<姓名>`，向项目负责人报告 |
| 独立性要求 | 配置审计的执行人**不得**是本次被审计配置项的作者；质量负责人参与并复核审计结论 |
| 决策机构 | 配置控制委员会（CCB）：项目负责人、技术负责人、质量负责人、配置管理员、测试代表 |
| CCB 议事规则 | 变更批准按 7.2 的审批权限执行；涉及需求范围的变更必须通知甲方/产品 |
| 生效范围 | 全体项目成员与外协方，无例外 |

### 3.2 职责

| 角色 | 配置管理职责 |
|---|---|
| 项目负责人 | 批准本计划与基线定义；CCB 决策；对配置管理有效性负总责 |
| 技术负责人 | 批准框架基线与框架变更（R5）；判定变更等级 |
| 配置管理员 | 维护配置项清单与基线；打标签与冻结；执行配置审计；出具状态报告；管理制品仓库 |
| 模块负责人 | 保证本模块提交符合提交规范；发起模块级变更申请 |
| 开发 | 按要求提交与关联变更编号；不直接修改他人模块；不绕过 CI |
| 测试 | 验证回归范围；核对制品版本与测试记录版本一致 |
| 质量负责人 | 复核配置审计结论；对不符合项跟踪至闭环；核查不可裁剪红线 |

### 3.3 禁止行为（违反即记不符合项）

| 编号 | 禁止行为 | 后果 |
|---|---|---|
| F-01 | 直接向受保护分支强推提交，覆盖基线标签 | 立即回滚；记不符合项；门禁不通过 |
| F-02 | 未走变更流程修改已冻结基线的配置项 | 变更无效；回溯影响范围并重新走流程 |
| F-03 | 交付物不在版本控制内（U 盘、共享盘、本地目录作为唯一来源） | 视为不存在；R7 交付物审计不通过 |
| F-04 | 修改代码而不同步更新对应设计/需求文档（文档漂移） | R4 门禁不通过 |
| F-05 | 用同一制品反复覆盖发布而不升版本号 | 版本号不合规；R8 不通过 |

| **`framework/v0.2` … `framework/v0.N`** | **框架基线（迭代）** | 每次 R5 框架变更批准并回归通过后 | 同 `framework/v0.1`，加上受本次变更影响的模块契约 | 同上；**变更频率应递减**，若长期高频推翻框架须复盘 S2 抽象层次 | 技术负责人（R5 主持） | R5 框架变更评审 |
| **`test-baseline/v1.0`** | **测试基线** | S5 测试准出评审（R6）通过后立即打标签 | 测试计划、测试说明与用例、测试报告与记录、测试数据生成脚本 | 冻结；测试资产变更须说明理由并同步更新 RTM | 质量负责人（R6 主持） | 变更控制流程 |
| **`product/v1.0.0`** | **产品基线** | S6 验收评审（R7）通过后立即打标签 | 全部文档、全部模块代码、全部脚本、构建产物 + 制品哈希、用户手册、版本说明 | **冻结为只读**；此后任何修改都产生新版本 `v1.0.1` / `v1.1.0` / `v2.0.0` | 甲方/产品（R7 主持） | 变更控制流程 + R8 发布评审 |

> **基线三律**：
> 1. **打标签之前的集合不是基线**——口头冻结不算数，必须有不指向可移动对象的标签；
> 2. **基线冻结后不得原地修改**——修正只能是"新版本 + 变更记录"；
> 3. **每次打标签必须同时记录"包含哪些配置项"**——否则无法回答"这个版本到底发了什么"。

### 5.2 基线建立与冻结操作规程

| 步骤 | 动作 | 产出 | 责任人 |
|---|---|---|---|
| 1 | 确认门禁已通过（R1 / R2 / R5 / R7） | 评审记录编号 | 配置管理员 |
| 2 | 核对本基线应包含的配置项是否全部就位、版本一致 | 基线内容清单 | 配置管理员 |
| 3 | 在受保护分支打**附注标签**：`git tag -a <基线名> -m "<说明>"` | 标签 | 配置管理员 |
| 4 | 保护标签：禁止强推、禁止移动、禁止删除 | 仓库保护规则 | 配置管理员 |
| 5 | 归档构建产物，标注对应提交号与产品版本号 | 制品记录 | 配置管理员 |
| 6 | 更新状态记录与基线条目 | 状态报告 | 配置管理员 |
| 7 | 通知全体成员 | 通知记录 | 配置管理员 |

### 5.3 基线回退

| 项 | 内容 |
|---|---|
| 允许回退的触发条件 | 发布版本出现 P0 缺陷无法快速修复；变更引入不可接受的回归 |
| 回退对象 | 制品（首选，秒级）/ 代码标签（次选）/ 数据（须评估） |
| 回退审批 | 技术负责人（R8 范围内）；涉及数据回退须项目负责人批准 |
| 回退记录 | 必须记录：回退原因、回退目标版本、影响范围、后续处置 |
| 回退后的版本号 | 回退不改变历史版本号；重新发布须升 PATCH 号并说明"回退至 <版本> 内容" |

## 六、版本号规范

### 6.1 语义化版本（MAJOR.MINOR.PATCH）

| 段位 | 何时递增 | 示例变化 | 兼容性承诺 |
|---|---|---|---|
| **MAJOR** | 不向后兼容的变更（接口契约破坏、数据结构不兼容、配置项语义变更） | `1.4.2` → `2.0.0` | 使用者必须适配 |
| **MINOR** | 向后兼容的功能新增 | `1.4.2` → `1.5.0` | 使用者可直接升级 |
| **PATCH** | 向后兼容的缺陷修复 | `1.4.2` → `1.4.3` | 使用者可直接升级 |

**附带规则**

| 规则 | 说明 |
|---|---|
| MAJOR 递增时 MINOR 与 PATCH 归零 | `1.4.2` 的破坏性变更结果是 `2.0.0`，不是 `2.4.2` |
| `0.y.z` 表示开发期 | `0.y.z` 阶段 API 不稳定，允许破坏性变更；**未稳定的框架不得宣布 v1.0** |
| 构建号可附加 | `<产品版本>+<构建号>`，构建号不参与比较 |
| 预发布标识 | `<版本>-rc.N` 表示候选版本，不得作为正式发布版本 |
| 版本号唯一 | 同一版本号不得对应两份不同内容的制品 |

### 6.2 各对象版本号对照（框架版本与产品版本分离）

| 对象 | 版本格式 | 示例 | 递增规则 | 批准人 |
|---|---|---|---|---|
| **需求基线** | `req-baseline/vMAJOR.MINOR` | `req-baseline/v1.0` | MAJOR：需求范围发生变更；MINOR：不改变范围的澄清与补充 | 技术负责人 |
| **框架基线** | `framework/vMAJOR.MINOR` | `framework/v0.1` | MAJOR：模块划分或契约的不兼容变更；MINOR：兼容性扩展 | 技术负责人（R5） |
| **模块** | `MAJOR.MINOR.PATCH` | `1.3.2` | 语义化，按 6.1 | 模块负责人 |
| **产品发布** | `MAJOR.MINOR.PATCH` | `2.1.0` | 语义化 + 可选构建号 | 技术负责人（R8） |
| **文档** | `VMAJOR.MINOR` | `V1.1` | MAJOR：结论、范围、裁剪等实质内容变更，需重新评审；MINOR：文字、补充、示例 | 文档责任人 |

> **为什么框架版本与产品版本必须分离**：框架的"稳定"与产品的"可用"是两个独立维度。
> 框架 `v0.1` 完全可以支撑产品 `v1.0.0` 的发布——**框架版本号表达的是契约稳定性，不是产品质量等级**。
> 把二者混为一个版本号，会导致两种错误：要么为了"版本号好看"过早冻结框架，
> 要么每次框架微调都强制产品升 MAJOR。
>
> **不要过早宣布框架 v1.0**：一旦宣布 v1.0 即意味着契约冻结，
> 此后任何破坏性变更都必须走完整变更流程并通知全部使用方。这是框架演进最常见的自伤。

### 6.3 分支与标签策略

| 对象 | 策略 | 说明 |
|---|---|---|
| 稳定分支 | `main`，受保护 | 只接受来自 PR 的合并；每次合并打标签；禁止直接强推 |
| 集成主线 | `develop` | 模块开发汇入此处；CI 全量执行 |
| 开发分支 | `feature/<M01>-<简述>` | 从 `develop` 切出，完成后 PR 回 `develop` |
| 修复分支 | `fix/<BUG-001>` | 必须关联缺陷编号 |
| 紧急修复分支 | `hotfix/<产品版本>` | 从 `main` 切出，修完回并 `main` 与 `develop` |
| 基线标签 | `req-baseline/*`、`framework/*`、`test-baseline/*`、`product/*` | 附注标签，受保护；禁止移动、强推覆盖或删除 |
| 提交信息 | 依 Conventional Commits：`<类型>(<范围>): <简述>`，正文写明**为什么改**，并附追溯信息 `<REQ-F-001>` / `<M01>` / `<BUG-001>` / `CHG-<YYYY-MM-DD>-<序号>` | **框架变更必须使用 `framework` 类型**，使框架变更在提交历史中一眼可辨，便于统计"框架变更次数 / 已实现模块数"这一健康度指标 |
| 合并要求 | CI 通过（构建 + 测试 + 覆盖率 + 追溯矩阵校验 + 改动范围校验）+ 至少 1 人评审通过 | 见 `.github/workflows/` 与 `tools/` |

> 分支模型、提交信息规范与合并要求以 `docs/04-配置与版本/配置管理与版本化.md` 第六节为准，本表与其保持一致。

## 七、变更控制

### 7.1 变更控制流程（七步，不可跳）

| 步骤 | 动作 | 责任人 | 产出 | 入口条件 |
|---|---|---|---|---|
| **① 申请** | 提交变更申请，写明动机、触发条件、现象证据 | 提出人 | 变更申请单 `CHG-<YYYY-MM-DD>-<序号>` | 有明确的现象证据（禁止"我觉得更好"） |
| **② 影响分析** | 列出受影响配置项、受影响需求（RTM 反查）、需重跑的测试、工作量估算 | 提出人 + 设计者 | 影响分析表 | 配置项清单与 RTM 可查 |
| **③ 评审** | 方案对比（至少 2 案：改 / 不改或最小改）；判定变更等级 | CCB / 评审组 | 评审意见 | 影响分析已完成 |
| **④ 批准** | 批准则确定新版本号；驳回则记入技术债清单（不是丢弃） | 按 7.2 权限 | 批准记录 | 评审结论明确 |
| **⑤ 实施** | 改代码 + **同步改 HLD/契约/需求文档**；同一次提交内完成 | 实施人 | 提交记录 | 批准已生效 |
| **⑥ 回归** | 按影响分析推导的范围执行回归（不必全量，但必须有依据） | 测试 | 回归记录 | 实施完成且 CI 通过 |
| **⑦ 新基线** | 打标签、更新配置项清单与状态记录、通知相关方 | 配置管理员 | 新基线标签 | 回归通过 |

> **规则**：**③ 与 ④ 不得合并到 ⑤ 之后。**"先改完再补审批"在本仓库视为未授权变更；
> 紧急变更按 7.4 处理，但仍须在 48 小时内补审。
>
> **与仓库文档的对应**：`docs/04-配置与版本/配置管理与版本化.md` 第五节把同一流程表述为**八步**，
> 将本表第 **⑦ 新基线**（打标签、更新配置项清单与状态记录、通知相关方）拆为
> "⑦ 新基线冻结 + ⑧ 归档与状态记录"两步。**二者步骤内容一致，仅拆分粒度不同**，不构成第二种流程。

### 7.2 变更分级与审批权限

| 等级 | 判定标准 | 评审 | 批准人 | 回归范围 | 版本影响 |
|---|---|---|---|---|---|
| **重大** | 破坏性接口变更；需求范围变更；基线定义变更；数据结构不兼容 | R5（框架）/ R1（需求） | 技术负责人 + 甲方/产品（涉需求时） | 全量或按影响分析的全回归 | 框架 MAJOR / 产品 MAJOR |
| **一般** | 兼容性扩展；模块内实现调整；新增非破坏性能力 | R5 或 R4 | 技术负责人 | 受影响模块 + 集成测试 | 框架 MINOR / 产品 MINOR |
| **轻微** | 缺陷修复；文案；不改变契约的重构 | R4（可简化） | 模块负责人 | 定向回归 + 冒烟 | 产品 PATCH |
| **紧急** | 生产环境 P0 故障修复 | **事后评审**（48h 内补） | 技术负责人（事后补批） | 定向回归 + 冒烟，24h 内补全回归 | 产品 PATCH |

### 7.3 变更申请最小字段集

| 字段 | 是否必填 | 说明 |
|---|---|---|
| 变更编号 | 必填 | `CHG-<YYYY-MM-DD>-<序号>` |
| 变更类型 | 必填 | 需求 / 设计 / 代码 / 脚本 / 构建方式 / 基线定义 |
| 变更等级 | 必填 | 重大 / 一般 / 轻微 / 紧急 |
| 触发条件 | 必填 | 框架变更须引用 FC-1…FC-6 编号（见 `docs/01-流程与阶段/框架与模块共演化.md`） |
| 现象证据 | 必填 | 可复现的现象、日志、缺陷编号；**禁止仅凭个人偏好** |
| 受影响配置项 | 必填 | 引用 4.2 的配置项编号 |
| 受影响需求 | 必填 | 引用 `<REQ-F-001>` 形式的编号（RTM 反查） |
| 需重跑的测试 | 必填 | 单元 / 集成 / 系统 / 冒烟，逐项列出 |
| 方案对比 | 必填 | 至少 2 案，含成本估算与"不改"的持续成本 |
| 决策与理由 | 必填 | 采纳方案 / 驳回理由 |
| 版本影响 | 必填 | 新框架版本号 / 新产品版本号 |
| 批准人与日期 | 必填 | `<姓名>` / `<YYYY-MM-DD>` |

### 7.4 紧急变更（生产故障）

| 步骤 | 要求 | 时限 |
|---|---|---|
| 1 | 由技术负责人口头授权先行修复，**记录授权人与时间** | 立即 |
| 2 | 修复提交须关联故障编号，走最小回归（冒烟 + 定向） | 4h 内 |
| 3 | 补交变更申请与影响分析 | 48h 内 |
| 4 | 补做完整回归并出具记录 | 24h 内（自补审后计） |
| 5 | 复盘并更新基线 | 5 个工作日内 |

> **规则**：紧急变更**不是免流程通道**，只是流程顺序后置。缺少 3、4、5 步的紧急变更，
> 在 S7 发布评审（R8）中一律判为不通过。

## 九、配置审计

### 9.1 审计类型

| 类型 | 全称 | 回答的问题 | 时点 | 执行人 |
|---|---|---|---|---|
| **FCA** | 功能配置审计 | 交付物是否实现了已基线需求？（"该做的做了吗"） | R6 前、R7 前 | 质量负责人 + 测试代表 |
| **PCA** | 物理配置审计 | 交付物是否与文档、基线、制品一致？（"做的和说的是同一个东西吗"） | 每阶段末、R7 前 | 配置管理员 + 质量负责人 |

### 9.2 配置审计检查单

**A. 配置项完整性（PCA）**

- [ ] 4.2 配置项清单表覆盖**文档、代码、脚本、构建产物**四类，无缺类；
- [ ] 清单中每一项都能在指定位置找到，且路径无误；
- [ ] 不存在"存在于交付物中但不在清单里"的实体（无账外配置项）；
- [ ] 不存在"在清单里但已删除/失效"的悬挂条目；
- [ ] 全部配置项均在版本控制或制品仓库中，无"仅本地/共享盘"的孤本；
- [ ] **无密钥/凭据入库**（含历史提交扫描）——一旦发现，立即吊销并轮换，同时记严重不符合项；
- [ ] 第三方依赖清单与锁定文件（如 `requirements.txt` / `package.json` + lock）已入库，构建可复现。

**B. 基线与版本（PCA）**

- [ ] 应存在的基线标签齐备：`req-baseline/v1.0`、`framework/v0.1`、`test-baseline/v1.0`、`product/v1.0.0`（按当前阶段判定）；
- [ ] 每个基线标签为**附注标签**且内容不可变（未被移动或强推覆盖）；
- [ ] 每个基线有"包含配置项清单"，且清单与标签实际内容一致；
- [ ] 版本号符合第六章语义化规范（MAJOR/MINOR/PATCH 递增理由成立）；
- [ ] 框架版本与产品版本**分离**，未混用同一版本号；
- [ ] 模块版本号与产品版本号无矛盾；
- [ ] 制品版本号与源码标签一一对应，且同版本号制品内容唯一（未覆盖发布）；
- [ ] **制品哈希已记录并可校验**；
- [ ] 不存在把构建产物提交进源码仓库的做法（构建产物走制品库）。

**C. 变更控制（过程审计）**

- [ ] 本期内每一次变更都有变更编号，且能追溯到代码提交或文档版本；
- [ ] 每次变更都有影响分析（受影响配置项、受影响需求、需重跑测试）；
- [ ] 变更等级判定与批准权限符合 7.2；
- [ ] 无未授权的基线直接修改（对基线的差异提交全部有对应变更单）；
- [ ] 紧急变更已完成 48h 内补审与 24h 内补回归；
- [ ] 被驳回的变更已记入技术债清单，未丢失。

**D. 文档与代码一致性（PCA，红线）**

- [ ] 代码变更涉及的 HLD / 模块契约 / LLD 已在**同一次变更**中同步更新；
- [ ] 需求变更已同步更新 SRS 与 `req-baseline/*`，并升版本号；

## 十五、填写指引

1. **构建产物最容易被漏掉。** 只把源码放进 Git、把包放在本机或 CI 临时空间，
   会导致"发布出去的制品到底是哪次提交构建的"无法回答，追溯链在最后一步断裂。
   4.2 表中"构建产物"一类必须有条目，并注明制品仓库位置。
2. **基线标签不要随手打。** 基线必须在对应门禁通过后打——需求基线走 R1、框架基线走 R2、
   测试基线走 R6、产品基线走 R7——并且要同时记录"这个基线包含哪些配置项"。
   没有内容清单的标签，事后无法回答"这个版本究竟发了什么"。
3. **不要把框架版本当成产品版本。** 框架 `v0.1` 支撑产品 `v1.0.0` 是正常的；
   为了"版本号好看"而过早宣布框架 `v1.0`，会让此后每一次合理调整都背上破坏性变更的流程成本。
4. **"先改完再补审批"不是变通，是未授权变更。** 变更七步中③评审与④批准必须在⑤实施之前；
   紧急变更可以后置，但必须完成 48h 补审与 24h 补回归，否则 R8 发布评审一定不通过。
5. **配置审计检查单不能只由配置管理员自查。** 审计执行人不得是本次被审计配置项的作者；
   9.2 的 A–F 六组检查单须逐项给出结论与证据位置，勾选而无证据的审计记录视为无效。
6. **配置项清单是活文档，不是 S0 的一次性作业。** 新增模块、新增脚本、新增文档时，
   必须在同一次变更中更新清单；清单长期不更新的项目，配置审计会立刻暴露账实不符。
