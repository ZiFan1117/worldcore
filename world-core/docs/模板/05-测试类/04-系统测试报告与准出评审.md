# 系统测试报告与准出评审

> **文档编号**：`<项目代号>-TR-<序号>-V<主版本>.<次版本>`
> **编号规则**：`<项目代号>-<类别码>-<三位序号>-V<主版本>.<次版本>`；本文件类别码 **TR**（Test Report），

> - **GB/T 25000.51-2016**《系统与软件质量要求和评价（SQuaRE）第51部分：就绪可用软件产品（RUSP）的质量要求和测试细则》——**8 个质量特性逐项结论的依据**；
> - GB/T 8566-2022《系统与软件工程 软件生存周期过程》——**验证过程（§6.4.9）**与**确认过程（§6.4.11）**的定位。
>   ⚠️ 注意：8566-**2022** 已删除"软件合格性测试"术语，**不要写成"合格性测试过程"**。

> - GB/T 8567-2006《计算机软件文档编制规范》——文档编写要求。

## 9 填写指引（常见错误）

1. **质量特性表留空或写"待补"**——8 个特性**必须逐项有结论**。不适用的要写明理由（如纯后端服务无界面 → 易用性部分子特性不适用），留空等于承认有未测项，直接导致不准出。
2. **只写"结论：满足"不给证据**——"证据"列必须指向具体可查的东西：用例执行记录路径、压测报告、监控曲线、数据库核对截图。没有证据的结论在评审会上不予采信。
3. **未执行用例不列明细**——未执行用例**不得计入"通过"**，也不得静默略过。必须逐条列出原因、风险、补偿措施、批准人与期限，否则用例执行率不成立。
4. **缺陷统计只报总数不分模块/级别**——只报"共发现 30 个缺陷"无法支撑准出判断。必须给出 P0–P4 分布与模块分布，才能看出风险集中在哪、成熟度是否收敛。
5. **把"不通过"用例悄悄删掉或标记为跳过**——正确做法是给出四类处置结论之一（修复后重测 / 判定用例错误并修正 / 降级为已知问题 / 转技术债）并留痕。静默删除会导致追溯体系失效。
6. **用"基本满足""总体良好"作结**——准出结论必须二值化（准出 / 不准出），并附量化依据。模糊表述会让门禁失去闸门作用。
