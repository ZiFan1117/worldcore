# 项目开发计划

> **文档编号规则**：`<项目名称>-<文档类型码>-<三位流水号>-v<主版本>.<次版本>`，本文件类型码为 `SDP`，
> 示例 `<项目代号>-SDP-001-v1.0`；编号一经分配永不复用，版本号随文档修订递增。
> 文档类型码：`FSR` 可行性研究报告 / `SDP` 项目开发计划 / `SQAP` 软件质量保证计划 / `SCMP` 软件配置管理计划。
> **适用阶段**：**S0 立项与策划**；准出门禁为 **R0 立项评审**，并在 S1–S7 各阶段被引用作为进度与裁剪的基准。
> **依据标准**：**GB/T 8567-2006**《计算机软件文档编制规范》（项目开发计划）；流程依据
> **GB/T 8566-2022**《系统与软件工程 软件生存周期过程》；裁剪依据见 `docs/00-标准依据/标准依据.md` §四。
> **状态**：**模板（未填写）**。本计划经批准后即成为**进度基准与裁剪基准**，修订须走变更控制。
>
> 本文件回答三个问题：**做什么、谁来做、什么时候做到什么程度。**
> 其中「五、标准裁剪说明」是本仓库的**强制章节**：不写裁剪说明的项目，每个阶段都会重复争论
> "这份文档要不要写"，这是 S0 最常见的失败模式。

## 五、标准裁剪说明

**裁剪不等于不做。** 裁剪是"声明哪些标准要求本项目不做、为什么不做、用什么手段补偿其目的、谁批准"。
国标是通用要求，项目必须裁剪；**但未留痕的裁剪等于没做**。

### 5.1 裁剪原则与红线

| 编号 | 原则 | 说明 |
|---|---|---|
| PR-01 | 裁剪须留痕 | 任何裁剪必须填入 5.2 表格并获批准，口头约定无效 |
| PR-02 | 裁剪须补偿 | 裁剪一项要求，必须给出覆盖其目的的替代手段 |
| PR-03 | 裁剪须可追溯 | 裁剪决策是本计划的一部分，纳入配置管理，随基线版本化 |
| PR-04 | 红线不可裁剪 | 见下方红线清单，任何项目、任何规模、任何理由均不得裁剪 |

> **红线：以下三项不可裁剪。**
>
> 1. **需求基线与需求追溯矩阵**——没有需求基线，变更无从判定；没有 RTM，无法证明"该做的都做了"。
> 2. **配置管理与版本化**——文档、代码、脚本、构建产物必须纳入版本控制；没有版本化就没有可复现的交付。
> 3. **至少一个级别的、有记录的系统级测试**——端到端验证必须有可复现的记录；
>    "开发自测通过"不构成系统级测试。
>

## 八、填写指引

1. **裁剪说明不能等到"以后再说"。** 最常见的失败是 S0 只写进度和分工、跳过裁剪说明，
   结果 S1–S7 每个阶段都要重新争论"这份文档要不要写"，反复返工。裁剪必须在 R0 一次谈清。
2. **"时间紧、人手不够"不是裁剪理由。** 这类表述应写入 3.6 关键问题并配应对措施；
   裁剪理由只接受项目规模、风险等级、合同约定、生命周期四类客观理由。
3. **红线项不要试图变通。** 例如用"开发自测通过"代替系统级测试、用"文件共享盘"代替版本控制，
   在 R0 评审时会直接判定门禁不通过，不存在协商空间。
4. **任务分解不要出现"共同负责"。** 每项任务必须有唯一责任人和可交付物；
   出现共同负责即视为无人负责，这是进度失控的最常见起点。
5. **进度表不要把 S2 与 S3 合并。** 合并压缩的是唯一的低成本框架验证窗口，
   代价会在 S5 集成期以数倍返工的形式出现。
6. **关键问题不等于技术难点清单。** 本表只放影响里程碑可达性的问题；
   其他技术问题进入技术债清单，否则关键问题表会被稀释到失去预警作用。
