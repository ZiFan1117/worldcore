# 主文 · 可行性研究报告

> 本节是**给人看的主文**：按标准章节结构写"是什么／怎么做／判据／结论"，**力求简练**。
> 一切依据（标准条款逐字与双源、每条判据的「应当失败」反例与实测原始输出、论证与裁定、台账、
> 历史冻结表、证据索引与实测命令）**一律在本文档后面的附录**里，**不另立文件**。

## 一、本报告要回答什么

本项目要做的产品是**世界核心（World Core）**：一个以**只追加事件账本**为唯一事实来源、
以**本体（词表）**定义世界、以**可重建读模型**对外提供投影的本地单机系统。
本报告回答一个问题：**这件事做不做得成、值不值得做、在什么条件下做。**

## 二、结论

**有条件可行。** 四个维度各自的结论：

| 维度 | 结论 |
|---|---|
| 技术 | **可行**：核心机制（追加账本、词表校验、读模型重建、门禁拦截）已在骨架层实测跑通；**主要不确定性集中在性能与并发**（见第五节） |
| 经济 | **可行**：**零外部依赖、单二进制交付**；无采购、无云服务、无授权费 |
| 法律 | **基本可行、有一处未闭合**：许可为双许可（`MIT OR Apache-2.0`）；**合规缺口两处**已登记为条件（缺 `LICENSE` 文件、`tools/` 三条脚本的上游授权） |
| 进度 | **可行**：单人 + AI，按阶段推进；**最大风险是批准者吞吐（1 人 × 9 道门禁）** |

## 三、候选方案与取舍

至少两个方案被评估并给出淘汰理由；**被选方案**＝"极小核心 + 命名空间扩展"：
本体只管极小核心，其余能力以命名空间扩展接入；账本**只追加**，读模型**可丢弃可重建**。
被否方案与其理由见**附录**中的方案对比表。

## 四、已知边界（不做什么）

本报告明确**列出本项目不做什么**：不追求分布式/联邦、不做多租户、不做图形界面、
不引入外部运行时（Python/Go/JVM/Node）、不做数据迁移与生产环境部署。
完整的边界清单与其影响见**附录**。

## 五、主要风险（每条给触发信号）

| 编号 | 风险 | 触发信号（可观察） |
|---|---|---|
| R-01 | 门禁不可绕过这一承诺可能不成立 | 越权用例矩阵出现**未被拦截**的一条 |
| R-02 | 性能承诺可能不成立 | 冷启动全量重放的 P95 **超过目标值**，或测量环境缺项 |
| R-03 | 一人多角色导致**无独立复核** | 某道门禁的"复核"由产出者本人完成 |
| R-04 | 关键技术洞（补偿、新鲜度、演进）未闭合 | 对应模块的实现与文档出现**不一致** |
| R-05 | 合规缺口未闭合 | 仓库内**仍无** `LICENSE`，或上游授权未落 |

## 六、条件清单（本报告提出的前置条件）

本报告提出若干**条件**（编号 `CON-01`…`CON-12`）：每条给**责任人**与**关闭日期**。
这些条件与 R0 评审的条件清单是**同一套口径的两处投影**；**未闭合者不得被当作已满足**。

## 七、本报告不能证明的事

不证明"标准条款号正确"（引用核验级别见附录）、不证明"性能达标"（那是 S5/S6 的度量）、
不证明"门禁强度已足够"（那是独立评审的判定）。**"已升格"不等于"已达标"。**

## 三、对现有系统的分析

> **"现有系统"的定义（本章的范围声明）**：本项目**没有可替代的现成系统**，
> 故本章分析的对象是**"现状做法"**——即"通用 OS + 应用层拼装"这套今天实际在用的东西
> （编辑器 / 终端 / git / 文件系统 / 聊天记录 / `agentd` / `transferor`）。
> 这是方案 D（维持现状）的基线，也是 §4.3"改进之处"和 §6.4"收益"的对照物。

### 3.1 数据流程和处理流程

| 序号  | 现状环节                         | 输入             | 处理                                   | 输出             | 痛点                                                                    |
| --- | ---------------------------- | -------------- | ------------------------------------ | -------------- | --------------------------------------------------------------------- |
| 1   | 人做一件事（编辑文件、跑命令、改配置）          | 人的意图（在编辑器/终端里） | 应用自行执行，**不产生语义事件**                   | 文件字节变化、终端输出    | **无 `before` 镜像**：改完只剩"现在"，改之前是什么只能靠 git 或记忆；**git 有提交粒度，没有字段粒度**     |
| 2   | agent 做一件事（经 MCP / CLI / 脚本） | 任务描述           | 工具调用，**能力声明与审计靠约定**                  | 副作用落在文件/进程/网络上 | 内核只有 **uid/gid/cgroup 粒度**，答不了"这个动作声明了哪个能力、谁批准的"；越界与否**无法在动作前判定**     |
| 3   | 状态被多方读取（人看界面、agent 读文件）      | 同一份底层数据        | **各自解释**：人看渲染、agent 读文本              | 两套"眼里的世界"      | 没有"同一份读模型"的结构保证；**不同源比截图更危险**（REF-06 §2.5）                            |

## 四、所建议的系统

> 本章描述的即**第五章的方案 A（推荐方案）**。章内不重复论证取舍理由，取舍见 §5.3。

### 4.1 对所建议系统的说明

| 项                | 内容                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 系统定位             | **一句话**：造一个以**语义事件**为唯一真相的"世界"——**人和 AI agent 共享同一份状态、同一条门禁、两个同源投影**（语言投影给 agent、视觉投影给人）。<br>**不是**又一个 AI 浏览器/agent 产品，**不是**给 Linux 装适配器，**不是**写操作系统。                                                                                                                                                                                                                                |
| 建设方式             | **自研**（无供应商：`存`/`传`/`管`/`显` 造；`载` 采购 Linux；`进` 的算力买、脐带造）                                                                                                                                                                                                                                                                                                                              |
| 技术路线要点           | • **语言**：Rust（单一可执行文件）<br>• **真相模型**：**纯事件溯源**——语义事件日志是唯一真相，对象/状态是读模型（可随时重算），回滚靠追加补偿事件<br>• **依赖纪律**：只用标准库 + **最小依赖**（当前 `Cargo.toml` 仅 `serde_json = "1"`）<br>• **持久化**：账本 / 词表 / 协议**一律纯文本**（JSON Lines / JSON），**语言无关**<br>• **进程形态**：**单进程**（本体/账本/读模型/运行时/门禁都在核心内，不拆）<br>• **部署形态**：载体上的一个**一等组件**（系统服务层，与 systemd 同层），非应用层；成熟后作 PID 1（阶段二，**不在本期范围**）<br>• ⚠️ **不展开设计**（设计见 S2） |
| 主要子系统 / 模块划分（初稿） | `M01` **本体**（词表加载 + 版本校验 + 事件合法性校验）· `M02` **账本**（只追加、按 `seq`、可重放）· `M03` **读模型**（fold + 可重建）· `M04` **运行时**（启动装配 + 主循环 + **唯一写入口**）· `M05` **门禁**（能力表 + 不可逆分级 + 审计 + **不可绕过**）· `M06` **语言投影**（结构化出口）· `M07` **视觉投影**（渲染出口）· `M08` **检查点**（重放加速，非真相）<br>（最终以 S2 模块清单为准；⛔ **第一版不拆进程**）                                                                                                |
| 与外部系统接口          | • **载体**：进程 / 内存 / 文件 / IPC / 隔离 / 可开发 —— 只经**载体适配层**调用（薄到能替换）<br>• **上位**：`systemd`（启动它、给一个状态目录 + 一条 socket 路径）<br>• **`agentd`（Go）**：经**纯文本通道**复用其门禁/审计能力，**不重写**<br>• **`transferor`（Python）**：属 08 项目（脐带），**不在本项目范围**<br>• ⛔ **明确拒绝**：MCP / A2A / varlink **不作为世界协议**                                                                                                             |
| 交付形态             | **私有化部署**（勾选）：单机、单一可执行文件 + 出厂本体文件，随仓库分发（托管于 GitHub；2026-09-26 实测该仓库为**私有**。档位仍判 B——依 `06-swe-gb`「提交 GitHub = 按 B 档」，**不以可见性为条件**）                                                                                                                                                                                                                                                     |

### 4.2 数据流程和处理流程

| 序号  | 新流程环节     | 输入                    | 处理                                              | 输出                                               | 相对现状的改进                            |
| --- | --------- | --------------------- | ----------------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| 1   | 人要做事      | 界面上的操作（视觉投影）          | 投影把操作翻成 `act` 事件 → **写入账本**                     | 一条 `act` 事件（带 `actor`/`capability`/`request_id`） | 现状：操作没有语义记录 → 现在：**动作本身就是一等事件**    |
| 2   | agent 要做事 | 任务（语言投影）              | 同上，走**同一条总线**（只有安检不同）                           | 一条 `act` 事件                                      | 现状：能力声明靠约定 → 现在：**声明即请求，进门前查门禁**   |

| 7   | 回滚一次改动    | "回到某个 `seq`"          | 追加**补偿事件**（不改历史）                                | 状态回到目标点；**全程未用载体快照**                             | 现状：整机快照 → 现在：**一次改动级别的回滚，且不依赖载体**  |

#### T-01 专门说明：为什么"门禁不可绕过"是最高风险项（本节的承重段）

**（1）它不是"一个功能"，它是"这到底是世界还是一个应用"的判据。**

`07/4-计划/03` §六 上游 Step 5 的验收写得最直白：

> ① 以 Agent 身份改门禁配置 → **失败**；② 绕过世界核心直接写账本文件 → **失败**。
> 能改 / 能绕 → **那它还是应用，不是世界**。

也就是说，T-01 不达标时，**其余九个技术点全部达标也没有意义**——项目会得到一个"带语义事件日志的应用"，
而不是 `07/00-总纲` §7 B 门所要求的"世界"。这正是"决定性问题"的含义。

**（2）为什么它风险高：本项目**没有**内核级强制力的现成保障。**

- `agentd` 是**用户态程序**（145 行 `cap.d` 解析 + 路由，无内核模块）；
- 它当前靠**自律**：`07/00-总纲` §12 自首第 7 条原文——"**门禁的强制力尚未落地——Landlock 未接
  （05 篇列为'第二天'），当前 `管` 仍靠 agentd 自律**"；
- 而 §2.4 的"最强反驳"**已被承认为成立**：agent 只要能写自己的配置文件，就能自我授权；
- 载体能提供的东西是有天花板的：**"吊销不能即时生效"**（seccomp 不可卸载）
  → 语义只能定为 **"吊销 = 勒停重建"**（REF-06 §6 `管`）。

**（3）可行的技术路径是清楚的（这是它仍判"有条件可行"的原因）。**

强制力**不来自世界核心自己，而来自载体**，并且**完全可以只靠用户态做到**（REF-09 §三）：

| 路径                     | 内容                                            | 本项目中的落点                                 |
| ---------------------- | --------------------------------------------- | --------------------------------------- |
| ① **文件权限**             | 门禁配置与代码放在被管者不可写的目录（属主/权限位）                    | 世界核心以独立系统用户运行；配置目录 `0755 root:`、被管者无写权限 |
| ② **Landlock（最小权限沙箱）** | 对被管者进程施加不可自我解除的访问限制                           | `REQ-N-005`；【候选】S4 实现、S5 验证             |
| ③ **systemd 沙箱指令**     | 以服务单元固化 `ProtectSystem`/`ReadWritePaths` 等    | 一等组件的部署形态（系统服务层）                        |
| ④ 显式堵绕过口               | 堵 `io_uring` / `memfd` 等绕过路径；网络强制走代理（身份在代理层管） | REF-06 §6 `管` 的"硬约束"列                   |

**（4）为什么本阶段**不能**判它"可行"。**

模板规则要求：高风险技术点**必须**给出原型验证结论或明确的外部依据；
仅凭"业界有成熟案例"判定的，视为未验证。
本项目的实际状态是：**路径清楚、判据清楚、停机线清楚，但一行验证代码都没有**
（`src/` 仅 186 行本体校验，未编译）。
因此本报告把 T-01 记为"**有条件可行**"，并把它同时写进：
§2.3 假定清单（相关假定）、§4.5 局限性 SL-11、§8.2 条件清单 **CON-01**（最高优先条件）。

**（5）停机线（什么时候承认此路不通）。**

`07/4-计划/03` §六已给出：

> **上游 Step 5 做不到"不可绕过" → 世界核心的部署位置错了**（可能跑成了普通用户 / 规则放在可写目录）。

补充一条本项目自加的判据：若尝试 **3 次**仍无法在真 VM 中做到
"以被管者身份改门禁配置失败 + 绕过世界核心直写账本失败"，
则触发 `07/00-总纲` §7 的**停机线机制**——回退到"方案 B/C"，或承认"地"这一层在本项目周期内无法立起。
