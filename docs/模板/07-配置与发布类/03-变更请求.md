# 变更请求（CR）

> **文档编号**：`<项目代号>-CR-<三位序号>-V<主版本>.<次版本>`，示例 `<项目代号>-CR-001-V1.0`
> **类别码**：`CR`（Change Request）
> **适用阶段**：**S0–S7 全程**。任何对**已基线化内容**的改动，都必须先有本记录。
> **准出**：变更实施前的审批（B 档走 R5 或相应评审；A 档自审并留痕）
>
> **依据**：
> - **ISO/IEC 29110-5-1-2** 的 **Change Request** 工作产品（Basic 轮廓 22 个工作产品之一，Entry 轮廓 14 个之一）
> - `GB/T 8566-2022` 的**配置管理过程**（变更控制）与**信息管理过程**
> - `GB/T 8567-2006` **无独立的变更请求模板**——这是本模板存在的原因
>
> **文档状态**：模板（Template）· 未填写
>
> ⚠️ **引用提示**：ISO/IEC 29110 **中国未采标**，不能作为"符合国家标准"的依据。
> 对外文件引用时，请引 `GB/T 8566-2022` 的配置管理过程。
> 本模板采用它，是因为 **GB/T 8567-2006 的文档种类里没有"变更请求"这一类**，
> 而过程证据恰恰是审计最看重的部分。

---

## 1. 为什么要单独有这张表

| 没有变更请求时 | 有变更请求时 |
|---|---|
| 改了需求，没人知道为什么 | 改动的**理由**有记录 |
| 影响分析靠脑子想 | 影响分析**写下来**并被检查 |
| "这行为什么这么写"无从追溯 | 能追到具体一次变更 |
| 回归范围靠感觉选 | 按变更影响范围选（见附件四 §六） |
| **与需求基线不一致，且查不出原因** | 基线与实现始终对得上 |

> **一句话**：需求基线是对"不再随意改动"的承诺。
> **变更请求是唯一合法的破例程序**——没有它，基线就形同虚设。

## 7. ⚠️ 两条容易走偏的规则

### 7.1 紧急变更不等于免流程

**紧急**只允许**后置**影响分析与评审，**不允许跳过**：

| 允许 | 不允许 |
|---|---|
| ✅ 先止血（如回滚、热修），后补本记录 | ❌ 不写变更记录 |
| ✅ 影响分析在 24 小时内补完 | ❌ 不跑回归 |
| ✅ 审批后补（须注明"事后追认"与追认人） | ❌ 不更新文档与 RTM |

**追认栏**（紧急变更专用）：

| 项 | 内容 |
|---|---|
| 先行处置动作 | `<...>` |
| 处置时间 | `<...>` |
| 事后追认人 | `<姓名>` / `<日期>` |

### 7.2 一个变更一张表

不要把多个互不相关的改动塞进同一张 CR。**判据**：
**若两处改动的"不改的后果"不同，就是两个变更。**

> 合并的唯一后果是：出问题时无法定位是哪次改动引起的。

## 8. 本模板的边界

| 项 | 说明 |
|---|---|
| **性质** | **【本仓库】**——`GB/T 8567-2006` **无"变更请求"这一文档种类**；本模板依 ISO/IEC 29110 的 Change Request 工作产品与本仓库配置管理实践设计 |
| **可裁剪** | A 档可只填 §2 / §3.3 / §4.1 / §5 / §6 —— 但**§3.3 变更理由与 §4.1 影响分析不可省** |
| **不可替代** | 不得替代**框架变更申请**（`FC-`）；框架变更走 R5，流程更重 |
| **与 RTM 的关系** | 本变更若影响需求，**必须回写** `03-需求追溯矩阵.csv`，否则 `tools/trace_matrix.py` 会失败 |

> **实施时请以标准正文为准。** 本模板是结构骨架，不复制标准正文。
