## 4 测试设计技术选择

依据 **GB/T 38634.4-2020** 选择技术。**技术选择必须有理由**，写在表中"选择理由"列。

| 设计技术 | 适用场景 | 不适用场景 | 本项目选择 | 选择理由 |
|---|---|---|---|---|
| **等价类划分** | 输入域可划分为若干"处理逻辑相同"的区间；参数多、组合爆炸需先收敛 | 各输入值处理逻辑互不相同、无法归类的场景 | ☐ 采用 | `<如：金额、数量等连续输入的初步收敛>` |
| **边界值分析** | 存在明确上下限、长度限制、精度要求的输入；**缺陷高发区** | 无明确边界或边界不可知的输入 | ☐ 采用 | `<如：单笔上限 100000.00、字符串长度上限>` |
| **判定表** | 多个条件组合决定不同动作（业务规则矩阵、权限矩阵） | 条件之间无组合关系、纯顺序流程 | ☐ 采用 | `<如：折扣规则由会员等级×金额区间共同决定>` |
| **状态迁移** | 对象有明确状态机（订单、工单、审批流、连接状态） | 无状态或状态不可枚举的处理 | ☐ 采用 | `<如：订单状态 待支付→已支付→已发货→已完成>` |
| **场景法** | 端到端业务流程、跨模块串联、用户真实使用路径（L3/L4 主力技术） | 单函数级白盒验证 | ☐ 采用 | `<如：主流程下单到支付完成全链路>` |
| **错误推测** | 基于经验预判易错点；探索性测试；故障注入的选点 | **不可作为唯一技术**——覆盖率无法度量 | ☐ 采用 | `<如：并发下重复提交、时钟回拨、依赖超时>` |

### 4.1 技术覆盖度检查（GB/T 38634.4-2020 要求基于风险选择）

| 检查项 | 要求 | 本项目情况 |
|---|---|---|
| 黑盒技术覆盖 | 至少覆盖等价类划分 + 边界值分析 + 场景法 | ☐ |
| 白盒技术覆盖 | L1 单元测试须有语句/分支覆盖度量 | ☐ |
| 基于经验的技术 | 可用于补充，**不得作为唯一覆盖依据** | ☐ |
| 技术选择留痕 | 每项技术写明用于哪些测试项与理由 | ☐ |

> **最常见的错误**：全部用例都用"错误推测"设计。这样写出来的用例看着很接地气，
> 但**覆盖率无法计算、无法证明测全了**，在准出评审上必然被退回。

## 5 测试用例标准卡片模板

**这是本仓库强制的用例格式。** 每条用例一张卡片，字段一个不能少。

```markdown
#### <TC-001> <用例标题：测试项 + 条件 + 预期，一句话说清>

| 字段 | 内容 |
|---|---|
| **用例编号** | `<TC-001>` |
| **对应用户需求编号** | `<REQ-F-001>`（多条用逗号分隔；**不得为空**） |
| **测试项** | `<所属测试项编号与名称，如 TI-02 金额校验>` |
| **测试级别** | `L0 骨架冒烟 / L1 单元 / L2 集成 / L3 系统 / L4 验收` |
| **测试类型** | `功能 / 性能 / 并发 / 异常 / 边界 / 恢复 / 安全 / 兼容` |
| **设计技术** | `等价类划分 / 边界值 / 判定表 / 状态迁移 / 场景法 / 错误推测` |
| **质量特性归属** | `<仅验收用例填写：GB/T 25000.51-2016 的 8 特性之一，如 功能性>` |
| **优先级** | `P0 / P1 / P2`（**P0 用例必须每次回归都跑**） |

| **测试步骤** | `1. <动作> 2. <动作> 3. <动作>` |
| **预期结果** | `<具体到文案 / 状态码 / 数据变化 / 日志；禁止写"显示正确">` |
| **实际结果** | `<执行时填写>` |
| **判定** | `<通过 / 不通过 / 阻塞 / 未执行>` |
| **缺陷编号** | `<BUG-001>`（不通过时填写，通过时留空） |
| **执行人 / 执行日期** | `<姓名>` / `<YYYY-MM-DD>` |
| **备注** | `<依赖、风险、复现线索、裁决说明>` |
```

### 5.1 用例设计的四条硬规则

1. **一条用例只验一个判定点。** 一条用例断言五个结果，失败时无法定位原因。
2. **预期结果必须可判定。** 写"提示"是错的，要写"提示『单笔金额不得超过 100000.00』且无订单产生且日志记录 WARN"。
3. **每条用例必须挂到至少一条需求编号。** 挂不上需求的用例要么需求漏了，要么用例多余——两种情况都要处理。
4. **用例必须可独立复现。** 执行者不看代码、不看作者、不看聊天记录，仅凭卡片即可执行。

## 7 测试规程说明

**测试规程**（test procedure）定义用例的**执行顺序与编排**，解决"用例之间有依赖"的问题。

| 规程编号 | 规程名称 | 包含用例（有序） | 前置环境 | 数据重置方式 | 依赖说明 |
|---|---|---|---|---|---|
| `PROC-01` | 主流程冒烟规程 | `<TC-001>` → `<TC-002>` → `<TC-003>` | `ENV-L3` | `reset_orders.py` | 顺序执行，共享登录态 |
| `PROC-02` | 金额校验规程 | `<TC-B-001>` → `<TC-E-001>` | `ENV-L3` | `reset_orders.py --scope=amount` | 用例间**无依赖**，可乱序 |
| `PROC-03` | `<业务流程规程>` | `<TC-001>` → `<TC-002>` | `<环境>` | `<重置方式>` | `<依赖关系>` |

| 规程要素 | 要求 |
|---|---|
| 自动化映射 | 每条规程标注是否已自动化及对应测试标识（如 `pytest tests/test_order.py::test_submit`） |
| 停止条件 | 规程中出现 P0/P1 缺陷时**立即停止后续步骤**，登记缺陷并转阻塞判定 |
| 结果采集 | 自动化执行须留存日志与报告路径；手工执行须留存截图/日志片段 |
| 清理动作 | 规程结束后必须清理测试数据，避免污染后续规程 |

|---|---|---|---|
| `<TC-001>` | `<REQ-F-001>` | ✅ | — |
| `<TC-0xx>` | **（空）** | ❌ | 要么补需求，要么删除用例——**不得保留无源用例** |

### 8.3 覆盖率核算

| 指标 | 计算式 | 目标 | 实际 | 判定 |
|---|---|---|---|---|
| 需求覆盖率 | 有对应用例的需求数 / 已基线需求总数 | **100%** | `<n>%` | ☐ |
| 用例设计完成率 | 已设计用例数 / 计划用例数 | `100%` | `<n>%` | ☐ |
| 四类路径覆盖 | 覆盖正常/边界/异常/空值的测试项数 / 测试项总数 | **100%** | `<n>%` | ☐ |

> 覆盖率由 `python tools/trace_matrix.py` 自动核算，**不采用人工统计**。
> CI 门禁在需求覆盖率 < 100% 时直接失败——这是机器能判的事，不交给人。

## 9 填写指引（常见错误）

1. **预期结果写"显示正确""功能正常"**——这是最致命的填写错误，等于没有预期结果。必须具体到**提示文案、业务码、数据库字段值、日志级别**中的至少两项，否则用例失败时无法判定是产品错了还是用例错了。
2. **测试数据写"若干""一批正常数据"**——测试数据必须写**具体值**。边界用例尤其如此：`100000.00` 与 `100000.01` 是两个完全不同的用例，不能含糊。
3. **用例没有需求编号（或事后补挂）**——需求覆盖率会因此无法达到 100%。**先写需求编号再写用例**，挂不上编号时先解决需求问题，不要先写用例再说。
4. **把多条判定点塞进一条用例**——"提交订单并检查库存、余额、短信、日志"是四条用例。一条用例多个判定点，失败后定位成本成倍增加。
5. **测试项只测正常路径**——正常、边界、异常、**空值**四类必须都有。空值（`null` / 空字符串 / `0` / 空集合）是最常被漏测且最容易崩溃的一类。
6. **用例编号复用**——作废用例的编号不得回收给新用例，否则历史测试报告中的编号将指向错误的用例含义，追溯体系失效。
