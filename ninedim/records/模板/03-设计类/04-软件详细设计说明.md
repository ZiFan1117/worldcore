详细设计**不是一次性写完的文档**，而是随 S4 的模块循环逐步生长的：

```
每个模块的循环（标准动作，不可跳步）：
① 读契约（03-模块接口契约.md）

      → ④ 编码
      → ⑤ 单元测试通过 → ⑥ 模块自测
      → ⑦ 框架适配性回判 ─┬─ 适配 → ⑧ 回写本文件（与代码同一次提交）

```

#### 3.1.7 算法与流程

**算法 A-01：口令校验**

```
输入: account, password
输出: 成功 → SessionToken；失败 → 错误码
步骤:
  1. 入口格式校验（不合法 → AUTH-4001，不写失败计数）
  2. user ← M40.find_user_by_account(account)
  3. IF user 不存在:
       执行一次"假校验"（对固定假 hash 做 bcrypt 比较）
       → 使耗时与真实路径相当，防时序侧信道枚举账号
       → 返回 AUTH-4011（与口令错误同一错误码）
  4. IF user.status == DISABLED → AUTH-4011（不泄露状态）
  5. IF user.lock_until > now → AUTH-4231(retry_after = lock_until - now)
  6. ok ← bcrypt.verify(password, user.password_hash, cost ≥ 10)
  7. IF NOT ok:
       M40.increment_fail_count(user_id)   ← 原子操作
       IF 新计数 ≥ 5: M40.set_lock_until(user_id, now + 15min)
       写审计日志(WARN, account 掩码)
       返回 AUTH-4011 或 AUTH-4231（第 5 次）
  8. M40.reset_fail_count(user_id)
  9. token ← sign_jwt(sub=user_id, exp=now+7200, jti=uuid4())
 10. 写审计日志(INFO)，返回 token
```

**算法 A-02：令牌撤销**

```
输入: jti, user_id
步骤: 1. jti ← 加入撤销集合（TTL = 剩余有效期，避免集合无限增长）
      2. 幂等：重复撤销同一 jti 无副作用，返回成功
```

**主流程逻辑**

```
[登录请求]
    │
    ├─ 格式校验失败 ─────────────────────────→ AUTH-4001
    ▼
[查用户] ──不存在──→ [假校验] ──────────────→ AUTH-4011
    │
    ▼
[已锁定?] ──是──→ AUTH-4231 (+retry_after)
    │否
    ▼
[bcrypt 校验] ──失败──→ [计数+1] ──≥5──→ [锁定 15min] ─→ AUTH-4011/AUTH-4231
    │成功
    ▼
[清零计数] → [签发 JWT] → 200 {token, expires_in, user}
```

> **流程设计要点（必须在评审中说明理由）**
> 1. 格式校验**先于任何 IO**：避免恶意请求打穿到数据库。
> 2. 账号不存在时执行"假校验"：**使响应耗时不泄露账号是否存在**（安全需求 `<REQ-N-013>`）。
> 3. 失败计数用**原子自增**而非"读-改-写"：并发登录下不丢更新。

#### 3.1.8 状态机

> **适用性判定**：本模块存在"账号锁定"这一有明确状态与迁移条件的实体，**适用**。
> 若无状态实体，本节写「不适用」并说明理由（**不允许留空**）。

**实体：账号锁定状态（LockoutState）**

| 状态 | 含义 | 初始态 |
|---|---|---|
| `S01 正常` | `fail_count < 5`，`lock_until` 为空或已过期 | ✅ |
| `S02 锁定` | `lock_until > now` | |

**迁移表**

| 编号 | 起始态 | 事件 | 守卫条件 | 动作 | 目标态 | 副作用 |
|---|---|---|---|---|---|---|
| T-01 | S01 正常 | 认证失败 | `fail_count + 1 < 5` | `fail_count += 1` | S01 正常 | 审计日志 WARN |
| T-02 | S01 正常 | 认证失败 | `fail_count + 1 ≥ 5` | `fail_count += 1`；`lock_until = now + 15min` | S02 锁定 | 审计日志 WARN；锁定通知（可选） |
| T-03 | S01 正常 | 认证成功 | — | `fail_count = 0` | S01 正常 | 签发令牌 |
| T-04 | S02 锁定 | 认证尝试（任意） | `now < lock_until` | 不校验口令 | S02 锁定 | 返回 `AUTH-4231` + `retry_after` |
| T-05 | S02 锁定 | 时间推进 / 认证尝试 | `now ≥ lock_until` | `fail_count = 0`；`lock_until = null` | S01 正常 | 审计日志 INFO |
| T-06 | S02 锁定 | 管理员解锁 | 有权限 | `fail_count = 0`；`lock_until = null` | S01 正常 | 审计日志（**必记**操作人） |

**状态机检查**

| 检查项 | 判据 | 结论 |
|---|---|---|
| 每个状态可达 | 从 S01 可达全部状态 | ☐ |

#### 3.1.10 错误处理

| 错误码 | 触发点 | 处理方式 | 日志级别 | 是否记审计 | 用户可见信息 |
|---|---|---|---|---|---|
| `AUTH-4001` | 入口校验 | 直接返回，**不写失败计数** | WARN | 否 | 账号或口令格式不正确 |
| `AUTH-4011` | 用户不存在 / 口令错误 / 账号禁用 | 统一返回（不区分） | WARN | 是 | 账号或口令错误 |
| `AUTH-4231` | 锁定期间尝试 | 返回 `retry_after` | WARN | 是 | 账号已锁定，请 N 分钟后重试 |
| `AUTH-5001` | `<IF-005>` 超时/熔断 | 重试 1 次后返回 | ERROR | 是 | 服务暂时不可用 |
| `AUTH-5002` | 未预期异常 | 捕获 → 映射 → 记录完整堆栈 | ERROR | 是 | 系统繁忙，请提供 `trace_id` |

**错误处理通则**

| 项 | 约定 |
|---|---|
| 禁止泄露 | 错误信息不得包含：账号是否存在、内部堆栈、SQL、下游地址 |
| 敏感字段 | `password` 在任何日志/异常/追踪中必须掩码为 `******` |
| 兜底 | 所有未映射异常统一转 `AUTH-5002`，堆栈只进日志 |
| 幂等重试 | 仅 `AUTH-5001` 允许重试 ≤ 1 次；其余不重试 |

#### 3.1.11 限制条件与注释设计

| 编号 | 限制条件 | 影响 | 规避方式 |
|---|---|---|---|
| L-01 | bcrypt cost ≥ 10，单次校验约 50–100ms | 高并发下 CPU 密集 | 并发上限与限流；cost 不得为性能而调低（`<REQ-N-013>` 红线） |
| L-02 | JWT 本地验签，无法即时失效 | 注销后令牌在剩余有效期内仍可验签通过 | 撤销集合（`jti` 黑名单）+ TTL = 剩余有效期 |
| L-03 | 依赖 `<M40>` 的原子自增能力 | 若仓储不支持原子操作，锁定策略失效 | 契约中要求原子自增；无则提 `FC-1` |
| L-04 | 时钟依赖 | 锁定判定依赖系统时钟 | 统一 UTC；NTP 同步；允许 ±1s 偏差 |

| 注释要求 | 说明 |
|---|---|
| 必须注释 | 算法 A-01 第 3 步（假校验）的理由——**这是安全设计，不注释会被后人"优化"掉** |
| 必须注释 | 锁定阈值 5 次 / 15 分钟的来源（`<REQ-F-001>`） |
| 禁止注释 | 复述代码本身（`i += 1  # i 加一`） |

## 6 填写指引

1. **最常见错误：一次性把详细设计全写完再编码。** 详细设计的价值是"在编码前暴露算法与状态的坑"。**写一节、编一个模块、测一个模块**，是最省返工的节奏；写完再编只会让文档变成事后追认。
2. **最常见错误：状态机一节留空。** 必须显式回答"适用 / 不适用"。适用时要做可达性、出口与迁移互斥性检查；**每条迁移至少一条单元测试**。不适用时写明理由，不允许空白。
3. **最常见错误：把契约内容抄进详细设计并"顺手扩展"。** 入参/出参/错误码语义以 `03-模块接口契约.md` 为准。契约表达不了实现需要 = `FC-1` 契约不足，**提 R5**，不是在详细设计里私改。
4. **最常见错误：只设计正常路径的单元测试。** 每个模块必须覆盖**正常、边界、异常、空值**四类路径（R4 门禁项），阈值行 ≥ 80%、核心分支 ≥ 90%。只测 happy path 是缺陷重灾区。
5. **最常见错误：改了代码不回写本节。** 代码变更若影响详细设计，**必须在同一次提交里更新本节**（IN-4）；框架变更（R5）后必须回写受影响模块的详细设计（修订类型 `框架变更回写`）。
6. **最常见错误：关键设计决策不写理由。** 例如"账号不存在时做假校验""失败计数用原子自增"——这类反直觉的设计**必须注释理由**，否则会被后人当作冗余代码"优化"掉，直接引入安全漏洞。
