## 零、使用说明（填完全文后请删除本章）

### 0.1 本模板的立场：S2 的框架是**假设**，不是**真理**

概要设计不是"一次设计到位"的成品，而是**第一版可被证伪的假设集**。
因此本模板的准出门禁不看"设计得多完整"，而看三件事：

1. **边界清晰**：模块划分高内聚、低耦合、**无循环依赖**；
2. **契约可执行**：每个模块有明确职责与对外契约（`03-模块接口契约.md`）；
3. **假设显式**：**框架假设清单已成文**，每条假设都有**验证时点**（见 §7）。

> **关键心态**：实现阶段推翻框架**不是失败**，前提是——假设当初被写下来了。
> 没有写下来的假设被推翻，叫返工；写下来的假设被推翻，叫**受控的迭代**（触发条件 FC-3）。

### 2.4 体系结构（结构）

#### 2.4.1 分层与模块编号分带

| 分层 | 模块号区间 | 职责 | 允许依赖 |
|---|---|---|---|
| 表现层 | `M01`–`M19` | 界面、输入校验、视图组装 | 业务层、公共/工具层 |
| 业务层 | `M20`–`M39` | 业务规则、用例编排、事务边界 | 数据访问层、基础设施层、公共/工具层 |
| 数据访问层 | `M40`–`M59` | 持久化、查询、外部数据源适配 | 基础设施层、公共/工具层 |
| 基础设施层 | `M60`–`M79` | 日志、配置、认证、MQ、缓存等技术能力 | 公共/工具层 |
| 公共/工具层 | `M80`–`M99` | 无业务语义的通用能力（日期、字符串、校验） | **不得依赖任何其他层** |

> **依赖规则铁律**：**只允许上层依赖下层，禁止反向依赖，禁止跨层跳跃（表现层不得直连数据访问层）。**
> 完整编号规则与登记表见 `02-模块清单与模块号登记表.md`。

#### 2.4.2 模块依赖图

```
        ┌──────────────┐        ┌──────────────┐
        │   M01 表现层  │        │   M02 表现层  │
        └──────┬───────┘        └──────┬───────┘
               │                       │
               └───────────┬───────────┘
                           ▼
                   ┌───────────────┐
                   │  M20 业务层    │
                   └───┬───────┬───┘
                       │       │
          ┌────────────▼─┐   ┌─▼──────────────┐
          │ M40 数据访问  │   │ M60 基础设施    │
          └──────────────┘   └────────────────┘
                       │       │
                       └───┬───┘
                           ▼
                   ┌───────────────┐
                   │ M80 公共/工具  │
                   └───────────────┘
```

| 检查项 | 判据 | 结论 |
|---|---|---|
| 是否存在循环依赖 | 依赖图必须为有向无环图（DAG） | ☐ 无环 |
| 是否存在跨层跳跃 | 表现层 → 数据访问层 直连数 = 0 | ☐ 0 |
| 是否存在反向依赖 | 下层调用上层次数 = 0 | ☐ 0 |
| 校验方式 | `python skeleton/run_skeleton.py` 的依赖拓扑检查 / CI 门禁 | ☐ 通过 |

## 7 框架假设清单【本仓库定制章节 · S2 准出必填】

> 这是 S2 最容易被忽略、但对后续迭代**最关键**的一份**活文档**。
> 它是"框架—模块共演化"的输入：假设被推翻 → 触发框架变更（`FC-3`）→ 有据可依、范围可控。

| 假设编号 | 假设内容 | 置信度 | 若不成立的后果 | 验证时点 | 状态 |
|---|---|---|---|---|---|
| `A-01` | 上游数据源提供稳定的同步 HTTP 接口 | 中 | 需引入异步补偿机制，影响全部 IO 模块 | `<M02>` 实现时 | ⏳ 待验证 |
| `A-02` | 单机部署即可满足 200 并发，无需分布式锁 | 高 | 需引入协调服务，框架层大改 | S5 压测时 | ⏳ 待验证 |
| `A-03` | 单租户任务数据 < 100 万行，现有索引可满足 P95 ≤ 2s | 低 | 需改流式/分页处理，`<M40>` 与 `<IF-003>` 契约需扩展 | `<M04>` 实现时 | ❌ 已推翻 → 触发 `FC-1` |
| `A-04` | 全部业务事务为单库本地事务 | 高 | 需引入分布式事务，`<M20>` 事务边界重划 | S3 骨架时 | ✅ 已验证 |

**置信度**：高 = 有直接证据；中 = 有间接证据/经验；低 = 纯推测。
**状态**：✅ 已验证 / ⏳ 待验证 / ❌ 已推翻（推翻时必须提 `FC-3` 框架变更）。

### 7.1 硬规则

> **每个假设都必须有「验证时点」。没有验证时点的假设 = 定时炸弹。**
>
> 定时炸弹的典型爆炸方式：到 S5 集成测试时才发现假设不成立，此时已有 N 个模块建立在错误前提上，
> 改造成本 = 受影响模块数 × 单模块改造成本 + 回归成本，且往往已经逼近交付期。

| 检查项 | 判据 | 结论 |
|---|---|---|
| 每条假设是否有验证时点 | 100% 有（时点须具体到模块或阶段，禁止写"以后"） | ☐ |
| 每条假设是否有置信度 | 100% 有 | ☐ |
| 已推翻的假设是否已提 `FC-3` | 100% 已提 | ☐ |
| 假设是否有责任人 | 100% 有 | ☐ |

### 7.2 假设与框架版本的联动

| 假设状态变化 | 必须执行的动作 | 责任人 |
|---|---|---|
| 验证通过 | 更新状态为 ✅，在 §0.4 修订记录登记 | 实现者 |
| 验证失败 | 提 `FC-3` 框架变更（R5）→ 更新本表 + 更新 §2.4 结构 + 更新模块契约 → 框架版本 `vN+1` | 实现者 + 架构师 |
| 新增假设 | 立即登记（含验证时点），不积压 | 架构师 |

## 9 填写指引

1. **最常见错误：S2 想一次设计到位。** 大设计先行（反模式）会让 S2 停留数周，而抽象基于想象，实现一碰就碎。**S2 只定边界与契约，细节留到 S4 详细设计。**
2. **最常见错误：框架假设清单不写或写了没有验证时点。** 这是本仓库最看重的一节。没有假设清单，框架变更就变成"说不清为什么改"的返工；没有验证时点的假设就是定时炸弹。
3. **最常见错误：模块划分靠感觉，出现循环依赖或跨层直连。** 依赖图必须是有向无环图，表现层不得直连数据访问层。**R2 门禁对循环依赖一票否决**，且 CI 会自动检查。
4. **最常见错误：选了架构风格但不写理由，也不写被否决的方案。** "因为流行/因为大家都用"不是理由。必须写清选型理由与被否决方案，否则评审无法判定决策质量。
5. **最常见错误：接口定义只写成功路径。** 本文档只做接口设计侧约束，完整的错误码/幂等/超时/版本兼容在 `../02-需求类/02-接口需求规格说明.md` 与 `03-模块接口契约.md`；**三处的接口编号必须一一对应**。
6. **最常见错误：改了框架不改 HLD。** 每次 R5 批准的框架变更，必须在**同一次提交**里更新本文档、模块契约与 RTM。文档滞后提交数为 0 是健康度指标（见 `docs/01-流程与阶段/框架与模块共演化.md` §八）。
7. **最常见错误：只画架构图，不写"回应了谁的什么担心"。** §8 是 2025 新标准（GB/T 45630-2025 ≡ ISO/IEC/IEEE 42010:2022）的核心要求——**架构描述必须回应利益相关方的关注点**。只画分层图、列不出关注点，在 R2 会被判为不合格。**§8.4 的覆盖度检查有孤儿项（关注点无视角 / 视角无关注点）即一票否决。**
