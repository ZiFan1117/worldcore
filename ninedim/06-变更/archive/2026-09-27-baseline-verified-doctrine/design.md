# Design

## Context

见 `proposal.md` 的 Why。这里只写塑造了做法的现状与约束。

**证据环境是分裂的，这一点决定了规格的写法。** 主机 `D:\Code\08-worldcore-openspec` 是 git 仓库、
是编辑与门禁脚本所在；但它**没有 Rust 工具链**，`cargo` / `rustc` 都不在 PATH，`target`
不存在。真正的构建与验收只在 Linux VM 内进行：`ssh world`（VirtualBox Arch Linux，
内核 `7.2.6-arch2-1`，cargo 1.98.1），工作区 `/root/world/world-core`。

**VM 的工作树不是 git 仓库。** 真仓库是 `/root/world.git`（bare），VM 侧身份用
`GIT_DIR=/root/world.git GIT_WORK_TREE=/root/world` 自证。核查时发现 VM 有 4 个文件处于
未提交状态（`src/main.rs`、`scripts/test/cli.rs`、`src/carrier/mod.rs`、`2-依据/15-…md`）；
逐文件 sha256 比对确认：这 7 个关键文件与主机副本**逐字节相同**，即 VM 是"旧提交 + 本地回填，
回填后恰好等于主机 HEAD `61c95b0` 的内容"。⇒ 证据资格成立，不必再同步。

**这本书与这个实物的关系是"学说 vs 标本"。** 书第五章自评 16 行判据里 10 行红，
但 `bash check.sh` 在 VM 内全绿。两者不矛盾：`check.sh` 测的是"造出来的东西守不守它自己的规矩"，
书判的是"这一层能力有没有"。本基线固化的是**前者**。

## Goals / Non-Goals

**Goals:**

- 把"这台世界核心今天真的承诺什么"变成可验收、可追踪、机器可检查的规格。
- 每一条 Scenario 都能指到**一个具体测试函数**，而不是一句"应当通过"。
- 把已知的边界与残余风险写进规格本体（例：无密钥摘要链挡不住整本重写），
  使"这个机制有效"与"这个机制的极限在哪"两句话同时成立。

**Non-Goals:**

- 不把书里"应当是什么样"但今天没做到的部分写进规格（那是 L5 兑现，不是基线）。
- 不替人裁定任何待人裁项（清单见下）。
- 不修改 `` 下任何产品代码、测试或既有文档；本 change 只产出文本。

## Decisions

### 决策 1：按"对外可观察的能力"切分，不按书的章节或代码模块切分

规格分为 6 条能力：`ledger-integrity` / `envelope-validation` / `gate-enforcement` /
`read-model` / `projections` / `channel-identity`。

**为什么不用书的六章**：书的章节是**叙述层**（L1 问题 / L2 规格 / L3 命题 / L4 机制 /
L5 兑现 / L6 未定），其中只有 L2 与 L4 能落成能力规格，L5 与 L6 按定义**不进**基线。
按章节切会把"未定"混进"已定"。

**为什么不用代码模块**：规格是行为契约，不是实现计划。`src/` 里的 `carrier/` 有 7 个文件，
但对外只体现一件事（身份与执行清单），按模块切会让规格随重构失效。

**备选方案**：一条大规格（"语义世界"）——被否，因为 `openspec validate` 的 Requirement
粒度会退化，且无法按能力追踪变更。

### 决策 2：每条 Scenario 末尾挂 `证据：` 行，指向测试函数名

OpenSpec 的 Scenario 语法是 `WHEN` / `THEN`，没有"证据出处"这一格。本基线在 THEN 之后
加一行 `- **证据**：<路径>::<测试函数名>`。

**为什么**：这个项目的既有文化就是"每个判据都要能回源"（序第 62 行："我们只要求：等你看到
那条记录时，你能自己去核"）。规格若只说"应当如何"而指不到会红的断言，就退化成了文档。

**代价**：这不是 OpenSpec 的标准字段，`openspec validate` 不校验它，可能随时间失效。
**缓解**：把"证据行是否仍指向存在的测试"列为 `tasks.md` 里的一条维护任务。

### 决策 3：把"边界"写成 Requirement，而不是写成注意事项

`c18_chain_cannot_detect_a_full_rewrite` 断言的是"整本重写**检不出**"，且测试注释明说
"这条测试的存在本身是设计的一部分"。本基线把它写成一条 Scenario（"整本重写按设计检不出"），
与"局部篡改必须被检出"并列。

**为什么**：如果只写"链能检出篡改"，规格就成了一句会误导人的话——下游会以为它是防篡改机制。
**一个只证明自己有效的机制，不如一个同时证明自己边界在哪里的机制。** 这也与书第五章
"上限先放在最前面"的写法一致。

### 决策 4：验证走 VM，且一次只跑 `check.sh`

所有 Scenario 的验证命令统一为：

```
ssh world "cd /root/world/world-core && bash check.sh"
```

需要单条取证时用 `cargo test --locked --test <file> <name> -- --nocapture`。

**为什么不用主机**：主机无 Rust 工具链；且项目自己的度量规则要求"所有度量必须在真 VM 中执行，
并把命令、版本号、原始输出归档"（`WC-SQAP-001` §2.1.2）。

**已知代价**：`check.sh` 单次约 4 秒，但**依赖 VM 在线**。VM 不在时基线无法复验——
这条依赖本身登记为本 change 的风险。

## Risks / Trade-offs

- **规格可能"冻结"未定的东西** → 缓解：`Non-Goals` 与下方排除清单逐项点名；
  凡书中标注"待人裁"的条目一律不写进 Requirement。
- **证据行会陈旧**（测试改名、`check.sh` 步骤号变动）→ 缓解：列为维护任务；
  改测试名时同步改规格，纳入今后每个 change 的检查清单。
- **VM 是单点**：VM 不在线则基线不可复验 → 缓解：如实登记；不假装主机能代替。
- **本基线不含"必要性"** → 这是最大的一条风险：书里"最重的一条"（G-X）尚未裁定，
  即有"这一层到底需不需要存在"尚未论证完毕。基线固化的是**已经成立的行为**，
  **不构成对必要性的论证**。规格不得被引用为"必要性已证"。
- **`dsh-openspec` 插件在 Windows 上工具全废**（`spawn` 不解析 `PATHEXT`）→ 本 change 只用 CLI，
  不受影响；缺陷另行登记。

## Migration Plan

本 change 只新增文本，不动运行中的系统。落地步骤：

1. 写完 6 份 delta；`openspec validate` 通过。
2. 在 VM 内跑一次 `bash check.sh`，确认所有 `证据：` 行指向的测试**仍然存在且仍会通过**。
3. 归档（archive）本 change，delta 合并为 `ninedim/01-意图环/04-规格/` 下的主规格。

**回滚**：删除 `ninedim/01-意图环/04-规格/` 下 6 个目录与本 change 目录即可；不涉及产品代码。

## Open Questions

- `证据：` 行这个非标准字段，长期是留在 spec 里，还是改为 `design.md` 的一份对照表？
  两种都能答"这条判据从哪来"，前者离判据近、后者不污染规格语法。**可延后决定，不影响本次范围。**
