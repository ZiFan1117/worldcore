# 说明：**映射表是什么** —— 就是一个文件（2026-10-17）

> ★ **作者问（逐字）**：「**两者由一张表连着 映射表是什么**」。
> ★ **一句答**：★★ **映射表就是一个文件**：★ `crates/aios-ontology/data/command-map.jsonl`（★ **2018 字节／11 行**）★ —— ★ **一行一条，写明「世界里的名字 ↔ 底下那条命令」**。

---

## §一 ★★★ 它长什么样（★ 逐字 · 第 3 行）

```json
{"action":"service.start","function":"fn.service.start","registered_by":"builtin-commands","registered_by_kind":"system","required_roles":["human"],"program":"systemctl","args":["start"]}
```

| 格 | 值 | ★ 它在说 |
|---|---|---|
| `action` | `service.start` | ★★ **世界里的名字**（★ 左边） |
| `program` ＋ `args` | `systemctl` ＋ `["start"]` | ★★ **底下那条命令**（★ 右边） |
| `function` | `fn.service.start` | ★ 它对应的函数入口名（★ 本体那一格） |
| `registered_by` ／ `registered_by_kind` | `builtin-commands` ／ `system` | ★ 谁注册的、哪一类（★ 三方同构那一格） |
| `required_roles` | `["human"]` | ★ 谁能用（★ **声明**，★ 判定仍在门） |

★ 文件格式叫 **`.jsonl`**（★ JSON Lines）＝ ★ **一行一条 JSON**（★ 不是一个大 JSON 数组）★ ⇒ ★ 追加写、逐行读、坏一行看得见。

## §三 ★★★ 两个时点（★ 这张表在两个时候被用）

```
★ 启动时（注册）：
   读映射表 ⇒ 逐条 register ⇒ 注册表（落盘）⇒ 在册表 ＝ 本体 9 条 ＋ 注册表 11 条 ＝ 20 个动作

★ 有人报一个名字时（执行）：
   报 fs.list ⇒ 门：在册 ✓ ／ 身份 ✓ ／ 权利（human,agent）✓
              ⇒ 执行器查表 ⇒ program=ls, args=[-l] ⇒ 起 ls -l ⇒ 回结果 ⇒ 落账
```

★ 这整条**刚在 VM 上真跑过**（T-250）：★ `[注册] 映射表 11 条已登记`／★ `[在册] 本体 9 条 ＋ 注册表 ⇒ 合计 20 个动作`／★ `[跑] fs.list ⇒ ls ["-l"]`／★ `[成] 输出 3085 字节` ✓

## §四 ★★★ 最容易混的一点：**映射表 ≠ 注册表**（★ 两张表分工不同）

| | ★★ **映射表**（源头） | ★★ **注册表**（在册） |
|---|---|---|
| 路径 | ★ `crates/aios-ontology/data/command-map.jsonl` | ★ `/root/bus/registry.jsonl`（★ 运行时那份） |
| 谁写 | ★★ **我们（人）写的** —— 替底下的工具写的一张**对照单** | ★★ **运行时落盘的登记结果**（★ `register_from_map` 灌进去；★ 软件也可以**自己注册**） |
| 一行有什么 | ★ 那五格 ＋ **`program`／`args`** | ★ 那五格 ＋ `alive` ⇒ ★★ **【没有】`program`／`args`** |
| 行数（现取） | ★ **11** | ★ **11** |
| 它回答什么 | ★ 「**这个名字对应哪条命令**」 | ★ 「**在册吗／活着吗**」 |

### ★★★ 现取对照（★ 同一个动作，两张表各一行）

```
映射表（有命令）：
{"action":"fs.list","function":"fn.fs.list","registered_by":"builtin-commands","registered_by_kind":"system","required_roles":["human","agent"],"program":"ls","args":["-l"]}

注册表（没有命令）：
{"action":"fs.list","function":"fn.fs.list","registered_by":"builtin-commands","registered_by_kind":"system","required_roles":["human","agent"],"alive":true}
```

★★★ **这两行的差别就是那条边界**：★ **命令名（`ls`）只出现在映射表里；★ 「在册那一份」里一个字都没有** ✓
★ 出处：★ `Register::register` 收的是 `CommandRoute::as_registration()` ★ —— ★ 那个函数**只搬那五格**（★ 有测试逐字钉住：★ `the_command_literal_stays_out_of_the_registration`）。

## §五 ★★ 为什么要有这张表（★ 为什么不直接把这些写进本体）

| 若写进本体 | ★ 后果 |
|---|---|
| ★ 本体里出现 `pacman`／`systemctl` 这类字面量 | ★ **判据 C14／C22 当场红** —— ★ 理由逐字：「★ 等于让本体长出**第二份**可执行事实」 |
| ★ 本体里出现 `program`／`args` | ★★ 那**实现就住进了本体** ⇒ ★ 与「**代码不进本体**」相抵 |

⇒ ★★ **所以**：★ **名字进本体（其实是进注册那一层）／命令留在映射表** ★ —— ★ 表就是**「实现那一层」的落点**。

## §六 ★ 本件不能证明的事（如实）

- ★ **两张表的路径与行数是现取**（★ 2018 字节／11 行；★ VM 上 `/root/bus/registry.jsonl` 11 行）；
- ★ **「启动时读表」**：★ 今天**由那支 `run_action`／`project_frame` 手动调**，★ **还没有一个常驻进程**在启动时做它 ⇒ ★ 那是**下一步**；
- ★ **映射表里没有「动作自己的可填参数」那一格**（★ 如 `service.start` 需要「哪个服务」）—— ★ 那是**已登记的缺口**（T-251）；
- ★ 本件**没改代码、没改本体**（★ 只有档案）⇒ ★ 门禁 **C1–C24 全绿**。
