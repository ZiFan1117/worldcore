# 设计提案：**本体做「最高权限」—— 两层本体**

> **状态：提案（待人裁）。★ 一行代码未写。**
> ★ 作者问（逐字）：「我想把本体就像咱们的系统一样做成**最高权限**……你比如说是 Windows 系统，你这个能不能干，**有没有管理员权限，一申请就会有相应的反应**，这个怎么才能办到呢？是**需要软件在开发的时候就接入我这块**吗？还是怎么回事」
> ★ 追问（逐字）：「**那我们能不能把本体做在这里面呢**」（★ 「这里」＝ 内核里的 LSM 插槽）

---

## 一、★★★★★ 结论先行（三句话）

| # | ★ 结论 |
|---|---|
| **1** | ★★ **「最高权限」只有【OS 层】做得到 —— ★ 应用层只能【约定】，★ 拦不住不接入的程序。** |
| **2** | ★★★ **本体【不能】整个搬进内核** ★ —— ★ 内核里跑不了 Python、不能阻塞、不能记账。 |
| **3** | ★★★ **但【能把本体的「规则」编进内核】** ★ —— ★ 内核里放一份【影子】，★ 用户态本体【更新它】。 |

> ★★★ **一句话：本体不是【守门人】，是【立法机关】。★ 守门的是内核。**

## 三、★★★★★ 为什么【不能】把本体整个搬进内核 —— 三个硬原因

### 原因一：★ 本体【是用户态进程】，★ 内核【先于它】看到一切

```
★ 程序 open("/etc/shadow")
★   ⇒ 【内核】判 ⇒ 拒
★        ↑
★      ★ 本体【没机会】
```

### 原因二：★ 本体【会挂】，内核不会

| ★ 对照 | ★ SELinux | ★★ 本体 |
|---|---|---|
| ★ 在哪 | ★ **内核里** | ★★ **用户态进程** |
| ★ 挂了 | ★★ **不会单独挂** | ★★ **进程挂了 ⇒ 保护就没了** ✗ |

### 原因三：★ 本体【做不了内核里的三件事】

| ★ 本体要做的 | ★ 内核里能做吗 |
|---|---|
| ★ 判「这是不是同一件事」（语义） | ★★ **不能** ✗ |
| ★ **转**（把请求给别人） | ★★ **不能** —— 内核不能等网络 ✗ |
| ★ **记账**（写文件） | ★★ **不能** —— 会死锁 ⚠ |
| ★ **跑 Python** | ★★★ **更不能** ✗ |
| ★★ **「这个操作许不许」** | ★★ **能** ✓ ★ —— **这才是内核该做的** |

## 四、★★★★★ 所以的架构：【两层本体】

```
★ ┌─ 内核（OS 层）
★ │   ★【本体的影子】
★ │     = 一份编译好的规则表（★ BPF map / LSM 策略）
★ │     = ★ 只答「这个操作许不许」
★ │     = ★ 微秒级、★ 拦得住一切、★ 拦得住不接入的程序
★ │
★ ├─ 用户态
★ │   ★【真正的本体】
★ │     = 判语义 ＋ 转 ＋ 记账 ＋ 改规则
★ │     = ★ 它【更新】内核里那份表
★ │
★ └─ 应用
```

★★★ **⇒ 这不是新发明 —— 现成的两个例子**：

| ★ 系统 | ★ 用户态（定规则） | ★ 内核（执行） |
|---|---|---|
| ★★ **SELinux** | ★ `semodule` 装策略 | ★ 内核 LSM 执行 |
| ★★ **systemd** | ★ 单元文件 | ★ cgroup／LSM 执行 |
| ★★★ **我们（如果做）** | ★★ **本体** | ★★ **BPF LSM** |

## 五、★★★★ 落地路径：**两步，先易后难**

### 第一步：★ 用户态本体当【决策者】，各机制当【执行者】（★ 小）

| # | ★ 让本体生成什么 | ★ 谁执行 | ★ 能管住什么 |
|---|---|---|---|
| **1** | ★★ **polkit policy**（★ 现在 25 个 action 那套） | ★ polkit | ★★ **「一申请就弹窗」** ✓ |
| **2** | ★★ **zenoh ACL** | ★ `zenohd` | ★★ **总线通路**（★ 谁能发/订哪些 key） |
| **3** | ★★ **systemd 沙箱开关** | ★ systemd | ★★ **进程能看哪些文件、能开哪些 socket** |
| **4** | ★ **单元文件** | ★ systemd | ★ 起停与依赖 |

★★ **★ 局限**：★ 管不住【不走这些机制】的程序 ⚠

### 第二步：★ BPF LSM 影子（★ 大）

| ★ 做什么 | ★ 说明 |
|---|---|
| ★★ **写一个 BPF LSM 程序** | ★ 挂钩 `file_open`／`socket_connect` 等 |
| ★★ **规则表放 BPF map** | ★ 本体【运行时更新 map】⇒ ★ **不用重启** ✓ |
| ★★★ **拦得住一切** | ★ 包括【不知道本体存在】的老程序 ✓ |

## 六、★★★★★ 代价与风险（★ 必须先想清）

| # | ★ 代价 | ★ 严重度 |
|---|---|---|
| **1** | ★★★ **内核里不能犯错** ★ —— 一个 bug ⇒ 整个系统崩 | ★★★ 最高 |
| **2** | ★★★ **策略更新** | ★ ACL 现取的限制是「**cannot be updated at runtime**」★ —— ★ BPF map 好些，但要设计 |
| **3** | ★★★ **内核里没有 Python** ★ —— 本体要么用 C/Rust 重写，★ 要么只编成规则表 | ★★ 高 |
| **4** | ★★ **调试极难** | ★ 内核 panic 没有 Python traceback ⚠ |
| **5** | ★★ **可移植性差** | ★ BPF LSM 要求内核 ≥ 5.7 ＋ 开 `CONFIG_BPF_LSM` |
