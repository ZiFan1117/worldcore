## §一 ★★ 08 是怎么做的：**它本来就不分门别类**（现取）

### §一·1 五条贯穿纪律（`08/src/lib.rs:12-17` 逐字）

1. ★ **一个进程**（本体／账本／读模型／运行时／门禁**同进程**）；
2. ★ **一个写入口**（只有 `World::commit` 能改世界）；
3. ★ **法律在前、落笔在后**（校验不过就绝不写账本）；
4. ★ **状态是算出来的**（`state = fold(events[0..seq])`，**派生物、可随时重算**）；
5. ★ **门禁不可绕过**（决策在唯一咽喉 ＋ 规则与真相不受被管者写入）。

### §一·2 模块是**按「职责」分的，不是按「执行种类」分的**（`lib.rs:4-8` 逐字）

| 模块 | 它是谁 |
|---|---|
| `ontology` | ★ **法律**：一条事件长什么样、什么算合法变更 |
| `ledger` | ★ **事实**：只追加的语义事件账本 |
| `readmodel` | ★ **状态**：派生物、可随时重算 |
| `gate` | ★ **门禁**：一件事现在能不能做（默认拒 ＋ 按不可逆性加摩擦） |
| `guard` | ★ **静态防线**：法律与真相的存放处**不得对被管者开放写权限** |

★ 注意：**这五样里一个「执行种类」都没有** —— ★ **没有**「进程内/子进程/沙箱」那套分发枚举，★ **没有**「IO 模式／稳定度／队列类」那套分类。

### §一·3 ★★★ 你说的「翻译器」，在 08 里就是**载体那一层**（`carrier/`）

| 件 | 它自己怎么说的（逐字） |
|---|---|
| `carrier/mod.rs` | 载体适配器（`M10`）—— ★「**载体侧的手：只执行、不裁决**」 |
| `carrier/providers/mod.rs:1` | ★★「内置执行器 —— **只有这些事需要碰到载体**，所以只有这些事在这里」⇒ ★ **只有 3 个**：`backlight`／`package`／`job` |
| `carrier/provider.rs:5-6` | ★「契约只有三个词：**入参无歧义、返回结构化、失败类型化**。不允许『调一条命令、从人话里猜结果』」 |
| `carrier/provider.rs:12` | ★ 执行器**不能裁决**（允不允许问门禁）、**不能写账本**（只能请求内核追加）；★「执行器**不持有身份**：它写的每一条结果都由内核按连接给出身份，请求体里没有任何地方可以自称」 |
| `carrier/translate.rs:1` | ★「**外部变化 → 世界消息**——前值必须带上；**翻不出来就报错，不许猜**」 |
| `carrier/run.rs:1` | ★「适配器的运行形态 —— **先问、再做、再报**（顺序不可交换）」 |
| `carrier/capd/mod.rs:1` | ★「执行清单（`cap.d`）的解析 —— **声明是怎么干的，不是允不允许**」 |

### §一·4 ★★★ 最关键的一格：**两栏词表**（`carrier/providers/mod.rs:11-18` 逐字）

> 「[`Provider::name`] 是**实现词／设备词**（`backlight`／`package`／`job`）——回答「**怎么实现**」；
> [`Provider::capabilities`] 是**语义层的名字**（`notice.mute`／`ledger.compact`／`job.start`）——回答「**叫什么**」，与本体 `_interfaces`、`cap.d` 的 `capability` **同一套词表**。
> 这两栏一旦混用，`cap.d` 与执行器就会**各有一个合法名字、却对不上**。」

★★★ **这就是你说的那个「翻译器」**：★ **一侧是实现词（今天底层的世界），一侧是语义名（我们本体在册的名字）**；★ **它是一张对照表，不是一套分类学**。

### §一·5 结论：**08 走的是「一条链 ＋ 一张对照表」**

```
语义事件（唯一真相） → 本体（法律） → 门禁（唯一硬分界） → World::commit（唯一写入口）
                                                              │
                                                              ▼
                                        载体（carrier）＝ 那只「手」：只执行、不裁决
                                                              │
                              ┌───────────────┼───────────────┐
                         backlight         package           job        ← ★ 只有 3 个：
                         （实现词）        （实现词）        （实现词）      只有这些事要碰载体
                              └──── 两栏词表：实现词 ↔ 语义名（notice.mute／ledger.compact／job.start）
```

## §二 那上游为什么要分门别类？（★ 不是「错」，是**位置不同**）

| 它分出来的类（现取） | 它为什么必须分 |
|---|---|
| `ActionDispatchKind` **4 档**（进程内／子进程／隔离沙箱／干跑） | ★ 它要**逐档管控「动作跑在哪」**——AI 发起的强制进沙箱 |
| `AdapterIOMode` **2 档**（类型化参数／类型化模板） | ★ 它要**堵住「自由形式 shell」**（逐字：shell 命令**不是一个取值**） |
| `AdapterStability` **5 档**（登记/实验/稳定/弃用/退役） | ★ 它要管**适配器的生命周期与信任** |
| `QueueClass` **4 档**（人/AI/后台/恢复） | ★ 它要**给 AI 限流**（AI 只进 `AGENT_PROPOSAL`，封顶 50%） |
| `TerminalMode` **3 档**（Lx／Mix／Ai） | ★ 它要**分清「人打的 shell」与「AI 的意图」** |

★★ **一句话**：★ **上游站的位置是「怎么把动作安全地执行下去」** —— ★ 它**要把每一条执行路径都变成可管控、可审计的闭集**，所以它**必须**分门别类。

★★★ **它为什么必须靠分类兜底？** ★ 因为**它没有一层能判「这件事合不合法」**：
· ★ 它的动作名是**提示词里的自由字符串**（`translator_system_prompt.txt`）；
· ★ 上一会话实测：`TBox`／`ABox`／`ontology`／`RDF`／`OWL` **全 0**；★ 它自己的 `L7.2` 写着「This spec is purely structural」；
· ★ 所以它只能**按种类加摩擦**（哪一类走哪个队列、哪一类强制沙箱、哪一类要审批）—— ★ **那是「按形状防」，不是「按语义判」**。

★ **而我们的位置是「这件事凭什么算数」** —— ★ 见同盒 `说明-本体空间的意义与相对AIOS的位置.md` 逐字：「**AIOS 有「语义」这个词，没有「语义」这一层**」。★ **有那一层，就不必按种类防**：★ **不在册的，连门都进不来**（已实测：不在册的动作连总线上不去）。
