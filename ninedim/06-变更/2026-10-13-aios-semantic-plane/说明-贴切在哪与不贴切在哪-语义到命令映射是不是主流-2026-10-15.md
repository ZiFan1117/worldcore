# 说明：**贴切在哪、不贴切在哪** —— 「语义 → 命令行映射」是不是现在的主流（2026-10-15）

> ★ **作者问（逐字）**：「**他们贴切的地方是在哪里呢？我们是做一个羽翼（＝语义）到一个命令行的一个映射，现在他们做的都是这样吗**」。
> ★ **一句话答**：★ **贴切处在「两栏表 ＋ 出闸前校验 ＋ 受信侧构造命令 ＋ 审计链」四处**；★ **不贴切处在「表住在哪」**；★ 而「语义 → 命令文本」的映射 ★★ **恰恰不是主流 —— 那正是 SysKnife 用 GuardFall 的实测否掉的那条路**。
> ★ 本件是**读数件**：外部逐字带 URL；★ 行业对照一节**是 SysKnife 自己的说法**（厂商自述，★ 不等于本席核实过那些竞品）。

## §二 ★ 不贴切的地方（逐条 · 这才是要紧的）

| # | 不贴切 | 说明 |
|---|---|---|
| **1** | ★★ **它管的是 Linux 系统管理，不是「世界里什么算数」** | 它装包／起服务／改内核参数（`rpm-ostree`／`apt`／`systemctl`）；★ 它**没有「世界本体」** |
| **2** | ★★ **它的表住在它自己的代码里** | `KNOWN_ACTIONS` 是 **brain crate 的源码常量**、`ActionSpec.mechanism` 在 **daemon 里**；★ 我们的表要**住在本体**（可导出、住在所有参与者之下） |
| **3** | ★ **它没有「分级」这一维** | 它有 `risk`（低中高，讲**危险度**），★ **没有 privacy／marking／天花板**（那是我们 H08 那一层） |
| **4** | ★ **它没有「词表身份」** | 没有「词表对不上即拒」这种跨参与者的一致性号（我们 08 有 `vocab_hash` 那一格） |
| **5** | ★ **它没有「底层也语义化」的位置** | 它是「AI → 系统」的**一次性翻译**；★ 没有「将来底层自己也说语义」那条路（★ 你说的**阶段性**它没有） |

## §三 ★★★ 「现在他们做的都是这样吗？」——它自己的**行业对照表**（逐字抄，见 [comparison](https://lacs-project.github.io/sysknife/comparison.html)）

| | generic mcp-shell ／ mcp-firewall | AIShell-Gate | gate-oc-audit | MCP traffic gateways | **SysKnife** |
|---|---|---|---|---|---|
| **AI 产出什么** | **shell 字符串**（白名单） | **typed JSON commands** | 什么都不产出（只观察） | **代理转发 MCP 调用** | **typed semantic actions** |
| **在宿主上拦不拦执行** | 策略过滤 | 拦 | 不拦（只劝告） | 在代理处、不在宿主 | ★ **拦 —— 服务端强制互锁** |
| **审计方案** | 日志 | HMAC-SHA256（对称） | Merkle 树 ＋ 可选锚 | 日志／不可变轨迹 | ★ **Ed25519（非对称）** |
| **第三方可验** | 否 | 否（验证者握密钥） | 经外部网络 | 视情况 | ★ **可 —— 只需公钥** |
| **自动回滚** | 无 | 无 | 无 | 无 | ★ **有（rpm-ostree）** |

★ 它自己的总结（逐字）：「**most tools either filter shell strings or watch after the fact. SysKnife removes the shell string entirely, gates execution with a hard interlock, and produces an audit trail anyone can verify with a public key.**」

### §三·1 ★ 所以回答你的问题：**不是「都在做语义 → 命令行的映射」**

| 档 | 谁在做 | 做法 |
|---|---|---|
| ★ **主流一：过滤 shell 字符串** | `mcp-shell`／`mcp-firewall`／MCP 流量网关那一类 | ★ 让模型**产出命令**，再拿白名单／正则去挡 —— ★ **这就是「语义 → 命令行」那条路，而且是它被证明会被绕过的那条** |
| ★ **主流二：事后观察** | `gate-oc-audit` 一类（observe-only） | ★ 不拦，只记 |
| ★★ **少数派（含 SysKnife）** | SysKnife／AIShell-Gate | ★ **类型化动作**：模型**只见动作名**，命令**在受信侧构造** |

★★★ **结论**：★ **「语义 → 命令文本」的映射不是主流，是被否掉的那条路**；★ **「语义名 → 实现（命令）」的映射是主流做法，但它只在受信侧发生、且判据盯着**。
★ 两句话别混：★ **「谁翻译」**（受信侧翻，不是模型翻）与 ★ **「翻什么」**（名字 → 实现，不是语义 → 命令文本）。

## §四 ★ 对我们的三点含义（建议 · 待人裁）

| # | 含义 |
|---|---|
| **1** | ★★ **映射表的两栏要写死**：左＝**本体在册的语义名**；右＝**实现（命令／设备／包管理器）**；★ **右栏永不交给模型** |
| **2** | ★★ **表要有判据盯着不许漂移**（★ 它用「生成 ＋ cargo test 一漂就红」；★ 我们 08 用 `cross_check`）——★ 这条**两家撞车**，值得照做 |
| **3** | ★ **它多一格我们没有的：`preview`（执行前看到确切命令）**；★ 它少一格我们有的：**分级／天花板**。⇒ ★ 建议：`preview` 这一格**补进 `cap.d`**（我们有 `confirm`，但没有「给人看确切命令」这一栏） |

★ 另两条**对照出来的事实**（不是建议）：★ 它**没签名我们也没**（H11 依裁决不做）⇒ ★ 「公钥可验」这条**今天两家都做不到**；★ 它的**自动回滚只在原子发行版上成立**（它自己写了 scope limit：Ubuntu/apt 上**不回滚**）——★ **「自动回滚」不许当成通用能力吹**。
