## §一 ★★★★ 关键证据：本体里的 `envelope`（信封）**早就写了「每个信封都进账」**

★ `ontology.json` 的 `envelope` **逐字**：

```json
{
 "_comment": "一条事件的外壳（信封）—— 机制只看这一层，不看信纸",
 "required": ["world", "kind", "id", "seq", "at", "actor", "flags", "body"],
 "optional": ["to", "trace"],
 "fields": {
  "world":  "integer  # 词表版本；只加 flags，永不改这个数的含义",
  "kind":   "enum(change, act, notice)  # 三个家族",
  "id":     "string  # 事件自身身份（去重）",
  "seq":    "integer  # ★★ 在账本中的位置，全局单增，由世界分配",
  "at":     "integer  # 时间戳，Unix 秒。顺序由 seq 决定，at 只作辅助",
  "actor":  "string  # 世界内身份，如 world://user",
  "to":     "string  # 目的地；空 = 广播",
  "trace":  "string  # ★ 因果：引发本条的那条事件的 id",
  "flags":  "array  # 能力旗标；未知旗标必须忽略",
  "body":   "object  # 三个家族各自的信纸"
 }
}
```

### §一·1 ★★★ 三条结论（★ 全是逐字）

| # | ★ 逐字 | ★★ 意思 |

| **3** | ★★ `world`：「**词表版本**」 | ★★★ **这就是第②张通行证要的 `vocab_hash`！** ★ 它**早就在信封里**了 ✓ |

★★★ **⇒ 所以「要不要记整体的信息交流的账」—— ★ 不需要新想：★ 本体早就写了，★ 只是【没有实现】** ✗

## §四 ★★★★ 「整体信息交流的账」谁来记 —— ★ 这是本件最要紧的问题

### §四·1 ★★ 两条路（★ 差别很大）

| # | ★ 路 | ★ 谁写账 | ★ 后果 |
|---|---|---|---|
| **A** | ★★ **只记【动作】**（★ 像 P） | ★ **本体**（★ 载体执行完 ⇒ 请求本体追加） | ★ 简单；★ 但★ **「信息交流」记不全** ✗ |
| **B** | ★★ **记【所有信封】**（★ 你要的） | ★ **？？哪一个进程能看见所有消息** | ★★ **必须有一个【站在总线上看得见一切】的东西** |

### §四·2 ★★★ 方案 B 的三种落法

| # | ★ 落法 | ★ 好处 | ★ 坏处 |
|---|---|---|---|
| **B1** | ★ **每个进程自己记，写同一本账** | ★ 不改进程数 | ★★ **并发写＋多写者** ✗（★ 违反「账只有一处」） |
| **B2** | ★★ **每个进程把消息【都发一份给本体】** | ★ 单写者 ✓ | ★★ **本体成了总线上的过滤器** ✗（★ 违反「四个独立、互不直连」） |
| **B3** | ★★★ **新开一个【账本进程】**（★ 订总线上所有话题） | ★★ **单写者 ＋ 不碰别人** ✓ | ★ **多了一个进程**（★ 第五个）★ ＋★ **订阅全量话题的性能** |

★★★★ **⇒ 你说的「新开个文件夹」如果指【新开一个账的组件】，★ 那 B3 就是它**：★ **账本进程** —— ★ 它**只干一件事：把所有信封按 `seq` 记进账** ✓

★★ **而且这正好合你之前定的「四个独立进程」**：★ **账本进程也是独立的**（★ 不读别人的文件、★ 只订总线）✓
