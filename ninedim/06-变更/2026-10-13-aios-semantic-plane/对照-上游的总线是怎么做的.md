# 对照：上游 AIOS 的"总线"是怎么做的（现取）

| 阶段 | 环 | 维 | 版本 |
|---|---|---|---|
| S3 | 执行 | 三 结构 | **1.0（现取）** |

> **作者问**：「我想问你这个**总线**，现在**根据 AI Native OS，他们的总线是怎么做的**？」

---

## 一、★★★ 结论先说：**上游没有"总线"这个东西**

| 现取 | 命中 | 说明 |
|---|---|---|
| `EventBus` | ★★ **0 处** | ★ 没有事件总线 |
| `struct *Bus` | ★★ **0 处** | ★ 没有任何叫 `Bus` 的构件 |
| `UnixListener` / `UnixStream` | ★★ **0 处** | ★★ **没有"同机 socket"这一档** |
| `tonic::` | ★ **457 处** | ★★ **主力＝gRPC** |
| `TcpListener` | ★ **67 处** | ★★ **走 TCP** |
| `Broker` | ★ 51 处 | ★ **但那 51 处是 `VaultBroker`（保管库代理）**，不是消息中间件 |
| `subscribe` ／ `publish` | ★ 10 ／ 39 处 | ★ 是**存储订阅**（rocksdb／inmemory）与**发布包**（recipe／manifest），**不是语义事件** |

## 二、★ 那它到底是什么形状：**点对点的 gRPC 网格**

★ **22 个 `.proto`**，★ **每个 crate 一个 package ＋ 一到三个 service**（现取）：

```
aios.fs.v1alpha1          -> AiosFs
aios.policy.v1alpha1      -> PolicyKernel
aios.evidence.v1alpha1    -> EvidenceLog
aios.runtime.v1alpha1     -> CapabilityRuntime
aios.cognitive.v1alpha1   -> CognitiveCore
aios.vault.v1alpha1       -> VaultBroker
aios.sgr.v1alpha1         -> SgrService
aios.renderer.web / .kde  -> WebRendererService / KdeRendererService
aios.hardware             -> HardwareManagerService / GpuResourceService / FirmwareTrustService
aios.network              -> NetworkPolicyService / DnsVpnService
aios.distribution.v1alpha1-> RepositoryService / PublisherService
（其余略 —— 共 22 个）
```

⇒ ★★ **谁要跟谁说话，就直接连对方那个服务**（★ 连接靠 `tonic`／地址靠配置）⇒ ★★ **它是**网格**，不是**总线** ✓
★ 而且★ **没有一点"中枢"的味道**：★ 一个 `Bus`／`Hub`／`Gateway` 服务都没有（★ proto 里 `service *Bus/Broker/Gateway/Hub/Router` 只命中 1 处 —— ★ 那是 **`VaultBroker`**）✓

## 三、★★★ 于是和"我们要造的总线"逐条比

| 项 | ★ 上游 AIOS 的做法 | ★★★ 我们说的"总线" |
|---|---|---|
| 形态 | ★★ **点对点网格**（22 个服务面） | ★★★ **中枢**（一个总机 ＋ 一套通行证） |
| 传输 | ★★ **gRPC over TCP**（`tonic` 457 ／ `TcpListener` 67） | ★ 三档：进程内 ／ **同机 Unix socket** ／ 跨机 gRPC |
| 同机那一档 | ★★★ **没有**（`UnixListener` **0 命中**） | ★★ **有**（`/run/world-core/omarchy.sock`） |
| 谁认识谁 | ★ **每方各自认识对方的服务与类型** | ★★★ **互不认识，只认识本体** |
| 一致性靠什么 | ★ **靠各 crate 自己的类型**（★ 各写各的 `ObjectKind`） | ★★★ **靠本体 ＋ 三张通行证** |
| 有没有中枢 | ★★★ **没有** | ★★★ **有 —— 那就是要造的** |

## 四、★★★ 它这个做法好在哪、代价在哪

| ★ 好处 | ★ 代价 |
|---|---|
| ★ **简单**：一门专科一个服务面，加一个 crate 就多一个 `.proto` | ★★ **每加一个专科，就多一条专线** —— N 个专科是 **N² 的接线面** |
| ★ **类型强**：gRPC 有 schema，编得过才算 | ★★★ **每方都要认识对方的类型** ⇒ ★★ **这正是"语义散在各处"的根因**：★ 上游没有一处说"这个世界有哪些类型" |
| ★ **跨机天然**：本来就是 TCP | ★ **同机也走 TCP**（★ 没有 Unix socket 那一档）⇒ ★ 同机上多一层网络栈开销 |

## 五、★★ 一句话

★★★ **上游的"总线"其实是**22 条专线**；★ 我们要造的"总线"是**一个总机**。**
★★ **总机把"每方都要认识对方"换成"每方只认识本体"** ⇒ ★★ **这也是为什么"本体"和"总线"必须一起做**：★ **总线离开本体就没规矩，本体离开总线就只是一个库** ✓

## 六、本件没做的事（如实）

1. ★ **没核**那 457 处 `tonic::` 具体怎么建连、怎么做服务发现（★ 上游有没有注册中心，**本席没查**）；
2. ★ **没核** `ActionReceivedPayload` 那类"跨 crate 统一 payload"覆盖了几个面（★ 那算不算"半条总线"，**本席没查完**）；
3. ★ **没跑**任何编译。
