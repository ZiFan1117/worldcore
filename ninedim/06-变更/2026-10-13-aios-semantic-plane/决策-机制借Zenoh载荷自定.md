## 二、★★★★ 为什么 Zenoh 贴（现取 feature flags，不是猜）

★ `zenoh` 1.10.1 共 **25 个 feature**，与我们的需求**逐条对上**：

| ★ 我们的需求 | ★ Zenoh 现取 |
|---|---|
| ★★ **三档：同机 ＋ 跨机** | ★★★ `transport_unixsock-stream`／`transport_unixpipe`（**同机**）＋ `transport_tcp`／`transport_quic`／`transport_tls`／`transport_ws`（**跨机**） |
| ★★★ **同机零拷贝** | ★★★ **`shared-memory` 是一个 feature**（`zenoh-shm`）⇒ ★ **不是外挂，是一等公民** |
| ★★ **Rust 原生、可内嵌** | ★★★ **整个栈是 Rust**（★ 不必额外起一个别语言写的 server） |
| ★★ **高性能** | ★★ **`uring`（io_uring）** ＋ `transport_multilink`（多链路） |
| ★★ **名字（通配符）** | ★★ **`zenoh-keyexpr`** ⇒ ★ 正好是"名字查表"的落点 |
| ★ 压缩 | ★★ `transport_compression` |
| ★ 认证 | ★★ `auth_pubkey`／`auth_usrpwd`（★ 与我们的治理配合） |
| ★ 特殊链路 | ★ `transport_serial`（串口）／`transport_vsock`（VM socket） |

⇒ ★★★ **结论：Zenoh 像是照着我们的"三档"长出来的。** ✓

## 三、★★★ 三条必须写清的边界（否则会出"两本账"这类错）

| # | 边界 | 为什么 |
|---|---|---|
| **1** | ★★ **Zenoh 只管「送」，不改「记」** | ★★ **"记了不许改"仍是我们的账（`Ledger`）** —— ★ Zenoh 的持久是**消息层**的，★ 我们的账是**语义层**的，★ **两者不是一回事，不能混** |
| **2** | ★★ **持久与重放由我们的账担** | ★ Zenoh 的 storage 插件**不如 NATS JetStream 强** ⇒ ★★ **而我们的账已经"只追加 ＋ 防篡改"** ⇒ ★ **它天然就是重放的底** ✓ |
| **3** | ★★★ **校验在「进 Zenoh 之前」** | ★★ **本体校验发生在信封上**，★ 进了 Zenoh 就只是**字节**了 ⇒ ★ **"第 19 条功能"必须挡在 Zenoh 前面** ✓ |

## 四、★★ 名字怎么落到 Zenoh（keyexpr）

```
★ 我们的名字（本体里的）           ★ Zenoh 的 keyexpr
  world://<域>/<类>/<实例>    ⇒     world/<域>/<类>/<实例>
  ★ 动作不进 key，进信封的 type 字段（★ 因为动作是"做什么"，不是"在哪"）
★ 通配：world/<域>/application/*      （★ 订阅一族）
```
