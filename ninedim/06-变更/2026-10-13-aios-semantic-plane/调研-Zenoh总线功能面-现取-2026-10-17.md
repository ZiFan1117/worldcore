## §一 一句话定位（三条逐字）

★ **zenoh.io 首页**逐字（英文原文）：

> "Zenoh (/zeno/) is a pub/sub/query protocol unifying data in motion, data at rest and computations."

★ **What is Zenoh?** 页逐字：

> "Zenoh is the only protocol available on the market that can work efficiently and perform from server-grade hardware and networks to the embedded microcontroller and extremely constrained networks."

★ **规范 v1.0.0《Introduction》**逐字：

> "Zenoh unifies data in motion, data at rest, and computations in a single coherent protocol designed to span the full compute continuum — from deeply embedded microcontrollers to cloud services."

★ **合成一句**（本席归纳，不是逐字）：**它不止是消息总线 —— 是「会话模型 ＋ 一个键空间 ＋ 推／查／存三种语义 ＋ 计算注册口」合一的一套协议**。

## §二 功能面清单（11 面）

### 2.1 数据模型：键表达式（Key Expression）

| ★ 项 | ★ 外部怎么说（据 §七 各页） |
|---|---|
| 键 | `/` 分隔的层级路径，形如 `organizationA/building8/room275/sensor3/temperature`；`/` 是**唯一**分层符（用它比用 `.` 快，官方称有人换过来 CPU 几乎降一半） |
| 通配 | `*` 只配**一个** chunk；`**` 配**零到多**个 chunk；`$*` 是 chunk 内任意前缀（比 `*` 慢，设计键空间时尽量避开） |
| canonical form | 同一集合只允许一种写法（`**/**`→`**`、`**/*`→`*/**`、`$*$*`→`$*`…）⇒ ★ 路由匹配**只要比字符串** |
| Selector | `key_expr?arg1=val1;arg2=val2` —— 把「按路径匹配」与「带参数查询」合成一次请求；参数 URL 编码 |
| Value ＋ Encoding | 值是「字节 ＋ 编码描述」；编码可自造（前缀 `EMPTY` 表示"我不会解，交给你"）；内置 `TextPlain`／`AppJson`／`TextProperties`／`AppInteger`／`AppFloat` 等 |
| 时间戳 | 第一个收到值的路由器给它打 **HLC（混合逻辑时钟）＋ 路由器 UUID** ⇒ ★ 全网唯一、**发生先后可保序**、**不用跑共识** |

### 2.2 发布／订阅（推模型）

- Publisher 发 `PUT`／`DEL`（带 key、可选 QoS、encoding、时间戳）；Subscriber 用 `D_SUBSCRIBER` 声明兴趣。
- ★ **Publisher 没有声明消息**（规范逐字：publishers 的**存在是隐含在它发出的 PUSH 里的**）；路由表靠**订阅者声明**建 ⇒ ★ 扩到大量节点时不用给发布者记状态。
- ★ 规范逐字：**"The Zenoh protocol uses a push delivery model only"**（只有推，没有拉模式）。
- 每条消息带：WireExpr（键的**紧凑别名**，`ExprId` 复用 ⇒ 省字节）、可选 QoS、可选 encoding、可选 HLC。

### 2.3 查询／可查询（Queryable）—— 请求应答、RPC、map-reduce

- 任意节点对 selector 发 `GET`；注册在该 key 上的 **Queryable** 收请求、回 **0..N 个** reply（`RESPONSE → REPLY/ERR`）。
- 声明元信息两条：`complete`（是不是**所有**这个 key 的查询我都能答，供 `AllComplete` 用）／`distance`（跳数，0＝同进程）。
- ★ 首页逐字：「**It also allows applications to register computations that will be triggered by queries**；a simple mechanism that allows many patterns to be implemented, such as **RPC and map-reduce**」。

### 2.4 存储（Storage）—— 静态数据 ＋ 地理分布

- ★ 定义（Abstractions 页逐字意）：Storage **既是 subscriber 又是 queryable** —— 订阅 key、把收到的值存下、被 query 时**返回每个匹配 key 的最新值**。
- ★ 规范逐字：「A **Storage** is a Queryable that also persists published data」；★ 它在 wire 上**不是新实体**，就是 `D_SUBSCRIBER` ＋ `D_QUERYABLE` 两条声明。
- ★ 落法：`zenohd` 的 **storage-manager 插件**管存储，**具体的存储后端交给可动态加载的 volume**（RocksDB／InfluxDB／文件…各卷各的取舍）。
- ★ 首页逐字：**geo-distributed storages with sharding and replication**（★ 本件**没核**分片／复制的实现细节，见 §八）。
- ★★ **注意语义**：它是「**每个键的最新值**」，**不是**「Kafka 那种只增日志 ＋ 按 offset 重放」—— ★ 这条对我们 §五 第 5 条很关键。

### 2.5 存活（Liveliness）

- `Token` 表示「某个命名实体还活着」：声明了 ⇒ 订阅该 key 的人看到 **present**；撤销／会话关 ⇒ **gone**。
- wire 上两条：`D_TOKEN`（声明）／`U_TOKEN`（撤销）。
- ★ 用途：在线检测、成员管理、拓扑里"谁还在"。

### 2.6 QoS（每条消息可调）

| ★ 旋钮 | ★ 规范 v1.0.0 的取值 |
|---|---|
| 优先级 | **0–7** 共 8 级：`Control`(=0)／`RealTime`／`InteractiveHigh`／`InteractiveLow`／`DataHigh`／**`Data`(=5，缺省)**／`DataLow`／`Background`(=7) |
| 可靠性 | **信道级**协商：`Reliable`（保序不丢，传输层重传）／`BestEffort`（可丢可乱序） |
| 拥塞控制 | `Drop`（队列满就丢，★ **PUSH 缺省**）／`Block`（背压，★ **REQUEST/DECLARE/INTEREST 缺省**）／`BlockFirst`（首条阻塞、其余丢，要 Patch ≥ 1） |
| Express 标志 | 绕过批处理**立刻单独发**，换最低延迟（规范逐字："should be used sparingly"） |
| 优先级通道 | 两端都开 QoS ⇒ **8 条独立优先级队列**，避免队头阻塞 |

### 2.7 路由与组网（拓扑无关）

| ★ 拓扑 | ★ 长什么样 |
|---|---|
| Peer-to-Peer Mesh | 全是 Peer，靠组播发现、直连；★ 局域网／机器人／科研 |
| Client–Router | Client 挂 Router，Router 转发；★ IoT／受限设备 |
| Routed（Router 联邦） | 多 Router 互联成骨干，地理分布；★ 云—边—端 |
| Hybrid | 上面任意组合 |

- **角色**：Peer／Router／Client。
- **发现**：Scouting 层 `SCOUT`／`HELLO`（UDP 组播）自动找邻居，也支持静态 seed。
- **声明与兴趣**：`D_*`／`U_*` 声明实体；**Interest** 机制让**后加入**的节点恢复全网声明状态（★ 规范逐字：**late-joining consistency**，不用全局重置）。
- ★ 规范逐字的设计目标：**百万节点／十亿命名资源**，靠"通配匹配 ＋ 惰性声明（Interests）"避免路由处**状态爆炸**。
- ★ 传输与拓扑**解耦**：★ 同一套 wire 协议跑所有拓扑，**不改格式**。

### 2.8 传输层（transport-agnostic）

| ★ 项 | ★ 现取 |
|---|---|
| 链路 | **TCP 单播／UDP 组播／TLS／QUIC／串口／WebSocket／共享内存（SHM）**；★ 可跑在 OSI **L2** |
| 会话 | `INIT`／`OPEN`／`CLOSE`／`KEEP_ALIVE`；分片（`FRAGMENT`）、批处理（`FRAME`）、流控 |
| 开销 | ★ 官网首页逐字「**5-bytes wire overhead**」；★ What is 页逐字「**4-6 bytes**」（★ **两处不一致，如实并列，见 §八**） |
| 规范的说法 | ★ 逐字：「**No mandatory framing overhead beyond a single header byte per message**」；LEB128 变长整数 ＋ 紧凑位域头 |
| 受限设备 | ★ 官方称最小实现在 **Atmel 8 位 MCU 上约 300 字节 footprint**；★ `zenoh-pico`（bare-metal／no-alloc）与 `zenoh-nostd` 是另两个实现 |

### 2.9 安全

- **认证**：TLS（含证书校验）／**用户名－密码**。
- **授权**：**Access Control（ACL）**，按 **key expression 粒度**控制谁能订／谁能发。
- ★ 规范有独立的《Security》章（威胁模型／认证／访问控制三节）。

### 2.10 插件与可管理面

- ★ `zenohd`（参考实现的路由器进程）**启动时或运行时**都能加载插件；插件与它**共享运行时、同一 peer ID**。
- ★ 官方自带两件：**REST 插件**（把 Zenoh 暴露成 HTTP API）／**storage-manager 插件**（管 storages 与 volumes）。
- ★ **Admin space**：管理面**就是一段 key** —— `@/<router-id>/router/**`，用普通 GET／PUT 读状态、改运行时配置；REST 下 `<router-id>` 可写 `local`。

### 2.11 多语言与生态

- ★ 实现：**Rust（参考实现）**；另 **C／C++、Python、Kotlin／Java、TypeScript／Node** 等绑定；受限侧 `zenoh-pico`／`zenoh-nostd`。
- ★ 生态件（本件只在官网／用例页见到名字，**未逐个核**）：**`rmw_zenoh`**（ROS 2 的官方 RMW）、`zenoh-bridge-ros2dds`、`zenoh-plugin-dds`。
- ★ 已见采用的用例（官网 Use Cases 页）：**机器人／ROS 2**（替代 DDS 做通信层）、**汽车与自动驾驶**（软件定义汽车、Indy Autonomous Challenge 的 V2X／遥测）、**IoT／边缘**（edge-to-cloud）、**电信／游戏**。

## §四 与既有中间件的位置差异（规范逐字）

★ 规范 §Introduction 逐字列了四条「别人各管一段」：

> "**MQTT** is simple but lacks geo-distributed query semantics and fine-grained QoS."
> "**DDS** provides rich QoS but imposes substantial code-size and memory overhead unsuitable for constrained devices."
> "**AMQP and Kafka** are broker-centric and ill-suited for peer-to-peer or bandwidth-constrained links."

★ 再加首页与 What is 页给出的两条对照（**转述**，非逐字）：

| ★ 对手 | ★ 它的问题（官方口径） | ★ Zenoh 的说法 |
|---|---|---|
| DDS | 定位透明只覆盖**在途数据**，上不了互联网尺度、下不了 MCU | 一套协议从 MCU 到数据中心 |
| MQTT | **broker 悖论**：同一局域网两台设备也得绕远端 broker | peer 直连、可无 broker |
| CoAP | 天生 **client/server**、云中心 | 推／查／存同一套 |
| Kafka／AMQP | **中心化 broker**，不适合 P2P 与窄带 | router 联邦／mesh |

★ 一句话（本席归纳）：**别人各占「一段」，它想占「一整条」—— 代价是概念多、生态新（见 §六）。**

## §六 三条对本仓的直接结论（★ 判断，可被读数推翻）

| ★ # | ★ 结论 | ★ 为什么 |
|---|---|---|
| **1** | ★★ **「先订阅、后发」是硬规矩** | ★ zenoh **默认不持久**：发布那一刻**没有订阅者**，那条消息就没了 ⇒ ★ 执行体／本体**谁先起**不是风格问题（★ 现场读数＝`zenoh真进13-2026-10-17.md` §三 两次对照） |
| **2** | ★★ **zenoh 只是【语义面】的传输；数据面不走它** | ★ 五步第 ④ 步逐字「不过总线」（★ 见 `改动对照.md` §五十八.2）⇒ ★ 不要把 zenoh 的 storage 当数据面通道 |
| **3** | ★ **storage 不能当"重放"用** | ★ 只存每键最新值；断线补漏／历史回放要另找载体（§2.4 ＋ §五 第 5 条） |

★ 另两条**用法提示**（照 §2.6／§2.9，未实测）：

- 语义面信封是**小消息** ⇒ Express 标志可换延迟，但规范自己说「sparingly」；
- 信封要过本体门 ⇒ **ACL（按 key 的读写权）能挡"谁能发到哪个 key"，挡不了"发的东西内容对不对"** —— 后者只能我们的第 19 条管。
