# 方案（待签）：最小内核 —— 支撑系统只要几个部分，且全都围着本体转

| 阶段 | 环 | 维 | 版本 |
|---|---|---|---|
| S2 | 意图 | 二 框架 ／ 三 结构 | **0.1（方案·待签）** |

> **作者令（逐字）**：「支撑我们这个系统的**最小的业务，我们需要几个部分**，而且这几个部分要**围绕着我们建立的这个本体来运转**，对吧？它是相互关联的。你比如说像什么**动作**呀，什么这些是吧，**策略**呀，什么的，**这本身我们本体里头不是都有了吗**？**围绕着我们转就行了，我们没必要就是单拎出来了**，对吧。我们需要的是那种**最基础的一些东西**，而且这些基础的东西**都要围绕着我们的本体运转**。」

---

## §一 ★★ 先把"本体里已经有什么"摆出来（这是中心的依据）

| 本体的节 | 现取 | 它管什么 |
|---|---|---|
| `objects` | ★ **9 类**（`surface`／`port`／`human`／`agent`／`application`／`service`／`device`／`workflow`／`ledger`） | ★ **世界里有什么** |
| `links` | ★ **3 条边** | ★ **它们怎么相关** |
| `interfaces` | ★ **9 条能力** | ★ **能做什么** |
| `actions` | ★ **9 条动作** | ★ **合法动作名**（★ 未登记即拒的权威） |
| `functions` | ★ **9 条** | ★ 动作的实现面形状 |
| `types` | ★ 基础类型 ＋ **`record_kind`** | ★ **取值域** |
| `permissions` | ★ 授权表 | ★ **谁能做什么** |
| `governance` | ★ 角色／标记 | ★ **谁是什么角色** |
| `envelope`／`families` | ★ 信封 ＋ **4 族**（change／act／notice／job） | ★ **记下来的事件长什么样** |
| `world` | ★ 词表版本 | ★ **这一版的身份** |

⇒ ★★ **即：类／关系／能力／动作／权限／角色／事件形状 —— 这些"声明"本体里全都有了** ✓
⇒ ★★ **所以作者那句话是对的**：★ **"动作、策略"再单独造一套，是重复** ✓

## §二 ★★ 但要分清一件事：**声明** 与 **机制**

| | 是什么 | 今天住在哪 |
|---|---|---|
| ★★ **声明** | ★ 「**世界里有什么、能做什么、谁能做**」—— **数据** | ★★ **本体**（上面那 10 行） |
| ★ **机制** | ★ 「**照着声明去执行/拒绝/记账**」—— **代码** | ★ 上游的 `aios-action`／`aios-policy`／`aios-evidence`… |

⇒ ★ **两者不是重复**（★ 一个说规矩、一个照规矩办）；
⇒ ★★ **但作者点出的真问题成立**：★ **规矩既然全在本体里、机制就不该是"一整套专科"** —— ★ 它该**很薄**（读本体、照做）✓
★ **硬证据**：★ 上游 `aios-capability-runtime` 一个人 **43,853 行／320 个 pub 项** ⇒ ★ **那是"把规矩也写进了代码"**（★ 因为它没有权威声明面可读）⇒ ★ **本体一立，它就该薄** ✓

## §三 ★★★ 最小内核：**6 个部分**（本席建议，待人裁）

| # | 部分 | 它管什么 | ★ 读本体哪一节 | 今天可借的上游件 |
|---|---|---|---|---|
| **1** | ★★ **本体**（中心） | ★ **权威声明**：类／关系／能力／动作／权限／角色／事件形状 | ★ 全部 | ★ `aios-ontology`（**我们已经有了**，512 行） |
| **2** | ★ **账本** | ★ **写与读**：把发生的事记下、折出现状 | ★ `envelope`／`families`／`objects`（实例） | ★ `aios-evidence`（账）＋ `aios-action`（信封） |
| **3** | ★ **执行器**（薄） | ★ **照本体办的机制**：查能力／查权限／拒或放 | ★ `interfaces`／`actions`／`permissions`／`governance` | ★ `aios-policy`（判定）＋ `aios-capability-runtime`（★ 但只取"薄"那层） |
| **4** | ★ **翻译** | ★ **把人的话翻成动作名**，并**查表拒** | ★ `actions`／`functions` | ★ `aios-cognitive`（★ 我们已装了闸） |
| **5** | ★ **载体** | ★ **按类存对象、按实例上限收** | ★ `objects`（＋ `instance_mode` 上限） | ★ `aios-fs` |
| **6** | ★ **界面** | ★ **给人看的那一面**（可被指向、可撤回） | ★ `surface`（＋ `port`） | ★ `aios-renderer-*` 里**选一个** |

⇒ ★★ **6 个里有 1 个是我们已有的（本体）；5 个是"薄执行器"** —— ★ **其余 31 个上游 crate 属"专科大全"，不进最小内核** ✓
★ 而★ **它们不会被删**（★ 上游骨架；★ 别人验证过）⇒ ★ **它们是"内核之外的扩展面"**，★ 将来按需接 ✓

## §四 ★★ "围着本体转"具体长什么样（这才是关键）

```
                    ┌──────────────────────┐
                    │   本体 aios-ontology   │  ← ★ 唯一的权威声明
                    │ objects/links/        │
                    │ interfaces/actions/   │
                    │ functions/types/      │
                    │ permissions/governance│
                    │ envelope/families     │
                    └───────┬──────────────┘
        读 ┌───────────┼───────────┬───────────┐ 读
          ▼           ▼           ▼           ▼
    ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
    │  翻译   │ │  执行器 │ │  载体   │ │  界面   │
    │查 actions│ │查permissions│按 objects │ │按 surface│
    └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘
         └───────────┴───────────┴───────────┘
                        ▼  写
                 ┌─────────────┐
                 │    账本     │  ← ★ 只追加；折出现状
                 └─────────────┘
```

⇒ ★★ **四条硬规矩**（★ 这就是"围着转"）：
1. ★ **谁都不许自带一份"类型清单"** —— ★ 只读本体；
2. ★ **不认识的名字即拒**（★ 这就是 **T-30**）；
3. ★ **本体不在 ⇒ 不许启动**（★ 这就是 **T-28**"闸常开"）；
4. ★ **写世界的每一笔都要过执行器**（★ 谁忘挂策略核谁绕过策略 ⇒ ★ **T-26**）。

## §五 落地顺序（本席建议）

| 步 | 做什么 | 为什么先做它 |
| **1** | ★ **T-30：未登记即拒**（载体侧不认识的类型不许偷偷当 `File`） | ★ 它是"**围着本体转**"的**第一道**也是最硬的一道 |
| **2** | ★ **T-26：策略核必挂** | ★ 不挂就绕过 ⇒ ★ 规矩形同虚设 |
| **3** | ★ **T-28：闸常开 ＋ 41 条并入本体** | ★ 把"本体在不在都得认它"变成常态 |
| **4** | ★ **按 §三 那 5 个部分各出"薄执行器"的形状** | ★ 到那时才有"最小内核"可跑 |

## §六 本件没做的事（如实）

1. ★ **没估** 6 个部分各自的工程量（★ 只给了"读哪一节、借哪个上游件"）；
2. ★ **没核** 上游那 5 个件（evidence／action／policy／cognitive／fs）里"薄的那层"具体在哪几行（★ 那是第 4 步的活）；
3. ★ **没定** 界面选哪一个（★ `renderer-cli`／`web`／`kde`／`terminal` 待裁）。
