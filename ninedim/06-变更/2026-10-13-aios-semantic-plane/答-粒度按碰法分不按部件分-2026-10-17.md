# 粒度的正确轴：**按「碰法」分，不按「部件」分，也不按「域」分**（2026-10-17）

> ★ **作者话（逐字整理）**：「**我不是说是有多个计算机**，我就说，就比如说你跑在这台计算机上头，你这台计算机的**所有以前的工具，以及它整个的一些能力，比如说 CPU，CPU 它的情况啥的这些东西都能用一个吗**？如果是一个的话，那就是以整个底层的 CPU、底层的 computer 来做一个**总总的映射**；如果要是你说计算机下面还要**细分一些，就是网卡啥的**这些东西，那就**需要多个**了。」
> ★★★ **这一问让我把上一笔（T-295）的答案【改准】**：★ 上一笔我说「**一个域一个载体**」★ —— ★ 那是**按「域」分**；★ 而**真正的轴是「碰法」**（★ 见 §一）。

## §一 ★★★ 底层只有【三种碰法】（★ 这才是分载体的轴）

| # | ★ 碰法 | ★ 怎么碰 | ★ 要特权吗 | ★ 例子 |
|---|---|---|---|---|
| **1** | ★★ **exec**（跑命令） | ★ `execve`：`program + args` | ★ 一般不要 | ★ `ls`／`stat`／`systemctl`／`apt`／**`ip addr add`**／`ps` |
| **2** | ★★ **读**（读状态） | ★ 读 `/proc`、`/sys` | ★★ **不要** | ★ CPU 负载／内存／★ 网卡统计（`/sys/class/net/*/statistics`）／温度 |
| **3** | ★★★ **写**（碰硬件） | ★ 写 `/sys`、`ioctl`、设备节点、`dbus`、`udev` | ★★ **要**（`CAP_SYS_RAWIO`／`CAP_NET_ADMIN`／root） | ★ 背光／电源／改网卡芯片寄存器 |

★★★ **一句话**：★ **「CPU 的情况」不是一种【对象】，是一种【读】；★ 「以前的工具」是【exec】** —— ★ **它们碰底层的【方式】不一样**，★ **这才是要不要拆载体的判据**。

## §二 ★★★ 直接答你的问题：**不是 1 个，也不是 N 个 —— 是 2 个**

```
┌──────────────────────────────────────────────────────┐
│ ★ 载甲（普通权限）                                    │
│   ★ exec：这台机器上所有以前的命令行工具（几千条）    │
│   ★ 读  ：CPU／内存／进程／网卡统计（/proc、/sys）    │
│   ★ ⇒ 「整个计算机的总映射」【就在这一个里】✓         │
└──────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│ ★ 载乙（特权）                                        │
│   ★ 写：背光／电源／网卡芯片／设备节点（ioctl、/sys 写）│
│   ★ 为什么必须另一个：★ 特权不同（★ 08 判据第 1 条）  │
└──────────────────────────────────────────────────────┘
```

### §二·1 ★★★ 为什么「网卡」**不需要**单独一个载体（★ 这是关键）

| ★ 网卡的事 | ★ 碰法 | ★ 归谁 |
|---|---|---|
| ★ 看收了多少包（统计） | ★ **读** `/sys/class/net/*/statistics` | ★ 载甲 |
| ★ 配 IP／启停 | ★ **exec**：`ip addr add`／`ip link set` | ★ 载甲 |
| ★ 改网卡芯片寄存器／固件 | ★ **写** `ioctl`／设备节点 | ★★ **载乙** |

★★★ **⇒ 「网卡」不是一个载体，★ 它的【三种碰法】分到两个载体里** ✓

### §二·2 ★★ 那「域」（文件／服务／包／进程…）算什么？

| ★ 项 | ★ 答 |
|---|---|
| ★ 域还是「一个域一个载体」吗 | ★★ **不是** —— ★ 域只决定**代码模块**与**数据文件**怎么分（`command.d/fs.jsonl`、`/pkg.jsonl`…） |
| ★ 为什么 | ★ 因为★ 文件／服务／包／进程 **都是 exec** ★ —— ★ **碰法一样 ⇒ 不必拆进程** |
| ★ 那上一笔说的「一个执行器管一类事」怎么放 | ★★ **它是【代码】的组织口径**（★ 一个模块管一类事）★ —— ★ **不是【进程】的划分** |

## §三 ★★★ CPU／网卡「的情况」在【本体】里放哪（★ 现取得出的结论）

### §三·1 ★★ 本体里【没有「度量／读数」这一类】

★ 现取 9 类：★ `surface`（屏幕那一面）／`port`（**跨进程进出的那一处** —— ★ 现取定义逐字，★ **不是硬件端口**）／`human`／`agent`／`application`／`service`／`device`（**硬件**，★ `anchor_note` 逐字「material entity —— 设备是硬件」）／`workflow`／`ledger`

★★ **⇒ 没有「状态读数」这一格** ✗

### §三·2 ★★★ 所以「CPU 的情况」应该是【动作】，不是【类】

| ★ 想法 | ★ 对不对 |
|---|---|
| ★ 把「CPU」做成一个类的个体 | ★ **不对** —— ★ CPU 是 `device`（★ 硬件），★ 它**已经是**一个类了 |
| ★★ **把「查 CPU 情况」做成一个【动作】** | ★★ **对** —— ★ `cpu.status` ⇒ ★ 读 `/proc/stat` ⇒ ★ 回一个读数 |
| ★ 把「网卡 1」做成一个个体 | ★ ★ 可以 —— ★ 它是 `device` 类的一个**个体**（★ `device/net0`） |
| ★ 把「网卡收包数」做成一个个体 | ★ **不对** —— ★ 那是**读数**，★ 是动作的**输出**，★ 不是一条持续体 |

★★★ **一句话**：★ **对象是【东西】（CPU／网卡是 device 的个体）；★ 状态是【动作的输出】（`cpu.status` 返回的东西）** ✓
