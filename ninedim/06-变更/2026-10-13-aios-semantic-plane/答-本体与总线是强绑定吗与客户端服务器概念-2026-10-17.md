# 答：**本体和总线是强绑定吗？能替换吗？总线有客户端/服务器概念吗？**（2026-10-17）

> ★ **作者两问（逐字整理）**：「**我的本体和这个总线是强绑定的吗？就是我能不能随机替换这个总线**」；「**这个总线有没有说客户端服务器的这种概念**」。

---

## §一 ★★★ 第一问：★ **不强绑定 —— 能替换**

### 一.1 ★★★ 现取：本体与总线之间【只有一个口】，★ 4 个方法

★ `crates/aios-worldcore/src/engine/transport.rs`：

```rust
pub trait Transport: Send + Sync {
    fn put(&self, topic: &str, payload: &str) -> Admit<()>;              // ★ 发一条
    fn take(&self, topic: &str, timeout: Duration) -> Admit<String>;    // ★ 收一条
    fn request(&self, ask: &str, payload: &str, reply: &str, timeout: Duration) -> Admit<String>; // ★ 先订后发再收
    fn subscribe(&self, topic: &str) -> Admit<Box<dyn Subscription>>;   // ★ 长期订阅
}
```

★★★ **就这 4 个方法** —— ★ **本体对总线知道的全部** ✓

### 一.2 ★★ 现取：**已经有【两个】实现**（★ 这本身就是「可替换」的证据）

| ★ 实现 | ★ 在哪 | ★ 用来干什么 |
|---|---|---|
| ★ `LocalTransport` | ★ `transport.rs:120` | ★ **同进程内存队列**（★ 测试用 —— ★ 一条网络都不拉） |
| ★★ `ZenohTransport` | ★ `transport/zenoh_impl.rs:148` | ★ **真总线**（★ zenoh） |

★★ **换总线 ＝ 写第 3 个 `impl Transport`** ★ —— ★ **本体那边【一行不用改】** ✓

### 一.3 ★★★ 现取：**zenoh 是 optional feature，★ 默认关**

```toml
# aios-worldcore/Cargo.toml
[dependencies.zenoh]
workspace = true
optional = true          ← ★ 可选依赖

[features]
bus-zenoh = ["dep:zenoh", "dep:tokio"]   ← ★ 不开就不拉网络栈
```

★★★ **⇒ 「本体核心」对 zenoh 【无硬依赖】** —— ★ 不开 `bus-zenoh` 时，★ **编译出来的本体里没有 zenoh 一行** ✓

### 一.4 ★★★ 今天的证据（★ 这条最有说服力）

★★ **「`mode: client` 在 systemd 下连不上」那个问题** ★ —— ★ **它是【zenoh 特有的】**（★ 换一个总线就没这问题）★ ⇒ ★★ **这正好说明「口」的价值**：★ **问题被关在一个 `impl` 里** ✓

### 一.5 ★★ 但有一处【必须如实】

| ★ 项 | ★ 内容 |
|---|---|
| ★★ **口的 4 个方法是从【zenoh 的能力】里抽的** | ★ `subscribe` 返回**句柄**、★ `request` **先订后发** —— ★ 那些语义是 zenoh 的 |
| ★ 换总线时要检查什么 | ★★ **那 4 个方法都实现得了吗** ★ —— ★ **MQTT／NATS／Kafka 都能**（★ 它们都有发布／订阅／请求-应答） |
| ★ 会不会要改口 | ★ **可能小改**（★ 例如某家没有「先订后发」的原子操作 ⇒ ★ `request` 要用「建临时订 topic」实现） |

★★★ **一句**：★ **口小（4 个方法）＋ 依赖可选 ⇒ 换总线的成本【低】，★ 但不是【零】** ✓

## §二 ★★★ 第二问：★ **有 —— zenoh 有三种角色**

### 二.1 ★★★ 现取：`zenohd --help` 逐字

```
The zenoh router
Usage: zenohd [OPTIONS]
  -l, --listen <ENDPOINT>
          Locators on which this router will listen for incoming sessions
  -e, --connect <ENDPOINT>
          A peer locator this router will try to connect to
      --no-multicast-scouting
          By default zenohd replies to multicast scouting messages
          for being discovered by **peers and clients**
```

★★★ **三样都露出来了**：

| ★ 角色 | ★ 谁 | ★ 逐字依据 |
|---|---|---|
| ★★ **router**（★ 服务器） | ★ `zenohd` | ★「**The zenoh router**」＋「**this router will listen for incoming sessions**」 |
| ★★ **peer**（★ 对等） | ★ 其他 peer | ★「**A peer locator**」＋「**discovered by peers**」 |
| ★★ **client**（★ 客户端） | ★ 我们的本体／执行体 | ★「**discovered by … clients**」 |

### 二.2 ★★★ 我们的拓扑（★ 本该是什么）

```
★ 服务器：★ `zenohd`（router）—— ★ `--listen tcp/127.0.0.1:7447` ★ 它就是【服务器】
★ 客户端：★ 本体进程（client）★ 连上去 ★ ⇒ 收/发消息
★ 客户端：★ 执行体（client）★ 连上去
```

★★★ **这是【标准的 client/server 拓扑】** ✓ —— ★ 也正是我**最初想用的**（★ `mode: client`）✓

### 二.3 ★★ 但今天的**妥协**（★ 如实）

| ★ 项 | ★ 内容 |
|---|---|
| ★ 本该用 | ★★ **`mode: client`**（★ 本体当客户端） |
| ★★ 实际被迫用 | ★★ **`mode: peer`**（★ 因为 `client` 在 systemd 下连不上，★ 未解） |
| ★ 后果 | ★★ **两个 peer 连同一个 router ⇒ 【peer 之间不互转】**（★ 前面实测：★ 本体收不到执行体的消息）✗ |
| ★ 所以 | ★★★ **这是个【临时状态】** —— ★ 一旦 `mode: client` 的根因解决，★ 就回到标准拓扑 ✓ |
