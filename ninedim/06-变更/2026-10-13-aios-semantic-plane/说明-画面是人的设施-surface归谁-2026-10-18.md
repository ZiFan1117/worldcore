## §一 判词：**人在需要，机器在承担**

| 说法 | 判 |
|---|---|
| 「画面/渲染/合成器/个人空间是给人看的」 | ★★ **对** —— 它们是**人这一侧**的设施 |
| 「机器（Agent/computer/服务）也需要画面」 | ★★ **不对** —— 机器之间只走语义事件/动作/查询；画面不参与、也帮不上 |
| 「所以这些进程可以不要」 | ★★ **也不对** —— "人需要"在系统里落成**机器承担**：这些进程跑在 computer 上、由 computer 提供资源；它们仍要是个体、要被记账 |

★ 准确一句：**不是"机器需要画面"，而是"机器替人搭了人的设施"。**
★ 配套纪律（10-18 会话内议定）：**"谁造帧，谁就是参与方"** —— 往人的屏幕上送东西的一方，必须是个体、可归因、过本体；**不许匿名弹窗**。

## §三 A2UI 与传统 UI 的差别（回答"是不是很大不同"）

> ★ a2ui.org 官方原话（旧会话 10-18 现取）：**「A2UI 协议像 HTML，渲染器像浏览器。」** 渲染器把 A2UI JSON 消息转成各平台原生控件；agent 负责**生成**消息，传输层负责**送达**；渲染器要缓冲、走生命周期、画控件，并把用户动作**路由回 agent**。

| 轴 | 传统 GUI（Qt/GTK 原生、HTML 应用） | A2UI 这套 |
|---|---|---|
| **界面是什么** | 应用里的**代码**（控件树＋渲染逻辑，编进程序） | **消息/数据**（JSON 组件树＋数据模型，走传输） |
| **谁渲染** | 应用自己画（或浏览器画 HTML/JS） | **通用渲染器**画（一份描述，多端/多渲染器） |
| **换端/远端** | 重写 UI；远端只能传像素（VNC/RDP） | 同一份描述多端渲染；**远端传描述、本地渲染** |
| **人的动作** | 点击＝坐标/事件，绑死在应用私有逻辑 | 点击＝**结构化动作**（componentId＋参数）回提供方，**可鉴权、可记账** |
| **谁能生成** | 人写代码 | **Agent 可生成**（A2UI 本来就是给 agent 产出 UI 的） |
| **状态归属** | UI 与业务状态混在应用里 | 渲染器只持"最新一帧/缓存"；世界真相在账本/本体；**帧内容不进本体** |
| **可替换性** | 换 UI 要改应用 | 换渲染器不改提供方（浏览器 → GTK → Flutter） |

★★ **两条本质**：①**传统 UI＝应用里的代码**，**A2UI＝走线上的语义描述**；②**传统人机回路＝像素/坐标**，**这套＝结构化动作**。
★★ **"最简便"五条**：提供方不写渲染代码；一份描述多端复用；Agent 天然会生成/增量更新；人的动作天然成为世界动作（过门禁、可记账）；远端传语义不传像素。
★ **边界（别把 A2UI 当世界语义）**：A2UI 只是**视觉投影的格式**，不是本体的法律、不进账本；世界真正的"共同说法"仍是本体（七问/三类话）；A2UI 的 catalog 只答"能画什么"。
★ **生态现状（旧会话现取，2026-10-18）**：官方维护渲染器只有 Web/Mobile（Flutter GenUI 为 v0.9.1 Stable）；v1.0 各渲染器 Planned/Candidate；官方**明确允许自写渲染器**（六条验收：解析扁平 JSON／映射原生控件／数据绑定与生命周期／处理增量消息／支持服务端发起更新／支持用户动作）。我们浏览器版已画到 **93 组件、未知 0**。

## §四 **surface 归谁**：四个归属（本件对作者问题的回答）

★ 先纠一个直觉：**surface 不是"某个进程拥有的一块画布"**。按 10-18 的定稿：
- `surface` **不是进程** —— 它是**一帧 A2UI 描述**（components ＋ layout）；
- 有进程的，是**提供者**（发帧的那一方）和**渲染器**（叠帧落屏的那一方）；
- 屏是**硬件**。

所以"画面在哪里"要拆成四问、各有主人：

| 归属 | 归谁 | 具体是什么 | 现状（13） |
|---|---|---|---|
| **① 画什么**（脸的内容） | ★ **提供者**（agent／本体／个人空间／应用） | 它自己出的 A2UI 帧（它的"脸"）——**谁的状态谁描述**，别人不替它编 | agent 发帧已通（10-18 上屏）；个人空间未写；载体/服务按需才有脸 |
| **② 摆在哪**（位置/层叠/焦点） | ★★ **个人空间**（`aios-space`） | `layout`（谁、z、rect、active、modal）＋共同部分（壁纸/顶栏/图标） | **未写**（10-18 议定：共同部分不是渲染器的，是个人空间那层的） |
| **③ 怎么合成**（叠＋落屏） | ★★ **渲染器/合成器** | 按 layout 叠缓存、画到屏；**不持状态、不裁决、不布局** | 浏览器版已画（93 组件/0 未知）；GTK/Flutter 待选 |
| **④ 谁在看/谁在点**（口与身份） | ★★ **接入/登录 ＋ `human/*`** | `by`（surface/renderer 发的）/`for`（human，需 Permit） | **未写**；现在只有 `surface/a2ui`，**没有 human 个体** |

```
提供者（各自出脸）──world/notice 帧──▶ 本体 ──▶ GUI ──▶ 渲染器（按 layout 叠）──▶ 屏
        ▲                                                    │
        └──────── world/ui/act（人点；by=surface, for=human）◀┘
  布局：个人空间给的    共同部分：个人空间画的    帧内容：不进本体
```

★★ **一句话**：**脸归提供者、摆放归个人空间、合成归渲染器、口/身份归接入；全链过本体。**

## §五 "每个进程自己画"的正确读法

| 说法 | 判 |
|---|---|
| 「每个提供者**自己决定自己那张脸长什么样**（发自己的帧）」 | ★★★ **对** ✓ |
| 「每个进程**自己开窗、自己渲染、自己决定摆哪、自己往屏幕上推帧**」 | ★★★ **不对** ✗ |

★★ **机器里只有**：**一支笔**（渲染器）／**一个布局主人**（个人空间）／**一个口的身份**（接入）。
★★ 其它进程**可以没有脸**：需要给人看时才发帧（10-18 定："有没有画面＝发不发帧；显示不显示＝布局里有没有它"；**关画面 ≠ 停进程**）。

## §六 为什么不让每个进程自己画屏（五条）

| # | 理由 |
|---|---|
| **1** | **界面不持状态**（Omarchy 纪律；书 §4.4"读法不持有状态"）——每进程自带渲染 ⇒ UI 与业务耦合，回到传统老路 |
| **2** | **换渲染器不改提供方**——帧是描述，浏览器→GTK→Flutter 可换；每进程自己画 ⇒ 换一次要改 N 个进程 |
| **3** | **布局只有一个主人**——谁在第几层/摆哪/模态/焦点是个人空间的事；每进程自己摆 ⇒ 每进程都是窗口管理器 |
| **4** | **人只有一个端点**——`by`/`for` 记账要求"人的口"唯一（接入）；各自直接面向屏 ⇒ 账不可核、可匿名弹窗 |
| **5** | **远端/多端复用**——同一张脸可由不同渲染器/远端渲染；像素不可复用、描述可以 |

---

## §七 反例（三种，见到就红/就停）

1. **某进程自己开窗/自带渲染器/直接写显示** ⇒ 绕过唯一笔与布局主人。
2. **渲染器自己决定布局/焦点/主题/业务状态** ⇒ 界面持状态、越权。
3. **提供者绕过本体直接把帧推到屏**（匿名弹窗）⇒ 不可归因，账缺一笔。
   （另：任何一方伪造 `for`＝冒充人 ⇒ 书 §4.3"身份由入口给出，请求说了不算"；必须 Permit。）
