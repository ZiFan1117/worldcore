# 说明：**三方同构 —— 底层工具、上层应用、A2UI 的界面，同一套逻辑**（2026-10-16）

> ★ **作者令（逐字）**：「**同样的道理，就是无论是底层的这个底层的系统工具，以及就是开发的上层应用，都应该是按照这个逻辑，包括那个 A2UI 的那个 GUI 都是这个逻辑**」。
> ★ **一句答**：★★★ **三方都按同一套五步走**：★ **它自己注册 → 本体登记 → 过三道门 → 走总线调它 → 它回结果并落账**。

---

## §一 ★★★ 三方同构（一张表）

| | ★ **底层系统工具** | ★ **上层应用** | ★★ **A2UI 的界面** |
|---|---|---|---|
| ★ 它的对外接口是 | ★ 它自己的命令行／`ioctl`／D-Bus | ★ 它自己的 API／端口 | ★★ **它自己的渲染器**（★ 收到消息后**自己改显示**） |
| ★ 它注册什么 | ★ 系统类动作（如 `service.start`） | ★ 应用类动作（如 `download.start`） | ★★ **界面类动作**（如 `ui.scroll_to`） |
| ★ 注册者类别 | ★ `system` | ★ `app` | ★★ `interface` |
| ★ 怎么叫它 | ★ 走总线发一条消息 | ★ 同左 | ★★ 同左 |
| ★ 它怎么干 | ★ 它自己知道（★ 我们不问不记） | ★ 同左 | ★★ 同左（★ **它自己决定怎么画**） |
| ★ 本体替它做什么 | ★ **登记 ＋ 判 ＋ 传 ＋ 记** | ★ 同左 | ★★ 同左 |

## §二 ★★★ 三个具体例子（★ 你上次说：举例一下就清楚了）

### 例一 · 底层系统工具：`brightnessctl`（调背光）

```
★ 它本来就存在，本来就有自己的接口（命令行 brightnessctl set 50%）。
★ 它注册：device.brightness.set  { percent: integer }

      registered_by_kind = "system"                ← ★ 系统类
      transport          = "bus"
      endpoint           = "bus:world.fn.device.brightness.set"
★ 老张说「调暗一点」⇒ 过三道门 ⇒ 走总线发到那个 endpoint ⇒ brightnessctl 自己去做
```

### 例二 · 上层应用：`downloader`（下载器）

```
★ 同 T-231 那个例子：它注册 download.start，kind = "app"。
★ 它自己的 API 是它的；★ 本体只记那个地址。
```

### 例三 ★★ · A2UI 的界面（★ 这一条最特别）

```
★ 界面（那个渲染进程）也【注册它自己的动作】：

      registered_by      = "a2ui"
      registered_by_kind = "interface"             ← ★ 界面类
      transport          = "bus"

★ 于是：★ Agent（或另一个应用）可以说：

★★ 这在今天【没有】：今天的界面只能自己切显示，别人叫不动它。
```

## §三 ★★★ 「同一套逻辑」到底是什么（五步，三方一模一样）

```
① ★ 它自己注册（★ 不是我们替它编目）—— 交「名字／参数形状／权限要求」
② ★ 本体登记（★ 记下：谁注册的、哪一类、怎么叫它、地址是什么）
③ ★ 过三道门（名字门／身份门／权利门）—— ★ 三方都过，一道不少
④ ★ 走总线发一条消息到它的 endpoint（★ 不一定是函数调用）
⑤ ★ 它自己干、回结果（OK／FAILED／REFUSED）；★ 本体落一笔账
```

★★ **注意 ② 里的四样**：★ `registered_by`（谁）／★ `registered_by_kind`（哪一类）／★ `transport`（怎么叫）／★ `endpoint`（它的地址）—— ★★ **前三样本笔已落（9/9），第四样上一笔落的（9/9）**。
