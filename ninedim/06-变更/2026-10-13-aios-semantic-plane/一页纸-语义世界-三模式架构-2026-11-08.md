# 一页纸：语义世界的三模式架构（讨论稿，2026-11-08）

> **一句话**：底层是统一的系统能力与状态层；上面并列「人类直接经 GUI 操作」「Agent 经工具接口委托执行」「人机通过共享 GUI/状态混合协作」三种模式。
> 人不必经过 Agent，Agent 也不必经过自己的 GUI；GUI 是共用的操作/监督/交接面，Agent 是**可选的委托代理**，不是新的中间收费站。
>
> **归入**：13-aios-worldcore 语义面变更盒（作者令 2026-11-08：「这个是我们语义世界，worldcore 应该放到 13 里面」）。
> **口径**：本页是**通用架构读法**，不绑定任何具体实现；图用纯 ASCII，便于贴进汇报或评审件。本页是讨论稿，不是正式结论。

---

## 0. 先钉术语（防再次混乱）

| 词 | 本页里的唯一含义 | 不是什么 |
|---|---|---|
| **桌面** | **GUI 的表现**：壁纸、主题、图标、窗口边框、排布 | ❌ 不是能力；❌ 不是“剪贴板/截图/点击”的集合 |
| **能力** | 能被**调用**、能被**授权**、能被**审计**的东西 | ❌ 不是“看起来和桌面有关的东西” |
| **剪贴板** | 一个**服务**（系统级缓冲区 + 读写 API） | ❌ 不是桌面 |
| **截图** | 一个**服务**（读屏幕像素，靠合成器） | ❌ 不是桌面 |
| **模拟点击** | 一种**实现路径**（computer-use 的低语义手段） | ❌ 不是能力条目 |
| **Agent** | **可插拔侧链**：把意图翻成工具调用 | ❌ 不是层；❌ 不是必经通道 |

## 1. 总图：底层统一，上层三模式并列

```
┌──────────────────────────────────────────┐
│ 交互与代理层                              │
│  ├─ 人类模式：人 → GUI/快捷键/点击 → 能力接口 │
│  ├─ 委托模式：人 → 语音/文字/Agent GUI/传统GUI委托按钮 → Agent → 工具/API → 能力接口 │
│  └─ 混合模式：人 ⇄ GUI/共享状态 ⇄ Agent → 工具/API → 能力接口 │
├──────────────────────────────────────────┤
│ 业务/应用能力层：文件、应用、网络、设置等 API/服务 │
├──────────────────────────────────────────┤
│ 系统服务与管理层：进程、内存、权限、应用管理、审计等 │
├──────────────────────────────────────────┤
│ Linux 内核：硬件抽象、驱动、系统调用        │
├──────────────────────────────────────────┤
│ 硬件                                      │
└──────────────────────────────────────────┘
```

**三层职责（一句一个）**

1. **Linux 内核**：抽象硬件，提供系统调用。
2. **系统服务与管理层**：管进程、内存、资源、权限、应用、审计。
3. **业务/应用能力层**：把文件、应用、网络、设置封装成**可调用能力**；人和 Agent 最终都落到这一层，**都不直接碰内核**。

                    人（看 · 点 · 说 · 写 · 按 · 拖）

                │ ① 点/键（确定性）             │ ② 说/写/点「帮我办」（委托）

**要点**：**GUI 下面第一批不是 Agent，而是“能力接口”**；Agent 是绕到侧边的一条可选链，最后也必须回落到同一个能力接口。

## 4. 公共部分：四个必须 + 一个可选

| # | 公共部分 | 三种模式怎么用 | 必须吗 |
|---|---|---|---|
| 1 | **GUI（同一张脸）** | 人类模式＝操作面；委托模式＝可选监督面；混合模式＝共享交接面 | ✅ 必须 |
| 2 | **能力接口（统一入口）** | 人直接调、Agent 经工具调、混合两种都调——**走同一个门** | ✅ 必须 |
| 3 | **状态 / 权限 / 审计（同一套家底）** | 三种模式看到同一份状态、同一套策略、同一本账 | ✅ 必须 |
| 4 | **底下三层**（业务能力 / 系统服务 / 内核+硬件） | 谁都不直接碰内核 | ✅ 必须 |
| — | **Agent（可插拔）** | 只在委托/混合时出现；拔掉它，人类模式照旧 | ❌ 可选 |
| — | **入口通道**（语音/文字/按钮/点击/快捷键） | 各模式入口不同 | 入口多样，**门下是同一扇** |

## 5. 三种模式 × 公共部分

| | 人类模式 | 委托模式 | 混合模式 |
|---|---|---|---|
| **入口** | 点/键/拖 | 语音/文字/「帮我办」按钮 | 两者交替 |
| **GUI 角色** | 操作面 | 可选监督面 | 共享交接面 |
| **谁在驱动** | 人 | Agent | 人 ⇄ Agent |
| **状态** | 人自己看 | Agent 经接口读/写 | **双方共享同一份** |
| **确定性** | 最高（人直接点，动作确定） | 中（Agent 翻意图，动作仍确定） | 中（交替，需交接协议） |
| **监管方式** | 无（人自己做） | 可看、可停、可接管 | 看 + 打断 + 接管 |

## 6. 修正版分层：**桌面只是表现，不是能力**

```
┌──────────────────────────────────────────────────────────┐
│ 交互层（表现，不是能力）                                      │
│   GUI：画布 · 窗口 · 图标 · 壁纸 · 主题 · 边框 · 排布           │
│   —— 人在这里看、点、说；这里没有“可调用能力”                  │
├──────────────────────────────────────────────────────────┤
│ 能力层（可调用；一个能力一个条目）                              │
│   文件 · 网络 · 设置 · 应用（各自的 intent/API）               │
│   剪贴板 API · 截屏 API · 可访问性/输入注入（若开放，最高危）     │
├──────────────────────────────────────────────────────────┤
│ 系统服务与管理层                                             │
│   进程 · 内存 · 权限 · 应用管理 · 审计                          │
│   窗口管理/合成器 · 剪贴板存储 · 输入设备                       │
├──────────────────────────────────────────────────────────┤
│ Linux 内核 / 硬件                                          │
└──────────────────────────────────────────────────────────┘
```

**被我塞错的东西，各归其位：**

| 东西 | 真正是什么 | 归哪 |
|---|---|---|
| 壁纸/主题/图标/边框 | GUI **表现** | 交互层（不是能力） |
| **剪贴板** | 系统级缓冲区 + 读写 API | 系统服务层（对外是剪贴板 API） |
| **截图** | 读屏幕像素（靠合成器） | 系统服务层（对外是截屏 API） |
| **模拟点击** | computer-use 的**实现路径**（语义会丢） | 不是能力条目；优先用结构化动作 |
| 窗口管理/合成器 | 系统服务 | 系统服务层 |

## 7. 确定性边界（Agent 语义偏离的兜底）

1. **高频短操作** → 走 GUI / 快捷键 / 确定性脚本；
2. **模糊长流程** → 才交给 Agent；
3. **Agent 优先调用结构化工具**，而不是模拟点击；
4. **高风险动作二次确认**（变更类默认要人批）；
5. **执行可观察、可回滚、可打断纠正**。

## 8. 易错点：“桌面能力”这个词为什么危险

**判据**：**同一层的条目，必须能被同一种授权模型管住。**

同样叫“和桌面有关”，背后是四种权限模型：

| 动作 | 谁能批 | 审计粒度 |
|---|---|---|
| 读文件 | 文件权限 / 沙箱（路径、可见范围） | 一次读写一笔 |
| 读剪贴板 | 剪贴板隐私授权（系统级、通常全局） | 有/无授权，无“哪一段” |
| 截图 | 屏幕录制授权（系统级） | 一次截屏一笔 |
| 模拟点击 | 辅助功能 / 自动化授权（最高危） | 一次点击一笔，但**语义丢失** |

四种授权模型 ⇒ **不能合成一个条目**。所以：

> **桌面 = 表现**（交互层，无能力）；**剪贴板、截图 = 两个独立服务**（各自一个条目、各自一套授权）；**模拟点击 = 一种实现方式**，不是能力条目。

## 9. 外部旁证（2026-11 现取）

**已核：**

- **统信 UOS V25**（2026-10-19 官方《技术开箱·路演》文）：自述 **“9000 余个 MCP、1.2 万余项 Skills、60 余组 AI SDK”**，并自称 **Agent OS**；磐石架构 2.0 含原子更新/自动回滚、关键目录只读、快照提速 80%。
  出处：<https://faq.uniontech.com/1111/ad73>
- **CrabOS**（arXiv:2608.28165v1，PKU，2026-08-28）《An Operating System for Human-AI Co-inhabitation》：工作状态 = **人机共享的自然语言文本对象** + **同一可审计入口**，不用截图/抄写转交；三条原则 = 文本化工作数据、共享可引用工作对象、**统一能力入口（禁止给 AI 的私有工具层）**。
  出处：<https://arxiv.org/html/2608.28165v1>

**未核（不当作证据）：** 微软 MXC 执行容器、HCU 三通道统一接口、OS-Helix、macOS View Annotations、KylinBot 的 MCP 细节。

**旁证结论（一句）**：**“能力统一”铺得快（MCP/Skills 数量），但“治理统一”（主体识别/权限/审计/沙箱）才是真门槛**；委托模式快，是因为它不必改 OS——一旦要求审计与可回滚，速度就掉到“治理统一”或混合模式那一档。

## 10. 一页版（可直接贴进汇报）

> 底层是统一的系统能力与状态层（Linux 系统服务 + 业务/应用能力 + 统一能力接口）；上面并列三种模式：**人类模式**（人经 GUI/快捷键直接调能力）、**委托模式**（人把目标交给 Agent，Agent 经工具/API 调同一批能力）、**混合模式**（人机共享状态、交替操作）。
> **人不必经过 Agent，Agent 也不必经过自己的 GUI**；GUI 是三种模式共用的操作、监督与交接面。Agent 是可插拔的委托代理，**不是新的中间收费站**；它的语义偏离由「确定性边界」（结构化工具、二次确认、可观察、可回滚、可打断）兜住；**桌面只是 GUI 的表现，不是能力条目**。
