# 方案：两个面怎么分工 ＋ 两套协议怎么叠（作者三问）

| 阶段 | 环 | 维 | 版本 |
|---|---|---|---|
| S2 | 意图 | 二 框架 ／ 三 结构 | **0.1（待签）** |

> **作者三问**：「① **他们俩非要传数据呢**，就是要经过语义一级的，首先得通过他们的交互嘛；**人家直接传数据就好了，为啥？怎么个逻辑关系？有没有一套详细的逻辑？** ② **协议分为两种**：一是像 **TCP** 这种**网络协议**，二是**自己定的里面的协议**，对吧？ ③ 就是说**这两个自己包一个协议**什么的，反正是**数据传输**或者**我们的控制指令都在一个协议上跑** —— **基于传统的这种 OS，面对这种情况，他们是怎么传的？**」

---

## 一、★★★ 第一问：为什么数据要先过语义（不是"绕"，是"开单"）

### ★ 五步（次序不许倒）

```
① A 要传 X 给 B        ⇒ 先在【语义面】发一条信封：「A 要把 X 给 B」
② 信封过本体           ⇒ 名字在册吗？A 有权吗？B 在册吗？
③ 过了 ⇒ 发【取件码】   ⇒ 含地址／凭据／有效期（一次性）
④ 【数据面】按码直连搬   ⇒ ★ 不过总线、不再检查、全速
⑤ 搬完 ⇒ 语义面记一笔   ⇒ 「已交付」（可追责）
```

### ★★★ 一句话

> ★★★ **语义面管「准不准」，数据面管「快不快」；数据本身一次都不走语义检查。**
> ★★ 比方：★ **去仓库提货 —— 先在柜台出示证件、开一张提货单（语义面），然后你去库房把货搬走（数据面）**；★ **不用把货再搬回柜台验一遍。** ✓

### ★★ 这个模型在市面上到处都是（不是我们发明的）

| ★ 系统 | ★ 控制面（语义） | ★ 数据面（干货） |
|---|---|---|
| ★★ **S3／对象存储** | ★ 鉴权 ⇒ **返回预签名 URL** | ★ 客户端**直连**搬数据 |
| ★★ **WebRTC** | ★ **信令**（signaling） | ★ **P2P 直连**（媒体流**不经**信令服务器） |
| ★ **Kubernetes** | ★ API Server（鉴权／语义） | ★ **Pod 之间直连** |
| ★ **NFS** | ★ mount／权限 | ★ 直接读写块 |
| ★ **Kafka** | ★ 元数据（topic／ACL） | ★ 分区直传 |
| ★ **DDS** | ★ QoS 声明 | ★ 数据面直传 |

⇒ ★★ **我们的模型 ＝ 「S3 预签名 URL」＋「WebRTC 信令」的合体**：★ **语义面发码，数据面拿码取货** ✓

## 二、★★ 上游实测：它其实"没分"（这就是它的代价）

| 现取 | 命中 | 说明 |
|---|---|---|
| `SCM_RIGHTS`（递 fd） | ★★ **0 处** | ★ 没有用"递文件描述符"这一手 |
| `memfd` | ★★ **0 处** | ★ 没有匿名内存 fd |
| `AF_UNIX` | ★ 2 处 | ★ 几乎不用 Unix socket |
| `shm_open` ／ `mmap` | ★ 4 ／ 8 处 | ★ 很少 |
| ★★ `tonic::` ／ `TcpListener` | ★★ **457 ／ 67 处** | ★★★ **它连本机都走 gRPC over TCP** |
| ★ **`DMA-BUF`** | ★ **159 处** | ★ **唯一例外：图形显示必须零拷贝** |

⇒ ★★★ **上游是"最笨但最通用"的一种：所有东西一个协议跑（gRPC over TCP）。**
★ **代价**：★ **本机上也要过 TCP/IP 栈 ＋ 序列化** ⇒ ★ **大块数据会慢** ✓
★ 这正是作者说的"**控制指令和数据都在一个协议上跑**"⇒ ★★★ **那在小数据上没问题；一大起来就必须分开** ✓

## 三、★★★ 第三问：基于传统 OS，他们（经典系统）是怎么传的

| ★ 机制 | ★ 怎么干 | ★ 谁在用 |
|---|---|---|
| ★★ **控制走 socket，数据递 fd** | ★ AF_UNIX 上发**一条小消息**，用 **`SCM_RIGHTS`** 把**文件描述符**递过去 ⇒ ★ 双方对**同一个 fd** 直读直写 | ★★★ **Wayland**／**D-Bus**／**PipeWire**／**systemd** ✓ |
| ★★ **共享内存 ＋ 环形缓冲** | ★ 双方 `mmap` **同一块内存**，用**环形缓冲**传帧 | ★★ **PipeWire**／**iceoryx**／**X11 SHM** ✓ |
| ★ **`memfd_create`** | ★ 一块**匿名内存**拿个 fd，递给对方 | ★ Wayland／PipeWire／Chrome |
| ★ **`DMA-BUF`** | ★ **显存**缓冲区跨进程共享 | ★ **Wayland 合成器**／视频｜★ **上游用了 159 处** |
| ★ **`io_uring`** | ★ 异步 IO（高性能） | ★ 现代 Linux |
| ★ **`eventfd`／`epoll`** | ★ **只报"有货了"，不搬数据** | ★ 传统 |

### ★★★ 经典答案一句话

> ★★★ **控制走 socket（小消息），数据递一个「文件描述符」过去，双方对同一块内存直读直写（零拷贝）。**
> ★★ **`SCM_RIGHTS` 就是那根「递 fd 的手」** —— ★ 这是 **Unix 上的标准做法**，★ **Wayland／D-Bus／PipeWire 全这么干** ✓✓

### ★★ 于是"取件码"就是它的一般化

| ★ 场景 | ★ 取件码是什么 |
|---|---|
| ★ **同机** | ★★ **一个文件描述符**（用 `SCM_RIGHTS` 递）／**一块 shm 的名字**（`memfd`） |
| ★ **跨机** | ★★ **一个预签名 URL**（★ 像 S3 那样，★ 带凭据与有效期） |

## 四、★★ 第二问：协议确实分两种（作者说得对）

| 类 | ★ 例子 | ★ 谁定 |
|---|---|---|
| ★★ **一：通用网络／系统协议** | ★ TCP／UDP／**QUIC**／**Unix socket**／**共享内存**／`SCM_RIGHTS` | ★★ **现成的，我们不改** |
| ★★★ **二：我们自己定的「里面的协议」** | ★ **本体信封的字段表**（含三张通行证）＋ **取件码的格式** | ★★★ **我们定 —— 那就是我们的活** ✓ |

### ★★ 两层怎么叠（一层套一层）

```
┌──────────────────────────────────────────┐
│ ★★★ 我们的协议（第二类）：本体信封 / 取件码   │  ← 我们定；带 world+vocab_hash
├──────────────────────────────────────────┤
│ ★★ 通用协议（第一类）：TCP / QUIC / socket / shm │  ← 现成的；我们只是"用"
└──────────────────────────────────────────┘
```
⇒ ★★ **我们的协议是「载荷」，通用协议是「运输」** ⇒ ★ **换运输不换载荷** ✓

## 五、★ 三问收口成三条（可写进规格）

| # | 话 |
|---|---|
| **1** | ★★★ **数据不走总线** —— 语义面发码、数据面取货；★ 数据本身**一次都不**过语义检查 |
| **2** | ★★ **协议两套叠着用** —— 我们的**信封／取件码**（我们定）装在**通用传输**（现成）上 |
| **3** | ★★ **同机的取件码就是「一个 fd」** —— ★ 经典做法是 `SCM_RIGHTS` 递 fd ＋ 共享内存；★ **Wayland／PipeWire 是活样本** |

## 六、本件没做的事（如实）

1. ★ **没核** `SCM_RIGHTS` 在**我们的宿主（Windows）**上有没有对应物（★ Windows 是 `DuplicateHandle` ＋ 命名共享内存，★ **不同机制，要单查**）；
2. ★ **没定**取件码的字段表（★ 下一件）；
3. ★ **没测** gRPC-over-TCP 与 Unix socket 的**实测差**（★ 要等有真数据面代码才谈得上）。
