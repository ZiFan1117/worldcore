# 决策（待签）：八个面做成**八个 crate** 还是**八个模块文件夹**

| 阶段 | 环 | 维 | 版本 |
|---|---|---|---|
| S2 | 意图 | 三 结构 | **0.1（决策·待签）** |

> **作者问（逐字）**：「**八个 crate 还八个模块文件夹，这两个哪个好一点**？」

---

## §一 ★★ 判据（用现取的规矩，不凭感觉）

| # | 判据 | 现取 |
|---|---|---|
| **1** | ★★ **NinDim 硬约束 1** | ★ 逐字：「**一个原子一个夹**：13 的形态是 `crates/<crate>/`」⇒ ★★ **即「原子 ＝ crate」** |
| **2** | ★ **那八个面是"原子"吗** | ★ 是：★ 注册／校验／存储／查询／账／执行／治理／导出 —— ★ **各管一摊、各有判据、可独立验** |
| **3** | ★ **它们之间有耦合吗** | ★ 有（校验要用注册表、存储要用校验、治理要拦执行）—— ★★ **但都走接口耦合，不走内部** ⇒ ★ **正好该用 crate 边界强制** |
| **4** | ★ **上游的先例** | ★ 上游 **37 个 crate**（★ 按同样的"一个规格/一个域一个 crate"路子） |
| **5** | ★ **本仓的先例** | ★ `crates/aios-ontology/`（★ 我们的，一个原子一个夹） |

## §二 ★★ 两种做法的对照

| | ★ **八个 crate** | ★ **一个 crate ＋ 八个模块文件夹** |
|---|---|---|
| **边界** | ★★ **编译器强制**（crate 之间只能用 `pub` API，不能偷偷伸手） | ★ 弱（同 crate 内 `pub(crate)` 随便伸） |
| **依赖方向** | ★★ **每个 crate 自己声明** —— **谁依赖谁，编译器管** | ★ 一个 `Cargo.toml`，谁依赖谁靠自觉 |
| **编译** | ★ 改一个只重编它及其上游 | ★ 改一个重编整个 crate |
| **可单独替换/部署** | ★ 能 | ★ 不能 |
| **文件数** | ★ 8 个 `Cargo.toml` ＋ 8 个 `src/` | ★ 1 个 `Cargo.toml` ＋ 8 个 `.rs` |
| **可回退性** | ★★ 要合并很容易（★ 删 `Cargo.toml`、把 `src/` 挪进来） | ★ 要拆出去**难** |
| **符合硬约束 1** | ★★ **符合**（原子＝crate） | ★ 不符合（模块不是"夹"） |

## §三 ★★★ 本席建议：**八个 crate**，但**加一个"共同类型"底座**

★ **为什么加底座**：★ 八个面**都要用**同一批类型（`Refuse`／`Registration`／`Event`／`Who`…）⇒ ★ **若各写一份，就重复了**（★ 正是作者先前点出的病）✓

```
★ 底座（谁都不依赖它、大家都依赖它）
   aios-worldcore-types        ← 共同类型：Refuse / Registration / Event / Who / Reason

★ 门面（调用者只认它；它 pub use 八面）
   aios-worldcore              ← 门面 crate（薄）

★ 八个面（各一个 crate，各自依赖底座）
   aios-worldcore-registry     ← ① 本体注册 ＋ ② 实例注册   ★ 作者点名先做
   aios-worldcore-validate     ← ③ 校验（进门安检）
   aios-worldcore-store        ← ④ 实例存储
   aios-worldcore-query        ← ⑤ 查询
   aios-worldcore-ledger       ← ⑥ 账
   aios-worldcore-execute      ← ⑦ 执行
   aios-worldcore-governance   ← ⑧ 治理
```

⇒ ★★ **合计 10 个 crate**（★ 底座 1 ＋ 门面 1 ＋ 八面 8）✓
★ **依赖方向单向**：★ `registry／validate／store／…` → `types`；★ 门面 → 八面 ✓

## §四 ★ 如果你嫌 10 个太多：折中方案（本席也接受）

★ **先做 2 个**：

```
   aios-worldcore          ← 门面 ＋ 共同类型 ＋ 八面（先做成八个模块）
   （将来哪个面长大／要独立部署，再把它提升成独立 crate）
```

⇒ ★ **好处**：★ 起步快、文件少；★ **坏处**：★ 边界靠自觉（★ 而边界一松就会烂）
⇒ ★★ **本席判断**：★ 若目标是"**最小内核先跑通**"⇒ **折中够用**；
★ 若目标是"**这八个面长期各自长**"⇒ **八个 crate 更好** ✓

## §五 ★★ 本席的一句话推荐

> ★★ **八个面各一个 crate** —— ★ 因为★ **NinDim 的硬约束就是「一个原子一个夹（crate）」**，★ 而★ **八个面各自就是一个原子**；
> ★★ **而且边界由编译器强制**（★ 模块做不到这一点）—— ★ **这是"不要重复"与"不要乱伸"的机器保证** ✓
> ★ **代价**：★ 多几个 `Cargo.toml`、编得稍慢 ⇒ ★ **换来"边界不会烂"** ✓

## §六 本件没做的事（如实）

1. ★ **没建**任何 crate（★ 等作者签字再动）；
2. ★ **没定**门面 crate 的名字（★ `aios-worldcore` 是暂用名）；
3. ★ **没估** 10 个 crate 的编译时间代价。

## §七 ★★ 附：底座那 5 个类型是什么（作者问 `Refuse / Registration / Event / Who / Reason`）

| 名字 | ★ 中文 | ★ 它是什么 | ★ 长什么样 |
|---|---|---|---|
| `Refuse` | ★ **"拒"** | ★★ 系统说"不行"时返回的那个东西（★ 带理由） | ★ `Refuse { kind: "FROBNICATOR", reason: UnknownKind }` |
| `Registration` | ★ **"要登记的那样东西"** | ★★ 一次注册请求的内容：★ 类型名 ＋ 各格填了什么 | ★ `Registration { kind: "application", fields: {name:"htop"} }` |
| `Event` | ★ **"发生的一件事"** | ★★ 账本上记的一行：★ 谁、何时、做了什么 | ★ `Event { seq:42, who:"world://user/zhang", what:"package.install" }` |
| `Who` | ★ **"谁"** | ★★ 做这件事的那个主体（★ 名字／身份） | ★ `Who = "world://user/zhang"` |
| `Reason` | ★ **"为什么"** | ★★ 拒绝的理由（★ 机器认的码） | ★ `UnknownKind`／`MissingField("name")` |

### ★★ 为什么它们要单独放底座

★ **八个面都要用这一批**：★ 注册面（`Registration`／`Refuse`）／校验面（`Refuse`／`Reason`）／账面（`Event`／`Who`）／执行面（`Who`／`Event`）／治理面（`Who`／`Refuse`）。
★ ⇒ 若各面各写一份 ⇒ **就会有 8 份"拒"、8 份"谁"**（★ 正是作者点出的"重复"病）⇒ ★★ **放底座，八面共 use 一份** ✓
★ **大白话**：★ **底座 ＝ 大家共用的那本小词典**（★ "拒"长什么样、"谁"怎么写、"一件事"怎么记，只说一遍）✓

### ★★★ 更要紧：它们**不是新发明**，每个都能指回本体

| 底座类型 | ★ 本体里对应 |
|---|---|
| `Who` | ★ `envelope.actor`（信封里的"谁"） |
| `Event` | ★ `envelope`（信封）＋ `families`（四族 change／act／notice／job） |
| `Refuse`／`Reason` | ★ `Reject`（`aios-ontology` 已有错误码，如 `ext.world.Ontology.ActionUnknown`） |
| `Registration` | ★ `objects.<类>.fields`（每类有哪几个格） |

⇒ ★★ **即：这 5 个类型"每个都能指回本体的一处"** ⇒ ★ **这就是"围着本体转"** ✓
