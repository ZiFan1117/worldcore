# 分工边界 · OpenSpec 与软件开发流程谁管什么

> **本件是 `fc-2026-001` 的附表**，用途是**判据**：以后每遇到一件事，先查这张表决定它归谁管。
> **一句话规则（作者裁定）**：**OpenSpec 有的，遵循 OpenSpec；OpenSpec 没有的，遵循软件开发流程那一套（国标／国际标准的经验）。**
> **两条附则**：① 两边都有但深度不同时——**OpenSpec 管形态，流程管内容**；② **同一件事只在一个地方落笔，不另抄一份、不设"一行指针"式的双份登记。**
>
> **流程侧原文出处**（本表逐条有据，**原件在本仓内**）：`refs/refs/_料/process-source/06-swe-gb/docs/01-流程与阶段/阶段流程与交付物.md`（S0–S7 交付物与门禁、H-01…H-26）、`refs/refs/_料/process-source/06-swe-gb/docs/02-评审与门禁/评审门禁与检查单.md`（R0–R8、准出准则、评审有效性规则）。

## 一、OpenSpec 有的 → 用 OpenSpec

> **本节的"有"只算原生那一份。** 实测：原生 `spec-driven` 的产物是**四个**——`proposal`／`specs`／`design`／`tasks`；
> `review` 不在这四个里面（出处：`openspec schemas --json`，原生那一条的 `"artifacts": ["proposal","specs","design","tasks"]`，
> `"source": "package"`）。**`review` 是本项目 `docs/schemas/opsx-swe-gb/schema.yaml` 自加的第五件**，
> 故它连同"结论枚举"一起列在 **§2.2**（归流程，载体落在 change 上），**不在本节**。

| 事项 | OpenSpec 的载体 | 说明 |
|---|---|---|
| **一次改动的产物链（原生四件）** | change 下的 `proposal` → `specs` ∥ `design` → `tasks` | 这四件的产物名、依赖顺序、阻塞关系由 schema 定，不另立一套。本项目的 `review` 是**自加第五件**（见 §2.2） |
| **"这件事应当是什么行为"** | `specs/<能力>/spec.md`：`### Requirement` ＋ `#### Scenario`（WHEN/THEN） | **这就是需求规格的机读子集**——需求内容写在这里，不再另写一份"需求条目" |
| **变更的 delta 语义** | `## ADDED／MODIFIED／REMOVED／RENAMED Requirements` | 增删改名的四种写法由 OpenSpec 定 |
| **形态校验** | `openspec validate`（Requirement/Scenario 结构） | **它只管形态**，见 §三。**它不是门禁**：`validate` 红了不拦任何动作，拦不拦由 §2.2 的评审与守卫脚本决定 |
| **归档后 lint** | `openspec validate --archived`（只查已归档 change 的 tasks 全勾） | 原生 CLI 自述用途为 "for pre-commit linting"（`openspec validate --help`，逐字），**且实测只查勾**：已归档件 `review.md` 通篇"待签"，它照样 `✓`（见 §三末「实测读数」） |
| **规格基线** | `ninedim/01-意图环/04-规格/`（归档时 delta 合并入册） | 这是"这台东西今天承诺什么"的权威载体 |
| **改动状态与进度** | `openspec status`／`list`／`show`／`instructions` | 不另做进度表 |

> **本项目的两件自加物**（原生没有，逐条见 §2.2／§2.3）：
> ① **`review.md`**——第五件产物，评审与签字的载体；
> ② **Scenario 末尾的证据行** `- **证据**：<path>::<fn>`——规格级的机读栏位，本项目加在 Scenario 上，`validate` 不校验它。
> 逐字出处：`docs/schemas/opsx-swe-gb/schema.yaml:136-139`（`- id: review` / `generates: review.md`）；
> 同一件 `:53-55`（`- **证据**：`path/to/test_file::test_name`（或 `tools/x.py --self-test`）` /
> `证据行的测试名必须是**真实存在**的。OpenSpec 的 validate 不校验这一点`）。

## 二、OpenSpec 没有的 → 跟流程

**OpenSpec 通篇没有"角色"这个概念**（它允许 agent 自己 propose → apply → archive），所以下面这些一律跟流程。

### 2.1 阶段与阶段交付物（S0–S7）

| 阶段 | 流程要求的交付物 | OpenSpec 有对应物吗 | 归谁 |
|---|---|---|---|
| **S0 立项** | 可行性研究报告、项目开发计划（含**裁剪说明**）、软件质量保证计划、软件配置管理计划、风险清单 | **无** | **流程** |
| **S1 需求** | 软件需求规格说明（SRS）、接口需求规格说明、**需求追溯矩阵 RTM**、需求评审记录 | **部分**：`specs/` 是需求的机读子集；SRS 的文档形态、RTM、评审记录**无** | 需求**内容** → OpenSpec 的 `specs/`；**文档形态与 RTM** → 流程 |
| **S2 框架设计** | 概要设计说明（HLD）、模块清单与模块号登记表、模块接口契约、框架基线 | `design.md` 是**变更粒度**的；HLD／模块号／契约／框架基线是**项目粒度**的，**无** | `design.md` → OpenSpec；**其余 → 流程** |
| **S3 骨架跑通** | 可运行骨架、冒烟测试用例与记录、CI 流水线配置、验证记录 | **无** | **流程** |
| **S4 模块实现** | 详细设计说明（按模块增量）、**模块代码**、单元测试用例与记录、**覆盖率报告**、框架变更申请与影响分析、框架基线 | `tasks.md` 与 `design.md` 的影响分析**有**；LLD／**模块代码**／覆盖率报告**无** | 影响分析 → OpenSpec；**LLD／模块代码／覆盖率 → 流程** |
| **S5 集成与系统测试** | 集成测试计划/说明/报告、系统测试计划/说明/报告、缺陷清单、**覆盖率与追溯矩阵更新** | **无** | **流程** |
| **S6 验收与交付** | 验收测试报告、用户手册、版本说明、产品基线、验收评审记录 | **无** | **流程** |
| **S7 运维与回归** | 变更申请与影响分析、回归测试报告、版本说明、发布评审记录 | **change 的申请＋影响分析有**；其余**无** | change → OpenSpec；**其余 → 流程** |

### 2.2 评审与门禁（R0–R8）

> 流程原文的三种结论形式、准出准则、谁主持谁必参，OpenSpec **一概没有**。

| 编号 | 评审 | 时机 | OpenSpec 有对应物吗 | 归谁 |
|---|---|---|---|---|
| **R0** | 立项评审 | 项目启动前 | 无 | 流程 |
| **R1** | 需求评审 | 需求基线建立前 | 无 | 流程 |
| **R2** | 框架（概要设计）评审 | 框架基线建立前 | 无 | 流程 |
| **R3** | 骨架跑通评审 | 骨架可运行后 | 无 | 流程 |
| **R4** | 模块评审 | 每个模块完成时 | 无；**但载体可以落在 change 上** | 流程，**载体 = `review.md`** |
| **R5** | 框架变更评审 | 每次框架变更申请时 | 无；**同上** | 流程，**载体 = `review.md`** |
| **R6** | 测试准出评审 | 系统测试完成 | 无 | 流程 |
| **R7** | 验收评审 | 验收测试完成 | 无 | 流程 |
| **R8** | 发布评审 | 每次版本发布前 | 无 | 流程 |

⇒ **这就是 `review.md` 为什么必须是第五件产物**：OpenSpec 没有评审与签字，流程有——按判据"没有的跟流程"，它就该在；而"不另立册子"这条又要求它**长在 change 上**。

> **它是自加件**：原生 `spec-driven` 只有 `proposal`／`specs`／`design`／`tasks` 四件（`openspec schemas --json`，`"source": "package"` 那一条），
> `review` 由本项目 `opsx-swe-gb/schema.yaml` 加为第五件。**故 §一 不再把它写作"OpenSpec 有的"。**
>
> 同样的自加件还有 **Scenario 末尾的证据行** `- **证据**：`：它归"需求内容"这一面（形态上属于 `specs/`），但**原生没有这一格**，
> `openspec validate` 也不校验它——它的执行者是 `spec_bridge.py` 判据②（见 §2.4 H-21 行）。
>
> **结论枚举也在本节这一档**（流程有、OpenSpec 没有，逐字出处 `附件三-评审与门禁.md:96-97` 的「结论形式」列）：
> **R4 ＝ 通过／有条件通过／退回**；**R5 ＝ 批准／驳回**。**两个档位的取值不许混用**
> （同件 `:417`：「**只有三种结论**：通过 / 有条件通过（附条件清单与期限）/ 退回」，且
> 「自创选项（"原则通过""基本通过""待补充后通过"）→ **无效结论，门禁不予放行**」）。
> 载体：`templates/review.md` 的 §一「结论」栏 ＋ §八「结论与后续」（**两处都按档位分列**）。

### 2.3 全阶段贯穿要求（流程侧标注"不可裁剪"）

| 流程要求 | OpenSpec 有对应物吗 | 归谁 |
|---|---|---|
| 需求基线 + RTM 双向可追溯 | 规格基线有（`specs/`）；**RTM 无** | 基线 → OpenSpec；**RTM → 流程** |
| 配置管理与版本化（全部配置项纳入版本控制） | OpenSpec 管自己那批文件；**"配置项清单"概念无** | 版本控制 → git（流程）；不另设清单副本 |
| 有记录的系统级测试，可复现 | **无原生对应物**；本项目用 Scenario 末尾的证据行做机读锚点 | OpenSpec（证据行，**自加**）＋ 流程（测试报告） |
| 文档与代码不漂移 | 无；`spec_bridge.py` 判据② 只在"证据锚点失效"（函数不存在）时判红——**漂移与仅改名两种，它就判不了** | 流程 ＋ 守卫脚本（**能力有边界**） |
| **AI 生成内容必须人工确认／不代签** | **无** | 流程（载体 `review.md` 的签字栏） |
| 承诺与实现一致（每处"已实现／已防护"都要能指向命令或测试） | **无原生对应物**；证据行是本项目自加的机读形态，**只到"证据锚点存在"这一级**——"该测试断言的真是那句话"它判不了 | OpenSpec（证据行，**自加**）＋ **流程加强**（见 §三「两边都有、但深度不同的」那一档） |
| 辩证处置评审意见（先复算前提、反驳是合法输出） | 无 | 流程 |

## 三、两边都有、但深度不同的 → **OpenSpec 管形态，流程管内容**

这一档是**最容易出错**的地方，也是 46 条审计发现的根因所在。

| 事项 | OpenSpec 管的（形态） | 流程管的（内容） | 出事形态（本项目实见） |
|---|---|---|---|
| **规格是否合格** | `openspec validate`：Requirement/Scenario 结构齐、每个 Scenario 恰好 4 个 `#` | **技术内容是否被评审并给出裁定**（H-24：「格式齐备」与「内容已裁定」**分列两条准出，只有前者不算过**） | 基线自报"6 份规格 / 40 条证据 / 0 条未命中"——**那是形态**；语义层 46 条对不上，**无人核过** |
| **承诺与实现是否一致** | 证据行指向的测试**存在**（`spec_bridge.py:102-119` 实查"文件在 ＋ `fn <名字>(` 在"） | **该测试断言的真是那句话**（断言与声明相符见 `评审门禁与检查单.md:272`／`:276` 反面清单 #5／#9；H-21 本身只要求"能指向命令或测试位置"，见 `附件二-阶段流程与交付物.md:655`） | 40/40 名字命中、跑完全绿；其中 5 条把书里判红的东西写成了绿 |
| **判据可判定性** | Scenario 有 WHEN/THEN | **操作定义＋比对对象＋期望值/阈值＋一个反例**（H-03） | 规格写"只允许白名单主体**并**加摩擦"，而出厂配置下二者不可能同时为真 |
| **验证面独立性** | 无 | **不得用被测实现自身的解析器**；反例必须真的会失败（H-16） | `project check` 自己渲染两份、自己比，三个不等分支**结构上不可达**（恒绿） |
| **冻结与复验** | 有对应概念 | 评审对象＝冻结 blob ＋ 提交号（H-10） | 台账三处引 `src/main.rs:394–397`，而该分支现在在 `:407–410`（行号漂移） |

⇒ **结论：OpenSpec 的绿只证明"形态对"；"内容对"必须另有承担者。** 本项目的承担者就是流程侧那套评审与硬条款——但它的载体只应出现在**一处**：change 的 `review.md`（评审与签字）＋ `spec_bridge.py`（可机核的那几条）。

## 四、这张表怎么用（三条落地）

1. **改融合档的文字以本表为准**：`docs/schemas/opsx-swe-gb/schema.yaml` 与 `README.md` 里"同一批文件双读：流程侧只留一行指针"这类写法——**删掉**；改成"OpenSpec 那一套是唯一产物；本表里判给流程的那些，作**件内栏位与附表**存在"。**同类还有一处**：把 `review` 或证据行写成"OpenSpec 有的"——按 §一 的实测口径，二者都是**本项目自加件**。
2. **`spec_bridge.py` 的各条判据，全部落在"OpenSpec 能机核的那一半"**（**条数以 `--json` 的 `passed`/`failed` 为准，本件不复述总数**）：判据① 归档硬前置、② 证据存在性、③ 默认档、④ 编号桥覆盖、⑤ 覆盖在册、⑥ 归档件已签、⑦ 让路登记（出处 `spec_bridge.py` 的 `--self-test`，实测 rc=0 时逐条打印"反例①—⑦已红 OK"；⚠ 该脚本头部 docstring 仍写"五条判据"，**文档与实现不同步**，以实测为准）。**内容那一半（"断言是否与声明相符"／H-24）机核不了，只能由评审签字承担**——`review.md` 里必须写明这一点，不许含糊。
3. **以后每遇到一件新事，先查本表**：表里判给 OpenSpec 的，按 OpenSpec 做；判给流程的，按流程做；**两边都有的，形态随 OpenSpec、内容随流程**。
