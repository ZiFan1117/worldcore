## 第 2 格 · `review.requires` / `apply.requires` 的**结构错位**（R5 前置闸在 CLI 判定面外）

### 实况（现取，逐字）

```
ninedim/records/openspec-流程件/schemas/opsx-swe-gb-atom/schema.yaml:300  apply:
ninedim/records/openspec-流程件/schemas/opsx-swe-gb-atom/schema.yaml:301    requires: [tasks]
ninedim/records/openspec-流程件/schemas/opsx-swe-gb-atom/schema.yaml:302    tracks: tasks.md
ninedim/records/openspec-流程件/schemas/opsx-swe-gb-atom/schema.yaml:247  - id: review
```

- 同一份档 `:260-261` 逐字「**未获 R5 批准不得进入实施**」、`:305-307` 逐字「`review.md` 的 R5 节必须已签」——
  **这两句写在 `instruction` 里**；`instruction` 是**打印给 AI 读的指导文本，CLI 不解析、不会因此 rc≠0**。
- 上游 skill 逐字（`.pi/skills/openspec-propose/SKILL.md:106`）：
  「Create ALL artifacts needed for implementation (as defined by schema's `apply.requires`)」
  ⇒ **R5 的批准状态不在任何判定面内。**
- **代价已实现过一次**：`changes/agentd-in-rust-into-worldcore/tasks.md:3-11` 逐字自认
  「第 1 组的前三笔……**在未获 R5 批准之前就已实施并入库**」「**责任在執行者，不在任何人**」。
  五席给出的定性：**「不是纪律松，是结构允许。」**

### ★ 实测（2026-09-28，本轮补跑；此前只是"静态可推"）

席③ 当时把这一条标为"**需跑命令才能定**"。本轮跑了，**证据比预期更干净**——
用**本批新立的 R5 件**（它的 `review.md` **今天就是未签的**）做受测对象：

```
$ openspec instructions apply --change wc-fc-2026-006-gate-integrity --json
state   : ready
missing : （空）
```

同一命令对在办件 `agentd-in-rust-into-worldcore` 也给 `state: ready`。

⇒ **两条一起看，机制就清楚了**：
1. `review.requires: [tasks]` **只判"文件在不在"，不判签没签** ⇒ 一份**未签**的 `review.md` 也让 `review` 显示 `[x]`；
2. `apply.requires: [tasks]` **根本不含 `review`** ⇒ `apply` 在 R5 未批准时就 `ready`。

⇒ **"未获 R5 批准不得进入实施"这句话，在 CLI 的判定面里不存在。**
（另：该件 `apply` 的 `requires` 回显为空，说明 CLI 不回显 artifact 级依赖——这条**只作旁证**，不作判据。）
