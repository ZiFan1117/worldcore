## 二、测试环境与数据纪律（**硬约束**）

1. **一律用一次性沙箱账本**（`mktemp -d`，退出即删）：**绝不触碰真实账本**
   ——依 `06-swe-gb` 幂等口径修订：命令幂等，**数据操作天然不幂等**；
2. **确定性**：不依赖 sleep / 网络 / 外部服务；不断言墙钟（`at`/`id` **不进** `State`、不进指纹）——
   教训来自 `07-agent-native-os` 的"完工铃丢铃"竞态；
3. **执行顺序无关**：测试名在输出中的次序由并行执行决定，结论不得依赖顺序；
4. **两类环境都要跑**：VM（`cargo test --locked` + `check.sh`）与 CI（GitHub Actions）；
   二者结论不一致时**以 CI 为准**，并把差异登记为环境类风险。

## 三、通过/不通过准则

| 判据 | 内容 |
|---|---|
| **阻断式** | 任一层失败即不通过；CI 五个作业**严禁 `continue-on-error`**（`ci_self_check.py` 专责检查） |
| **失败路径必须有反例** | 每道门禁都要有"**会失败**"的证据：`scope`（PR 正/反例）、`traceability`（5 类错误数据）、`gate`（越权/摩擦/静态墙）、`readmodel`（3 类坏账本）、错误码契约（`c15`） |
| **反假测试** | 关键等价性断言必须附"若实现是常量则必须失败"的对照（如 `t7` 的前缀对照、`c15` 的散文反例） |
| **未校验要说出来** | 工具未生效时必须显式打印（如"模块登记表尚未建立"），**不得静默通过** |
| **证据四要素** | 命令 + 原始输出 + **代码提交号** + 用例编号 ↔ 需求映射（见 `WC-RE09-003`） |
