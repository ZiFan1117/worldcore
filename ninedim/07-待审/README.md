## 性质与纪律

1. **为什么在这里**：依项目负责人 2026-09-26 指示「**把现在所有的东西都切割清楚，S0 的就是 S0 的，
   一个阶段一个阶段往前走，别跳什么 S1 的东西，就分割出去；下一阶段能利用的再利用**」。
2. **依据**：`06-swe-gb/docs/评审类/01-阶段评审记录.md` **铁律一**——"没有准出结论，不进入下一阶段；
   ……下一阶段的一切工作都属于**未授权开工**，**其产出不进入基线**"；`WC-SCMP-001` §8.4 **`G-20`**。
3. **可读、不可认**：这批材料**可被引用为现状事实 / 缺口 / 风险 / 可判定性支撑证据**；
   **禁止**作为任何门禁的判据或准出依据（承 `WC-SDP-001` §3.4A.1「可以读、不得认」）。
4. **不进入任何基线**：见 `WC-SCMP-001` §4.2 **表 I**（阶段外提前起草产物登记表）。
5. **移动方式**：**全部为 `git mv`**（历史保留）；**未删除、未复制、未改动任何内容**。
   移动提交 = **`ccf4333`**（18 份，`git show --name-status` 逐条为 `R100`）。
6. **启用后的回迁**：对应阶段准出并签署后，把该子目录**整体回迁**到 `docs/<Sn-…>/`，
   同步 `WC-SCMP-001` §4.2 表 I 的「是否进入基线」列与存放位置列，并在 `G-20` 登记撤销记录。

## `_非本项目样例/` 的单独说明

该子目录的 2 份**不是本项目的世界核心内容**，而是**上游模板库的示例数据**（原 `ninedim/records/demo/`）：
- `需求追溯矩阵.csv` 的内容是"提交订单 / 订单查询 / 单笔订单响应时间"等**电商订单域**样例，
  实现位置写 `skeleton/modules.py::OrderService.submit_order`——本项目**没有** `OrderService`、
  也**没有** `skeleton/modules.py`（实测：这两个符号在本项目内**只出现在 `scripts/verify/trace_matrix.py`
  与上游 `templates/` 的说明文字里**，无任何本项目落点）。
- `软件需求规格说明.md` **首行自述**："本文件是 `scripts/verify/trace_matrix.py` 的**示例数据**，
  用于演示 RTM 与 SRS 的一致性校验。真实项目请从 `templates/02-需求类/01-软件需求规格说明.md` 拷贝后填写。"
⇒ **判为非本项目样例**（判定依据见本节两条实测）。⚠ **该判定所引的台账编号 `WC-SCMP-001` §8.4 `G-68`
在库内尚不存在**（批次六被中断时未落笔；可核：`git grep -n "G-68" -- docs` 只命中本文件）
⇒ **属悬空引用**，登记为【待登记】，**不得**被当作已登记的结论引用。**永不启用**；
保留于此仅供 `scripts/verify/trace_matrix.py` 的 **`--sample` 显式自证模式**取用
（⚠ **不是**默认输入：默认输入＝本项目真实产物；样例数据在未显式加 `--sample` 时会被工具**直接判不通过**，
见批次七对"样例悄悄顶替真实输入"这一回归的修复）。
