## 一、为什么建这棵树（**一次事故长出来的**）

**事实（2026-09-28，现取命令见「本树事实」表下的核法）**：我在**共享主工作区**里把
`WC-MODREG-001` 的改动**落盘但尚未提交**时，**另一条线在同一段窗口里 `commit`** ⇒
**我的改动被它的提交 `72c0269` 一并卷走**（该笔的消息只描述它自己那半 ⇒ 通知单**追溯会撞墙**）。

- **形态**：`72c0269` 对 `WC-MODREG-001` 的 numstat ＝ **68 插 / 12 删**，而那是**两条线的改动叠在一个文件里**；
  其中「§2 六栏 ＋ §3.1」是**原子化设计线**的，「§2.1 的 `src/agent/` 登记行」是另一条线的。
- **完整登记见 `冲突总账.md` §7.18（另一条线记它那半）与 §7.19（本线记这半）。**

**根因（一条）**：**多条线共用同一棵树 ＋ 共享同一个 index（暂存区）**，
而 `git add` 与 `git commit` 之间**不是原子的**。

**⇒ 已证伪的办法**：`冲突总账.md` §7.18 原提的「提交前两步核 ＋ 提交后数文件」
**只能事后发现，不能预防** ✗（同形态在一天内发生过**两次**：`72c0269` 与 `74dc9bc`）。

**⇒ 结构性解法（委派者已批）**：**每条线各自独占一棵工作树**——
`git worktree` 给每棵树**自己的 index** ⇒ 不存在"别人 commit 我的暂存"这件事。

## 三、本树里的提交纪律（委派者裁定，立即生效）

1. `git add` **一次一条命令、只写自己的声明路径** ✗ 禁止 `-A`／`-u`／`.`；
2. **提交前**看 `git diff --cached --name-only`；**提交后**才核 `git show --name-only HEAD`／`--stat`；
3. **推送路线（本树 ⇒ `main`，fast-forward only）**：
   **本树 `commit`** ⇒ `git fetch` ⇒ 核 `origin/main` 有没有又前进（前进就再 `rebase`）⇒
   **主工作区** `git merge --ff-only wt/atom-design` ⇒ **主工作区** `git push origin main`。
   ✗ **任何情况不可** `--no-ff`／造 merge commit／`--force`／`--amend` 已推送历史。
   （为什么走这条：`main` 已在主工作区检出，同一分支**不能在两棵树同时检出**——这条路线保的是
   **同一个 `main`、无 force、fast-forward**。）
4. **别人的件里发现问题：只登记、不动手**（skill §十四）。
5. **主工作区里别人的未提交件，一个都不许碰、不许暂存**；若发现**索引里有不属于我的滞留件** ⇒
   **只 `git restore --staged` 它们**（**不动内容**），并把这件事记进本件。

## 四、本件不能证明的事

- 它**不能**证明"以后再也不会发生暂存被卷走"——**它只把发生条件去掉**（不再共享 index）；
  若有人**同时在这棵树里干活**，问题会以别的形态回来。
- 它**不是**"工区已隔离"的机器判据：**没有任何门禁会读本件**（`spec_bridge.py` 不读 `ninedim/01-意图环/01-策划/**`）；
  本件的"事实"栏也**没有**会红的断言 ⇒ **判断它准不准只有人核**。
- 它**不能**保证我这条线此前的四笔提交（`e97a315`／`eee65a8`／`fdb4dc9`／`c3ede56`）在**归属上**没问题——
