## §0 一句话：这条"主线"到底是什么

它是一条**两个面、一个信封**的线：

- **主干道（语义面）**：一封一封的信封，落到**只追加的账本**上。账本是唯一真相。
- **旁道（内容面）**：字节（文档、二进制）。**字节不进账本**，账本里只留它的指纹（摘要）。
- **总线本身不产生事实**：它只是账本的**投影 + 许可的**执行点 + 一个**投递面**。

```
                第 4 层（上层：GUI / Agent / 执行者 / 应用 / 会话）
                                   │
        ┌──────────────────────────┴──────────────────────────┐
        │                      总  线                        │
        │   ┌────────────────────┐    ┌────────────────────┐  │
        │   │ 主干道 · 语义面    │    │ 旁道 · 内容面      │  │
        │   │ 信封（UTF-8 行）   │    │ 字节（按摘要寻址） │  │
        │   │ kind/id/seq/at/    │    │ content://<algo>:  │  │
        │   │ actor/to/trace/    │    │ <digest>           │  │
        │   │ flags/body         │    │ 清单(manifest)     │  │
        │   └─────────┬──────────┘    └─────────┬──────────┘  │
        │             │  同一协议，`plane` 判别 │             │
        │   ┌─────────┴─────────────────────────┴──────────┐  │
        │   │ 闸：口→身份绑定 · to 路由 · 许可(default deny)│  │
        │   │     只追加 · 读法不持状态                     │  │
        │   └─────────┬─────────────────────────────────────┘  │
        └─────────────┼───────────────────────────────────────┘
                      │  ★ 唯一接合点：只有 actor（或翻译官）能落一封 change/notice
        ┌─────────────┴─────────────┐        ┌────────────────────┐
        │ 第 2 层 · 账本（唯一真相）│        │ 内容库（字节，非真相）│
        │ 只追加 · 撤回靠再写一条   │        │ 摘要即地址 · 只读     │
        └───────────────────────────┘        └────────────────────┘

  铁律落点（逐条挂在图上）：
   ① 一个事实一个权威载体 → 账本写状态，内容面写字节，两份不许互相抄
   ② 许可来源在世界、default=deny → 闸查账本/本体，不查总线内存
   ③ 申报 ≠ 授权            → "我上线了/我持这份文档"不产生任何通行
   ④ 读法不持状态           → 位点在信里(收件人自己的 --since)，不在口上
   ⑤ 世界的话 vs 机器的话   → 机器帧（重试/超时/到货/摘要）不许自签落账
   ⑥ 账本只追加             → 撤回=再写一条；删字节≠撤事实
   ⑦ 读数不写死             → 摘要/长度读时现算；在册≠上线
```

## §3 合并后的清单（按依赖排序）

排序原则：**上一层没定，下一层没法写判据**。每条给四样：**今天 / 该怎么走 / 会红 / 谁提的**。
「谁提的」里的编号：① 统一协议 ② 现成技术 ③ 账本不装二进制 ④ 总线不得成绕过口 ⑤ 身份与授权 ⑥ 原样线路帧。

## §4 六席之间的分歧（逐条，不和稀泥）

> 格式：**分歧** → 甲说／乙说 → **今天工作区支持哪一边** → **要什么读数才能定**。
> 凡"工作区支持"一栏写"都不支持"的，就是**纯设计裁决**，只能由作者裁。
>
> **六席对号**（下文一律用①–⑥指代）：① 统一协议（语义为主干／内容为旁道）｜② 现成技术角度（总线可借做法评估）｜③ 账本不装二进制（指纹进账本、字节走旁道）｜④ 总线不得成为第二个绕过世界的口（门槛／禁止／判红）｜⑤ 身份与授权（谁在说话、凭什么）｜⑥ 原样线路帧（过路不改帧、不持真相）。
> ⑥ 与④大量重叠；本文按它自己的主张单列，不和稀泥地并成一条。

**D1 · 旁道是"带许可的拉"还是"可以推"？**
甲（①③④）：首选拉——推会把"谁收"变成口的状态，读法就不持状态了；default=deny 也没了落点。
乙（②）：现成技术里推是常态（NATS/JetStream/Kafka 都是推+游标）；MQTT 的 retained/session 更是纯推。
**实仓**：今天**只有拉**（`subscribe --since`），没有任何向后推。→ 支持甲，但**这不是裁决**，只是现状。
**要什么读数才能定**：一条"若做推，收件人集合由世界声明在哪一格"的落点；没有它，推 = 口持状态。

**D2 · 内容面是复用 `world.sock` 还是另开 listener？**
甲（②）：单连接 `max_connections=1` 与二进制内容必然撞上一条连接的带宽与内存 ⇒ **必须分**。
乙（⑤④）：另开一条**无身份**的口 = 把"今天分不出谁在说话"复制一份 ⇒ 要么同口、要么新口也带身份绑定。
**实仓**：两边都对得上——`max_connections` 文本写 1（②的事实成立），而在册表里每个口都绑一个 actor（⑤的要求今天已满足）。**两句话合起来才是答案：分口可以，但新口必须进在册表并绑身份。**

**D3 · 账本完整性：单写者够不够？要不要 Merkle/透明日志？**
甲（②）：上树头 + 包含证明 + 一致性证明（CT/Rekor），否则"没被截断、没有第二本账"没有会红的读数。
乙（无人反对，但③④⑥都只主张"只追加+撤回形态"）：今天有前向 `chain`，够判"逐环是否自洽"。
**实仓**：**甲更贴近事实**——`chain` 锚点只有 genesis，**尾部整条删除不可检出**已在 `WC-CR-006` K-1 登记；`main.rs` 却打印"局部篡改可检出"。
**要什么读数才能定**：世界是否**永远单写者**。若永远单写者，指纹链+单签可能够；若会多写者，多签+每个写者的密钥注册都得做。**背景没给这条。**

**D4 · 一口一主体 还是 一口多主体？**
甲（⑤）：按主体开口；`max_connections=1` 让"每口一主体"与"同主体多会话"不可兼得，必须择一。
乙（⑥④）：口只当信道，靠帧 `actor` 区分；路由只按帧里声明的 `to`。
**实仓**：今天**桥在中间**——在册表一个口绑一个 actor（支持甲），而通道请求里的 `actor` 只是"自称"且允许缺省（支持乙的形态）。
**要什么读数才能定**：世界对"会话"有没有定义。**背景没说。**

**D5 · `to` 的粒度：单个 actor / 角色 / 组？**
甲（①）：先按单个 actor。
乙（④⑥）：`to` 必填，路由按它转发；未提组。
**实仓**：`ontology.json` 的类型里**没有"组"这个对象**（`_objects` 只有 notice/job/presence）。→ **写"组"就是新造一个本体里没有的东西**，必须先申报。
**要什么读数才能定**：作者是否要把"组"立成对象类型。

**D6 · 内容指纹放 `body.content[]` 还是新信封格？**
甲（①）：放 `body.content[]`（`algo/digest/size/media_type/name/role`）。
乙（③）：落在"账本里承载内容指纹的那个字段"——**在册九个信封字段中没有声明它**，所以要新增声明面。
**实仓**：两处都**没有**；`ontology.json` 的 `envelope` 是 8+2 格，`_section_map` 把"旁道与收据与缓存"整节标成 `attach: "out"`（挂不进五要素）。
**这不是分歧，是同一个洞的两种落点**；定哪一处都行，**但只能一处**（铁律①）。

**D7 · `world://core` 是"世界自身"还是"普通主体"？**
甲（⑤）：必须显式写明其一；不能靠默认豁免糊过去。
乙（④）：关键在"拿不出许可来源就不转递"这条门禁本身。
**实仓（重要订正）**：`world://core` **在 `policy.json.writes` 里被授权可写任意主体**，但**不在 `_permissions.grants` 的射程内**（那段只对 `world://presence/*` 判，源码射程自述已明写）。
⇒ 所以⑤那条"grants 里没有 core 就是漏配"**判错了性质**：不是漏配，是**射程只到这里**。
**仍要人裁的是**：这个"射程只到这里"要**写成一句权威口径**（甲），还是**把射程扩到全体主体**（= 门禁强度变更，源码已明说要人裁）。

**D8 · 撤回要不要传播到内容引用？**
甲（①）：两种做法都满足只追加，但会改变许可判据 ⇒ 判不了。
乙（③）：引用者是否必须再写一封——没说。
**实仓**：撤回在账本侧只有"撤哪条 seq"这一维（`body.after` = seq），**没有"撤一个内容引用"的概念**。→ 今天**做不到**传播，只能新立形态。

**D9 · 到货那一笔谁签：actor 本人还是翻译官？**
甲（①）：要由 actor（或按职权行事的翻译官）写一封 change/notice；机器不许自签。
乙（④）：机器帧不许被总线直接当 change 落账。
**实仓**：**无内容面**，所以这条今天无从执行。翻译官的职权边界在书里，**本人未核**（不在本次核对范围）。

**D10 · 那 6 处直读账本的脚本，迁移期算不算允许？**
甲（④）：目标收到 0，给复算命令。
乙（②）：若是当下允许的过渡，OS 级隔离就不能立刻上。
**实仓**：本人**未复核**那 6 处是否存在（背景称界面层不在版本控制内）。→ **这条今天连"观测对象"都不在受控范围内**，先把它纳入版本控制才有得判。

**D11 · 摘要算法与规范化选型**
甲（②）：JCS(RFC 8785) 或 CBOR canonical；multihash/multibase 自描述。
乙（⑥③）：应与 `WC-FMT-001` 一致；本处未读仓，判不了。
**实仓**：本仓已有的规范化口径是"**紧凑 + 键升序 + UTF-8 无 BOM**"，摘要形态是 `fnv1a64:<16位小写十六进制>`——**但这是非加密哈希，不得用于内容完整性判断**。⇒ 内容面**不能直接沿用** `fnv1a64` 当内容地址，得另定（且必须自描述）。

**D12 · 总线要不要是独立进程 / 跨主机？**
甲（②）：不跨主机用 AF_UNIX 对端凭据就够；跨主机要 SPIFFE 一类。
乙（全席）：背景没给，判不了。
**实仓**：部署件只有 AF_UNIX（`scripts/release/units/world-core.socket` 的 `ListenStream=/run/world-core/world.sock`；同目录另有 `world-core-dsh.socket` 指向 `dsh.sock`），**没有网络监听**。

**D13 · 保留期与 GC**
甲（②）：Kafka retention / git gc / IPFS GC 都是截断，都要拒。
乙（③）：内容面 GC 必须默认 deny，且必须**先证明不可达**才许动。
**实仓**：账本侧无任何 compaction 实施（`ledger.compact` 是**已声明但不可逆**的动作，只许 `world://user`）；内容面不存在。
→ **这条不是分歧，是两边合一**：GC 必须先有"账本侧的撤回"作为许可。

## §6 会红的判据清单（反例与真实违规同形态）

> **用法**：每条给「判据形态 / 会红的反例（= 真实违规的同形态）/ 怎么取数」。
> **本清单不是门禁**——它还没落地成脚本。**凡标〔形态〕的**是由人按结构看的（可写成静态门禁）；
> **凡标〔读数〕的**必须有**现取**读数（时点＋命令＋原始输出＋提交号），**本处不复述任何会漂的数**。
> **每条判据必须先在实盘跑一遍**：自证通过 ≠ 判据有效。**反例之间不许互相污染。**

**身份**

1. 〔形态〕信封必填 8 项**按结构取**，不按"字样第一次出现"取；`actor` 非空。
   反例：在 `dsh.sock` 的连接上发一封 `actor=world://core` 且被接受。
2. 〔形态〕口报出的身份 == 该口在在册表里的绑定。
   反例：在册是 `dsh.sock`→`world://agent/dsh`，连接时却报 `world://core`。
3. 〔形态〕一条连接在一个会话内不得充当两个主体。
   反例：同一 socket 先发 `actor=A` 再发 `actor=B`，两封都被接受。
4. 〔读数〕`实际监听 − 在册 ≠ ∅` 必须报红，且"在册未上线"要单独列出。
   反例：某个执行者私起 `world2.sock` 绕过世界；或报表写"两个 listener 正常"而其中一个在册未上线。
   取数命令（VM 上现取）：`ss -lx` 或 `/proc/<pid>/fd` 一类实际监听枚举 + `policy.json.listeners` 比对；**本处不给数**。

**寻址**

5. 〔形态〕`to` 的写入入口存在且可达（今天缺 `--to`）。
   反例：执行者发给应用 A 的私有指令被 GUI 连接也收到（"没有 `to` 就全放行"比"没有 `to` 就全丢"更危险）。
6. 〔形态〕"缺 `to` = 广播"这条口径**在册**，不是实现细节。
   反例：文档说"无 `to` 即拒"，实跑是广播 ⇒ 口径与实跑不一致。

**读法**

7. 〔读数〕同一 `--since` 重放得到同一事件集合；清掉口上的位点缓存后重放结果**不变**。
   反例：GUI 读法把"读到 seq=N"存本地文件，撤回记录插入后被它跳过。
8. 〔读数〕撤回一条 notice 后按 id 查：原记录**能逐字读回**，且撤回记录**指向**它。
   反例：实现用"删掉最后一行"救坏记录，账本行数变少。

**完整性**

9. 〔读数〕取树头 + 某条的包含证明 + 与上一时点树头的一致性证明。
   反例：给不出证明，或同一 seq 在两处内容不同而"树头"相同。
   ★ **今天的实情**：`chain` 锚点只有 genesis，**尾部整条删除不可检出**（`WC-CR-006` K-1）。⇒ **这条判据今天会红，而且是真红**——不许在改到之前报绿。

**内容面**

10. 〔形态〕账本任一记录的 `body` 里出现 base64/长字节块 ⇒ 红。**按 body 结构与长度判，不按关键词判**。
    反例：把一份文档 base64 塞进 change 的 `body` 落账。
11. 〔形态〕取件必须能指出世界侧放行它的那条许可记录。
    反例：客户端把 digest 粘进请求就拿到字节，世界侧没有任何许可记录。
12. 〔读数〕按账本里的 digest 取回内容并**重算摘要**。
    反例：账本写着"文档 D 已归档"，blob 已被清理，读数仍显示归档成功。
13. 〔形态〕账本里出现无 actor、或 actor 为机器自身的"已到货/已校验"信 ⇒ 红。
    反例：把传输完成回调直接 append 成一封信。
14. 〔读数〕**正控（钉住"不该红"）**：把内容面整面停掉，主干道仍能追加语义事件并落账。
    反例：此时主干道丢信或停摆 ⇒ 红。

**许可**

15. 〔读数〕一个在世界上没有任何授予的进程（但能打开 socket）写一条 change ⇒ 必须被拒。
    反例：新起的执行者只因能连上 `world.sock` 就能写 job 状态。
16. 〔形态〕`_permissions.default` **显式**为 `"deny"`。
    反例：用"没写 default"当默认允许（今天会红：`PermissionDefaultOpen`）。
17. 〔形态〕**申报 ≠ 授权**：先写 presence 申报，随即凭该身份写 change ⇒ 拒。
    反例：自报即通行。
18. 〔读数〕`world://core` 的许可地位**在册口径 == 实跑路径**。
    反例：文档写"core 需要许可"，实跑走的是 `writes` 直通；或反过来把"漏配"写成"设计如此"。

**只追加与幂等**

19. 〔读数〕同一 `id` 同内容投两次 ⇒ 账本**只有一条**事实，且**去重这件事有读数**。
    反例：重连重发把 job 状态记了两次，读法把它读成两个 job。
20. 〔读数〕并发两个进程各追加 N 条 ⇒ `seq` 不重复、不回退、不跳号后回填。
    反例：两个进程都以为拿到了锁，各自往同一偏移写。
21. 〔形态〕总线对外能力里出现 compaction/编辑/删帧/覆盖位点 ⇒ 红。
    反例：为省盘加一个"压缩日志"便利开关，用一次就破只追加。

**两句话分开**

22. 〔形态〕账本只有一个时间字段（actor 声明的 `at`）⇒ 要么补"核心收讫"一格，要么明写"不记且有意"。
    反例：核心用自己的时钟覆盖 `at`，事后把"网络慢"读成"事实发生在那一刻"。

**在册与实现一致**

23. 〔形态〕在册件的字段集 == 实现实际接受的字段集。
    反例：实现悄悄认了一个规格里没有的字段（如 `to_hint`）而下游已依赖它，在册件里查不到。
24. 〔形态/读数〕`policy.json.listeners` 的"生成关系"（渲染件）与在册一致；**在册未上线**要单独报。
    反例：`channel.json` 里凭空多出一条法律里没有的映射。
24b. 〔形态〕**"口→身份"只有一处权威**：`channel.json` 的 `listeners` 每一条都必须能在 `policy.json.listeners` 里解析到（今天 `ChannelConfig` 会**自己**读一份 `listeners`，两处不一致时**没有任何东西会红**）。
    反例：部署方往 `channel.json` 加一条 `{socket: /run/x.sock, actor: world://ghost}`，口起来了、账本里 actor 是 `world://ghost`，而法律里查不到这条映射。

**正控（不许乱红）**

25. 对一条正常、已声明、已授权的 change，以上守卫应**全绿**。
    反例：为了通过"实际 ⊆ 在册"把政策写成通配 `*`——守卫绿了而世界的约束没了（**"把守卫改成永远绿"的同一形态**）。

## §7 不该做什么（红线）

1. **不许把字节放进账本**——不许 base64、不许把文档塞 `body`、不许让账本长度随文件线性膨胀。
2. **不许用删除代替撤回**——不许 `rm` 字节、不许删最后一行、不许 compaction/截断来"救"坏记录。
3. **不许让总线持有状态**——不许总线缓存 job 状态/在场者名册/订阅表/投递位点/retained message。
4. **不许总线自持白名单**——许可来源必须在世界；总线只做"拿不出来源就不转递"。
5. **不许把"在册"当"在线"**——也不许把"上了线/连上了/占了名字"当作许可。
5b. **不许让"口→身份"出现两处在册**——`channel.json`（渲染物）自己带一份 `listeners` 是今天的现成形态；它必须**逐条**能在 `policy.json.listeners` 里解析到，**不许**在渲染物里新造映射（`policy.json._listeners_note` 的原话：总线上**不得**凭另一份配置文件自行定义映射）。
6. **不许机器自签世界的话**——重试/超时/心跳/传输完成/摘要校验结果都**不许**直接落成一封 change。
7. **不许用机器的话盖掉世界的话**——不许用对端凭据或核心时钟覆盖 `actor`/`at`。
8. **不许把内容索引做成第二本账**——不许有以 `digest→事实/actor` 为权威的反向索引。
9. **不许把"知道摘要"当"有权取"**——取件与列举分开授权；内容寻址的 digest 不是能力凭证。
10. **不许在口上存半包缓冲并据此裁决**——连接缓冲只能是机器细节。
11. **不许把界面层当落点**——新增的二进制/内容接入**不许**落在"不在版本控制内"的界面脚本里。
12. **不许为了消红放宽守卫**——不许把在册写成通配 `*`、不许把判据改成永远绿、不许把"未定"写成"已定"。
13. **不许改 `max_connections` 来"顺便"支持内容面**——今天写 >1 即拒启 `BadConcurrency`，那是**架构事实**，不是调优值。
