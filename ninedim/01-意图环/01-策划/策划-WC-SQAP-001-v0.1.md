## 一、质量目标（逐条可度量）

九项核心目标，每项给**数值 ＋ 度量方式 ＋ 测量时点 ＋ 一个「应当失败」的反例**：

| 编号 | 目标 | 目标值 |
|---|---|---|
| `QG-01` | 账本写入可靠性 | 追加 10 000 条：**丢 0 条、重 0 条** |
| `QG-02` | 崩溃恢复 | `kill -9` 后**已回执丢失 0 条**；恢复 P95 ≤ 2 s |
| `QG-03` | 读模型可重建 | 删掉读模型后重算与增量**100% 一致** |
| `QG-04` | 门禁不可绕过 | 越权用例**拦截率 100%** |
| `QG-05` | 重放性能 | 10 万条冷启动全量重放 **P95 ≤ 2 s** |
| `QG-06` | 单二进制部署 | 依赖白名单三条之内，无额外运行时 |
| `QG-07` | 代码结构 | 行覆盖 ≥ 80%、核心分支 ≥ 90%、四类路径各 ≥1 |
| `QG-11` | 投影同源 | 同源率 **100%** |
| `QG-12` | 投影不新增事实 | 可回溯率 **100%** |
| `QG-13` | 带检查点路径性能 | 续算耗时 ≤ 全量重算的 **1/2** |

**过程类目标**（`QG-08`–`QG-10`）与度量规程 `M-01`…`M-07` 见**附录**。

## 二、软件验证与确认计划（V&V）

**验证**＝"做得对"（符合规格）；**确认**＝"做对了东西"（满足需方需要）。

| 方法 | 用在哪 | 判据载体 |
|---|---|---|
| **评审** | 阶段门禁 R0–R8、框架变更 R5 | 阶段评审记录（逐次一份） |
| **检查** | 交付物齐备性、配置项"登记↔实存"、清单闭合性 | 三个自检脚本（机器判） |
| **分析** | 追溯完整性、风险与影响分析、强度不变量 | 追溯门禁 ＋ 变更影响分析 |
| **演示** | 骨架跑通、单二进制部署、一条命令跑通 | `check.sh`（构建→冒烟→测试→审计） |
| **测试** | 单元／契约／集成／系统／验收五级 | 测试记录与报告（逐级留痕） |

**V&V 报告**：单元/契约测试记录（R4）、系统测试报告（R6 前）、门禁执行证据（每次提交）、
验收测试报告（S6）、R0 记录（本次）。**每一份都必须描述计划的执行结果**，含命令与原始输出。

## 三、质量保证组织与职责

SQA 归口 ＝ **项目负责人兼任**（`ZiFan`）；**AI 不得担任 SQA、不得担任配置管理员、不得签署任何结论**。
**独立评审**由独立子代理承担（只作发现来源，其清单必须被逐条处置，**签署仍须人**）。

## 四、评审与检查

- **每条判据**必须有：操作定义、比对对象、期望值、**一个反例**；**四要素缺一即不可判定**。
- **正反例必须同档**：只给单侧结论的判据视为**未校验**。
- **未被校验 ≠ 校验通过**；"未能校验"按"校验不通过"处理。

## 五、证据规则

证据分两档：**文档核查**（路径 ＋ 逐字引用）与**实测**（命令 ＋ 原始输出 ＋ 环境版本号 ＋ 提交号）。
**凡引用运行结果者一律按实测档，不得以"S0 阶段"为由降档**。取不到原始输出者一律写
"待验证"并附验证命令，**不编造**。

## 六、本计划的自我限制

**不编造数值**；**【候选】值不构成测试判据**；未决项一律带责任人与关闭时点。
**AI 不代签、不代裁**；一切人名与结论栏由人填写。

| 证据 | 100 次注入的原始日志 + 恢复耗时分布 + 崩溃前后的账本 `sha256` |

### 2.4 本项目的三条专属验收测试（每个 Step 都要跑；必须原样纳入）

> 来源：`07-agent-native-os/4-计划/04-模块清单与实现顺序.md` §六（**原样引用，不得改写**）。
> 它们是贯穿全项目的**两条纪律**的唯一自动化检验——**这两条纪律是"世界只有一本账"的全部技术保障**。

**两条纪律（`4-计划/04` §六，原样）**

1. **一个写入口**：只有 `append(事件)` 能改世界。**别的模块拿不到这个函数**（代码层面封死，不靠约定）。
2. **缓存可重建**：任何"看起来像状态"的东西，都必须满足"**删掉它，能从账本 100% 重建**"。

> ⚠ **术语对照（2026-09-27 补，承 `WC-R4-DISP-001` §二 H 组第 12 行 / K 组末行）**：上句是**上游 `4-计划/04` §六 的原样引用**（本节已声明"**原样引用，不得改写**"），故**此处不改字**。但读的人必须知道：上游说的"`append(事件)`"在**本实现的 API 层面**对应 **`World::commit`**——实测 `src/lib.rs:133` 的 `pub fn commit(...)` 是**对外唯一写入口**，而 `src/ledger/mod.rs:286` 的 **`Ledger::append` 是 `pub(crate)`**（`:270` 注释自述"2026-09-26 收窄……不再是公开 API"）。**证据**：`docs/证据/EV-004.md`（`EV-11a`）。本文件 §1.3 与 §2.1.2 `M-01` 已按此口径改写。

**三个验收测试（`4-计划/04` §六，原样）**

| # | 测试 | 测的是 | **它在防什么（本项目专属解读）** | 对应度量 / 质量目标 |
|---|---|---|---|---|
| 1 | **追加 → 读回** | 账本本身对不对 | 防"写了一堆事件却读不回来"——即**持久化格式与解析不对称**（写的时候自由发挥，读的时候对不上）。账本是唯一真相，若它自己读写不对称，后面一切派生都无意义 | M-01 / QG-01 |
| 2 | **重启进程 → 事件还在** | 持久化真的生效 | 防"事件只在内存里"——即**把内存当成了真相**（进程一停，世界归零）。这条同时是最低成本的崩溃恢复检验 | M-02 / QG-02 |
| 3 | ★ **删掉读模型 → 重算，结果一致** | **读模型没有偷偷变成第二真相** | 防"两本账"——**这是本项目最重要的一个测试**，也是"一个真相"这条纪律的**唯一自动化检验**。读模型一旦持有账本里没有的状态（权限、待批集、渲染偏好以外的东西），它就成了第二本账；而两本账**必然对不上，且对不上时你不知道信谁**（`15` 篇 §八） | M-03 / QG-03 |

**执行纪律**

| 项 | 要求 |
|---|---|
| 频率 | **每个 Step（含 项目 Step 0.5 / 1 / 2 / 3 / 4 / 5 / 6 / 7 / 8）都要跑**，不是只在 S5 跑一次 |

| 证据 | 原始输出 + 命令 + 版本号 + 账本 hash，归档（见第十二章 RE-09） |

### 6.3 评审有效性规则（防止评审形式化）

> 本项目的特殊性：**材料几乎全部由 AI 起草**。因此"评审形式化"的主要形态不是"没人看"，
> 而是**"AI 写得很像样，人没看就签了"**。EV-08–EV-12 就是针对这一形态设的。

| 编号 | 规则 | 说明 | SQA 如何核查 | 违规处置 |
|---|---|---|---|---|
| EV-01 | **材料前置** | 评审材料至少提前 **1 个工作日**送达；会上不做首次阅读。**AI 起草的材料同样适用**——"AI 一秒就写好了"不构成豁免理由 | 核对送达时间戳与评审时间 | 评审无效，重新组织 |
| EV-02 | **角色齐备** | 缺测试参与的评审无效（可测试性是设计质量的核心判据）。**本项目"测试角色" = 独立子代理**，从 S1 起必参 | 核对签到与角色 | 评审无效，重新组织 |
| EV-03 | **记录留痕** | 每条评审意见有编号（`R#-###`）、责任人、闭环状态 | 核对评审记录 | 未闭环不得通过 |
| EV-04 | **结论明确** | 只有三种结论：**通过 / 有条件通过（附条件清单与期限）/ 退回** | 核对结论字段 | 结论含糊者按"退回"处理 |
| EV-05 | **时限约束** | 有条件通过的条件须在**下一阶段门禁前**闭环，否则自动降为退回 | 门禁前核查条件清单 | 自动降级，不得豁免 |
| EV-06 | **反形式化** | 某类评审连续 3 次"零意见通过"，须检查是否流于形式并调整检查单 | 统计评审意见数 | 强制复核检查单并调整 |
| EV-07 | **独立复核** | R4 模块评审须有 **≥ 1 名非本模块实现者**签字。**本项目：实现者 = AI，故"同级走查"由独立子代理承担，但签字必须是"人"** | 核对签字人与角色 | 评审无效 |
| **EV-08** | **AI 可代写，不可代签** | AI 可代写：评审材料、检查单预填、发现清单草稿、意见候选、趋势分析初稿。AI **不可**代写：结论、批准、签字、验收判定 | 核对每份记录的签字责任主体 | **结论无效**（承 REF-09 红线 1） |
| **EV-09** | **结论必须由人签署** | 任何 AI 生成的"评审通过""验收合格""准出"文本**一律无效**。结论栏必须由人签字或填写电子审批单号；无签署人的结论视为**未评审** | 核对结论栏签署人 | 门禁不通过；该阶段重做评审 |
| **EV-10** | **独立子代理只产出"发现清单"，不产出"评审通过"** | 子代理输出格式固定为：`发现编号 / 严重度 / **证据类型（EV-11a 文档核查 / EV-11b 实测）** / 证据 / 定位 / 建议`——**证据要求按 `EV-11` 分档**（2026-09-27 二轮复核补：原写"证据（命令 + 原始输出）"，会把 S0 文档核查类发现一律判为格式不合格，与 `EV-11a` 冲突）。**输出中不得出现"评审通过""验收合格"等结论性措辞**；若出现，该次评审材料作废并重新组织 | 逐份检查子代理输出是否含结论性措辞 | 材料作废，重新组织评审；记不符合项 |
| **EV-11** | **实测证据规则（2026-09-27 按三评委判词**分档**）** | **EV-11a（文档核查类）**：证据 = **文件路径 + 逐字引用原文**（不要求原始输出）；**EV-11b（实测数据类）**：证据 = **可复现命令 + 原始输出 + 环境版本号 + 代码提交号（四要素）**（⚠ **2026-09-27 订正**：原文只列三要素。**第四要素"代码提交号"不是新造门槛，而是本项目已有口径**——`WC-TP-001` §三 的"**证据四要素**"＝命令 + 原始输出 + 代码提交号 + 用例编号↔需求映射；两处此前不等价，现统一为**四要素**，承 `WC-R4-DISP-001` §二 H 组第 3 行"章号三处不一、目标计数三/四项 ⇒ 统一"）。**分档判据 = 该结论依据的是"文档文本"还是"程序运行"**——凡引用运行结果者**一律按 EV-11b**，**不得以"S0 阶段"为由降档**。**AI 不得生成测试报告中的"实际结果"**（REF-09 红线 4）。**① 否证子档（承标准符合性 U-03）**："零命中／不存在／未发现"类结论走 **`EV-11a` 的否证子档**——证据 = **命令 + 输出摘要 + 环境版本号**；理由是**"不存在的东西无文可引"**（`WC-OD-010` 等格式说明**已按 `G-20` 撤出仓库**，若强行要求"逐字引用原文"，该类结论**永远无法满足**）。**②"待归档"与"不合格"必须分开（承标准符合性 U-03）**：**证据待归档**（给了命令，缺原始输出／版本号）与**证据不合格**（证据**与结论不符**或**伪造**）是两件事——前者**可补**、后者**须重做**。处置：前者按"**未度量**"处理并**限期补档**（补档后结论复活，载体见 §十二 `RE-13`）；后者该数据**作废**、**已据此下的结论一并撤回**并记不符合项。**不得把"待归档"直接写成"不合格"**——那既误伤可补的证据，也让"不合格"失去分辨力。**③ 跨层传递纪律（承 `WC-SCMP-001` §8.4 `G-26` 的实测事故）**：**凡经"PowerShell → ssh → bash"之类跨层传递的命令，一律以 base64 传送后解码执行**，**不得依赖引号存活**。理由是可复现的实测事故：引号被逐层吃掉后，`git grep -I -l "$(printf "\r")"` 的**模式退化为空**，而**空模式匹配一切** ⇒ 同一条命令一次报"**152 个文件含 CR**"（**假警报**）、另一次报"**0 个文件含 CR**"（**假清白**）——**两个相反的错误结论都长着"实测"的样子**。配套纪律：**判据必须给出正反例**（一个应当匹配、一个不应当匹配），**只给单侧结论者视为未校验**。**④ 章号权威**：`EV-11` 位于 **§6.3**；本文件对它的引用此前出现 **§四／§五／§六** 三种写法（如 `WC-RV-R0-001:534` 写 §五），2026-09-27 **统一为 §6.3**（承 H 组第 3 行"章号三处不一"） | 抽查任意 3 条实测数据的可复现性 | 该数据作废并按"未度量"处理；若已据此下结论，结论撤回。**评审记录须设"证据类型"栏（`EV-11a` / `EV-11b`）；该栏留空或与结论依据不符者，该条证据判为不合格**（2026-09-27 二轮复核补：判词原本要求落此一条，前次落笔漏了） |
| **EV-12** | **反自我核查** | 实现者不得对自己实现的模块做最终判定。本项目 AI 是唯一实现者，故 R4 的"同级走查"由独立子代理执行，**但判定与签字仍由人** | 核对实现者 / 走查者 / 签字者三者是否分离 | 评审无效 |

## 十五、填写指引（本项目的自查）

1. **质量目标写成形容词是最常见的致命错误。** "稳定""美观""安全""高效"都无法判定达成与否，
   会把争议全部推迟到验收现场。本项目已把"世界要稳"改写成 QG-01/QG-02 两组可数、可计时的判据——
   **这是本文件最需要人确认的部分，也是最不该被"看起来挺合理"就放过的地方。**
2. **量化阈值不要留成 `<TBD-##>` 到 S5。** QG-05 的机器口径（TBD-12）必须在 **S1 需求基线前**关闭；
   留到测试阶段才定，等于测试无判据、验收无基准（模板指引 2）。
3. **不要把 SQA 计划写成"测试计划"。** 本计划管的是**过程与目标的受控性**（谁在什么门禁上检查什么证据），
   不是用例设计。**唯一例外**是 2.4 的三条专属验收测试——它们必须写进本计划，因为它们是"一个真相"纪律的**唯一自动化检验**。
4. **评审有效性规则不能只贴在文档里。** EV-01–EV-12 必须落到 `templates/06-评审类/01-阶段评审记录.md` 的固定字段与 CI 中，
   否则一定会退化为形式（模板指引 4）。**本项目的最可能退化形态是"AI 写得像样、人没看就签"——EV-08–EV-12 就是防它。**
5. **SQA 人员不得由被测模块的实现者兼任。** 本项目要实现者是 AI，所以 **AI 不得担任 SQA、不得担任配置管理员、不得代签**
   （3.1 + 3.2）。若项目负责人一人兼任全部人类角色，**必须在 R0 记录中声明并写补偿措施**（模板指引 5）。
6. **缺陷等级定义不要在项目中途改。** P0–P4 的判定口径一旦松动，"P0/P1 为 0"这条准出红线就自动失效。
   特别注意：本文件把"**性能不达标**"定为 P2、把"**两本账**"定为不低于 P1，**这两个定级本身就待人工确认**（8.1 提醒 2/3），
   一旦裁定改变，须走变更控制并重新批准本计划。
7. **【候选】不是"以后再填"。** R0 已就 `QG-01`/`QG-02`/`QG-04`/`QG-05`/`QG-06`/`QG-07` 作出裁定并升格，**项目负责人 2026-09-26 就 `QG-03`/`QG-11`/`QG-12`/`QG-13` 作出裁定并升格**，**九项核心目标的升格记录均已填入 RE-12**；**其余仍标【候选】者（§2.1.1 `QG-08`–`QG-10` 等）不得被引用为判据**；
   **把【候选】当基准使用属于流程违规**（3.3 Q-09），因为那等于**用 AI 编的数值当验收线**——这正是 REF-09 红线 3 要防的事。
8. **核心目标里 QG-01/02/03 是同一件事的三个侧面（账本-读模型）**：写不丢 → 停不丢 → 能重算。
   **任何一项不达标，S5 不得准出**；三项都通过，才谈得上"世界只有一本账"（`15` 篇 §八）。
9. **"文档多、代码为零"是本计划最大的现实风险。** 本文件写得越完整，越要警惕一种失败：
   **质量目标齐备、门禁齐全、证据为零**。若 S3 之后仍没有任何 RE-09/RE-10 原始输出，本计划的全部内容应被视为**未生效**。
10. **不要在 S6 临时另立标准。** 验收判据就是 2.1/2.1.1 的目标值；缺口 `G-01`/`G-02`/`G-04` 未在 R1 关闭前，
    S6 不得就"性能""部署"给出结论（2.3 规则）。
